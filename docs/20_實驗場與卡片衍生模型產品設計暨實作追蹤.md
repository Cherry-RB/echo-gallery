## 二、需求變更背景

### 2.1 儀表板原型暫停

2026-09-20 決定撤回尚未提交的回流與成長儀表板原型。該原型以存量、回流負載與異常統計為主要組織方式，尚未充分回答：

- 這些資訊為什麼值得注意？
- 它與內容轉化有什麼關係？
- 使用者下一步可以做什麼？
- 指標是否真的反映 Echo Gallery 的健康循環？

統計功能並未永久取消，但在 Card、Experiment、議題與事件資料尚未穩定前，不繼續擴張目前的指標與畫面。

### 2.2 議事廳已證明由上而下的思考價值

真實使用中，使用者曾以議事廳整理求職心理卡點與策略，更新議題進度、近況與研判，基於醒悟建立心得 Card，再將 Card 引用回素材池。

此流程是：

```text
Question → Material → Reasoning → Judgment / Action
```

議事廳因此承擔從問題出發、聚集素材並形成研判的 top-down thinking。

### 2.3 現有 growthStatus 未形成自然工作流

現有全域 `growthStatus` 是人工分類，而非狀態機。實際被標記為 `SEED` 的 Card 混合兩種需求：

1. **待整理**：來源可能失效，之後想補齊影片、文章或內容。
2. **思想種子**：內容令人心動，可能想模仿、擴寫、實踐或持續吸收。

前者描述 Card 本身尚未整理完成；後者描述 Card 在某個主題中可能長出新理解。兩者不應繼續共用同一個 enum。

### 2.4 新的成長模型

舊模型：

```text
一張 Card 是一株植物
SEED → GROWING → MATURE
```

新模型：

```text
Card A ─┐
Card B ─┼─→ 新 Card D
Card C ─┘
```

原始 Card 不必被改寫或升級。多張 Card 可以在同一座 Experiment 中形成關聯，再長出新的 Card。成長主要發生在 Card 之間，而不是要求每張 Card 走完相同生命週期。

## 三、產品目標與邊界

### 3.1 第一版目標

1. 讓使用者建立不同植栽主題，聚集彼此相關或令人心動的 Card。
2. 讓同一張 Card 在不同 Experiment 扮演不同培育角色。
3. 讓使用者從一張或多張 Card 長出新 Card，並保存思想來源。
4. 讓封存或暫停回流的 Card 仍保留於 Experiment。
5. 將「待整理」從思想成長中拆出，提供獨立標記與 Search 找回能力。
6. 安全保存並遷移既有非 `UNMARKED` growthStatus 資料。

### 3.2 非目標

- 不建立生產力儀表板、成熟率、種子債務或 Experiment 健康分數。
- 不要求 Card 依序升級。
- 不做 AI 聚類、自動摘要、自動成熟或自動產生 Card。
- 不建立 CardGrowthEntry、培育日誌或單卡成長時間軸。
- 不建立自由畫布、完整知識圖譜或多種 CardRelation taxonomy。
- 不把 Experiment 做成 Project、Todo、截止日期或完成率工具。
- 不讓 Experiment 操作改變回流排程、封存狀態或 WorkCard status。
- 不在本輪重新命名現有 Work／議題後端 domain。

## 四、核心概念與責任

| 模組 | 回答的問題 | 核心資料 |
|---|---|---|
| Card | 什麼值得保存與再次遇見？ | 內容、來源、個人理解、回流設定 |
| Today／看板 | 現在要重新看見什麼？ | 到期資格、批次與互動 |
| Tag | 如何橫向分類與找回？ | Card 與分類關係 |
| 實驗場 | 這些材料放在一起會長出什麼？ | ExperimentCard、CardRelation |
| 議事廳 | 這件事現在怎麼看、怎麼辦？ | 議題、素材、研判與更新 |

實驗場是 bottom-up thinking：

```text
Material → Pattern → Synthesis
```

議事廳是 top-down thinking：

```text
Question → Material → Reasoning
```

## 五、資料模型

### 5.1 關聯總覽

```text
User
 ├── Card
 │    ├── ExperimentCard ── Experiment
 │    ├── CardRelation(source) ── Card(derived)
 │    ├── WorkCard ── Work
 │    └── Tag
 └── Experiment
```

`ExperimentCard` 表示 Card 在 Experiment 中的歸屬、stage 與情境備註；`CardRelation` 表示 Card 與 Card 之間的思想衍生關係。兩者不可合併。

### 5.2 Experiment

```text
experiments
- id                  bigint primary key
- user_id             bigint not null
- title               varchar(255) not null
- description         text null
- hypothesis          text null
- theme_color         varchar(20) not null default 'LEAF'
- is_archived         boolean not null default false
- created_at          timestamptz not null
- updated_at          timestamptz not null
```

規則：

- Experiment 必須屬於登入使用者。
- 第一版允許封存、恢復與永久刪除。
- 封存 Experiment 不刪除 ExperimentCard 或 CardRelation。
- 永久刪除 Experiment 會移除它的 ExperimentCard 與 CardRelation，但保留所有 Card 本體；UI 必須先顯示影響範圍並取得確認。
- Experiment title 不自動建立 Tag。
- 不加入截止日期、完成率或健康分數。
- 後端限制 title 255 字、hypothesis 2,000 字、description 5,000 字；目前前端建立與編輯流程要求 hypothesis 非空白。
- `theme_color` 使用 `LEAF`、`LAKE`、`AMBER`、`LAVENDER`、`CORAL`、`MIST` 六個預設色盤，不接受任意 HEX。

索引：

```text
INDEX (user_id, is_archived, updated_at)
```

### 5.3 ExperimentCard

```text
experiment_cards
- id                  bigint primary key
- experiment_id           bigint not null
- card_id             bigint not null
- stage               varchar(20) not null
- note                text null
- added_at            timestamptz not null
```

stage：

| 值 | UI | 語意 |
|---|---|---|
| `SEED` | 種子土壤 | 令人心動、值得持續接觸，或可能成為新想法來源的材料。 |
| `GROWING` | 茁壯土壤 | 已長出的新連結、暫時理解、方法或正在驗證的想法。 |
| `MATURE` | 成熟土壤 | 目前相對穩定、可說明、可使用或已形成明確影響的理解。 |

stage 是關係角色，不是狀態機：

- Card 不必依序走過三個 stage。
- 原始種子可永久留在種子土壤。
- 新 Card 可直接放入茁壯或成熟土壤。
- 同一 Card 在不同 Experiment 可有不同 stage。
- 同一 Card 在同一 Experiment 第一版只能出現一次。

`note` 語意：

> 為什麼把這張 Card 放進這個實驗主題？希望從它長出什麼？它在此處扮演什麼角色？

規則：

- nullable `TEXT`，前後端限制 1,000 字。
- 可新增、編輯與清空；空白正規化為 `null`。
- 重新分類 stage 時保留 note。
- 同一 Card 在不同 Experiment 可有不同 note。
- 不顯示於一般看板，只顯示於 Experiment 與 Card Detail 的實驗關係區。

約束與索引：

```text
UNIQUE (experiment_id, card_id)
INDEX (experiment_id, stage, added_at)
INDEX (card_id)
```

第一版不加入手動排序 `position`。

### 5.4 CardRelation

```text
card_relations
- id                  bigint primary key
- experiment_id           bigint not null
- source_card_id      bigint not null
- derived_card_id     bigint not null
- relation_type       varchar(30) not null
- created_at          timestamptz not null
```

第一版唯一 relation type：

```text
DERIVED_FROM
```

語意：`derived_card_id` 是在指定 Experiment 中，由 `source_card_id` 促成或衍生的新 Card。

規則：

- 來源與衍生 Card 都必須屬於 Experiment owner。
- 來源 Card 必須已在該 Experiment 中。
- 新 Card 儲存時必須建立該 Experiment 的 ExperimentCard。
- 一張新 Card 可有多張來源 Card。
- CardRelation 第一版不另加 note；關係情境由 ExperimentCard.note 承接。
- Experiment 或 Card 封存、Card 暫停回流都不刪除關係。
- 永久刪除 Card 時移除相關 ExperimentCard 與 CardRelation。

約束與索引：

```text
UNIQUE (experiment_id, source_card_id, derived_card_id, relation_type)
CHECK (source_card_id <> derived_card_id)
INDEX (source_card_id)
INDEX (derived_card_id)
```

### 5.5 Card.needsProcessing

```text
cards.needs_processing boolean not null default false
```

它只回答：

> 這張 Card 的保存或整理是否尚未完成？

規則：

- 新建與既有 Card 預設為 `false`。
- 由使用者主動標記與清除。
- 不影響 Experiment、stage、回流排程、封存或 WorkCard。
- Search 提供「只看待整理」。
- 舊 `SEED` 不自動轉成 `true`，因為無法判斷原始意圖。

## 六、UX 與資訊架構

### 6.1 導覽

左側主導覽新增「實驗場」，與 Today、全部卡片、議事廳及標籤管理並列。實驗場不是看板，不應放在卡片看板子選單內。

### 6.2 實驗場列表

每座 Experiment 顯示：

- 名稱與最多四行假設；假設缺省時才回退顯示說明。
- 種子／茁壯／成熟三種 membership 數量，以該實驗主題色盤的亮色統計膠囊呈現。
- 最近更新時間。
- 右側由上而下排列更多操作、統計膠囊與靠右更新時間；卡片本身不重複顯示狀態 badge。

主要操作：

- 建立實驗主題。
- 進入 Experiment 詳情。
- 編輯名稱、假設、說明與識別色。
- 封存／恢復 Experiment。
- 以列表上方「觀察中／已封存」篩選器切換範圍。

列表不顯示完成率、成熟率、逾期或警告。

桌面版採每列兩張；900px 以下改為單欄。手機版將頁首操作與篩選器展開為可用寬度，不允許卡片或工具列造成水平捲動。主題色同時套用於列表統計膠囊與建立／編輯彈窗的已選色盤按鈕；未選色盤只保留鮮明圓點，選取後的背景、邊框與統計膠囊一致，文字維持一般介面色且不加粗，並使用 `color-mix` 配合亮色／暗色模式。

### 6.3 Experiment 詳情

```text
返回實驗場                      [狀態] [永久刪除] [編輯]
Experiment 名稱
Experiment hypothesis（需要時展開）
Experiment description（需要時展開）

[種入既有卡片] [長出新卡]

種子土壤
└── ExperimentCard 列表／分頁

茁壯土壤
└── ExperimentCard 列表／分頁

成熟土壤
└── ExperimentCard 列表／分頁
```

每張 ExperimentCard 顯示：

- Card ID、類型、標題與必要摘要。
- tags。
- ExperimentCard.note。
- 已封存／已暫停回流 badge。
- 查看 Card、編輯 note、重新分類、從 Experiment 移除。
- 選取後「長出新卡」。

三塊土壤可以視覺分區，但不設計成工作看板；不使用進度箭頭、完成百分比或「尚有 N 顆未成熟」。桌面可採三區段或雙欄自適應，手機改為垂直排列，不能要求水平拖曳。

實際 RWD 斷點以內容是否能正常操作為準：三欄土壤在中型寬度改為兩欄、720px 以下改為單欄；600px 以下的詳情操作列與議題詳情一致，狀態按鈕獨占第一列，永久刪除與編輯各占第二列一欄。假設與說明只有實際溢出時才顯示展開／收起。

### 6.4 種入既有 Card

1. 開啟 Card 選擇器。
2. 以 Card ID、標題或標籤找回 Card。
3. 選擇 stage。
4. 選填 ExperimentCard.note。
5. 建立 ExperimentCard，不修改 Card 本體與回流欄位。

選擇器應包含封存與暫停回流 Card，但清楚顯示狀態。已在此 Experiment 的 Card 不可重複加入。

此流程使用共用 `CardPickerDialog`：左側提供搜尋、分頁載入與穩定尺寸的選取列，右側以一般表單欄呈現已選 Card、土壤與種植備註。選取前後維持相同寬度與最小高度，只改變背景與「選擇／已選擇」文字，避免版面跳動。

### 6.5 長出新卡

1. 從 Experiment 選取一張或多張來源 Card。
2. 點選「長出新卡」。
3. 建立畫面保留來源 Card 標題與必要摘要，不自動拼接全文。
4. 使用既有 Card 欄位建立新內容。
5. 選擇新 Card 的 Experiment stage，預設 `GROWING`。
6. 選填新 ExperimentCard.note。
7. 儲存時以單一 transaction 建立 Card、ExperimentCard 與所有 `DERIVED_FROM`。
8. 原始 Card 保持原 stage。

若任何一步失敗，不得留下半套資料。後端 transaction 已保證原子性，前端會在 request pending 時避免重複提交；目前 API 尚無 idempotency key，因此已完成 request 的再次送出仍會建立另一張新 Card。

「長出新卡」使用 `QuickCreateCardDialog` 的 split layout：左側完整共用快速新增 Card 的欄位與驗證，右側只承接來源 Card、目標土壤與種植備註。兩種建立入口共用相同主要寬度；內容區禁止水平溢位，不顯示不必要的橫向捲軸。

### 6.6 Card Detail

Card Detail 新增一張「實驗主題與思想脈絡」資訊卡，卡內再分為兩個語意獨立的子區段：

```text
所在實驗主題
├── Experiment 名稱
├── stage
└── ExperimentCard.note

思想脈絡
├── 這張卡長自：source Cards
└── 這張卡長出了：derived Cards
```

- 「所在實驗主題」回答 Card 被種在哪裡、扮演什麼角色以及為什麼。
- 「思想脈絡」回答 Card 從哪些來源長出，後來又促成哪些新 Card。
- Card 可以只有 ExperimentCard 而沒有 CardRelation。
- 沒有任何衍生關係時，不顯示空的思想脈絡區塊。
- 點擊 Experiment 或 Card 可進入對應詳情。

Card Detail 同時提供 `needsProcessing` 的清楚狀態與切換操作，但不把它放入實驗場區塊。

所有實驗場相關彈窗以共用 `AppDialog` 統一置中、最大高度、footer 與內容捲動責任；桌面只允許彈窗內容區產生必要的垂直捲動，760px 以下改為接近滿寬並讓 workspace 轉成單欄，避免外部視窗、彈窗 body 與子清單同時競爭捲軸。

### 6.7 Search

目前新增以下條件；全域 `growthStatuses` 篩選在相容期仍保留，待 EXP-012 移除：

```text
□ 只看待整理
```

- 未勾選：不限制 `needsProcessing`。
- 勾選：只查詢 `needsProcessing = true`。
- 第一版不加入 Experiment／stage 複合篩選。
- 查詢不改變回流與回顧狀態。

## 七、Archive、回流與 Experiment 邊界

| Card 狀態 | Experiment membership | Experiment 顯示 |
|---|---|---|
| 正常回流 | 保留 | 正常顯示，可輔助顯示下次回流日 |
| 暫停回流 | 保留 | 顯示「已暫停回流」badge |
| 已封存 | 保留 | 淡化並顯示「已封存」badge |
| 永久刪除 | 移除 | 移除 ExperimentCard 與相關 CardRelation |

Experiment 查詢不得預設排除 archived Card，也不得因 `intervalDays`／`nextShowAt` 為 `null` 排除 Card。Experiment 操作不更新：

- `nextShowAt`
- `lastOfferedAt`
- `lastOpenAt`
- `openCount`
- `snoozeCount`
- `likeCount`
- WorkCard status

## 八、現行 API contract

> 本節記錄 2026.09.23 程式碼現況；後續若再修改 endpoint，仍須依 repository 規範先向使用者說明並確認 request／response 與相容策略。

### 8.1 Experiment

```text
GET    /api/experiments?archived=false&page=0&size=20
POST   /api/experiments
GET    /api/experiments/{experimentId}
PUT    /api/experiments/{experimentId}
PUT    /api/experiments/{experimentId}/archive
PUT    /api/experiments/{experimentId}/restore
DELETE /api/experiments/{experimentId}
```

Experiment list 回傳摘要與各 stage 數量，不載入完整 Card。

永久刪除只刪除 Experiment、其 ExperimentCard 與 CardRelation，不刪除 Card 本體。

### 8.2 ExperimentCard

```text
GET    /api/experiments/{experimentId}/cards?stage=SEED&page=0&size=10
POST   /api/experiments/{experimentId}/cards
PUT    /api/experiments/{experimentId}/cards/{cardId}/stage
PUT    /api/experiments/{experimentId}/cards/{cardId}/note
DELETE /api/experiments/{experimentId}/cards/{cardId}
```

新增 ExperimentCard request：

```text
cardId
stage
note optional
```

三個 stage 各自分頁，單次 size 設定合理上限，不一次載入整座 Experiment。

### 8.3 長出新 Card

```text
POST /api/experiments/{experimentId}/grow
```

request：

```text
sourceCardIds
stage
note optional
Card 建立所需欄位
```

後端在同一個 transaction：

1. 驗證 Experiment ownership。
2. 驗證全部來源 Card ownership 與 Experiment membership。
3. 建立新 Card。
4. 建立新 ExperimentCard。
5. 建立所有 `DERIVED_FROM`。
6. 回傳新 Card ID 與 Experiment 關係摘要。

### 8.4 Card Detail Experiment context

```text
GET /api/cards/{cardId}/experiments
GET /api/cards/{cardId}/relations
GET /api/cards/{cardId}/experiment-context
```

- experiments response：Experiment ID、title、hypothesis、stage、note、archived。
- relations response：每筆 relation 含 Experiment、source Card 與 derived Card，可由前端判斷目前 Card 的方向。
- experiment-context response：一次回傳 `experiments` 與 `relations`，供 Card Detail 合併區塊使用。
- 使用獨立查詢，避免一般 Card detail 永遠載入關聯資料。

### 8.5 needsProcessing 與 Search

```text
PUT /api/cards/{cardId}/processing-status
GET /api/cards/search?needsProcessing=true
```

processing-status request：

```json
{
  "needsProcessing": true
}
```

Search 未傳參數時不限制；傳入 `true` 時只回傳待整理 Card。第一版 UI 不需要提供「只看已整理」。

### 8.6 Garden → Experiment 暫時相容層

- `ExperimentController` 同時接受 `/api/experiments/**` 與 `/api/gardens/**`。
- Card membership 查詢同時接受 `/api/cards/{cardId}/experiments` 與 `/api/cards/{cardId}/gardens`。
- Card experiment／relation response 以 `experiment*` 為正式欄位，同時暫時回傳 `gardenId`、`gardenTitle`、`gardenHypothesis`、`gardenArchived`；context 也暫時回傳 `gardens` alias。
- 前端正式路由為 `/experiments` 與 `/experiments/:id`；舊 `/gardens` 路由只負責導向新路由。
- 相容層待資料庫 rename、已部署客戶端與回歸驗證完成後另案移除，不與本輪 UI／schema rename 混在同一步驟。

## 九、資料遷移與相容策略

### 9.1 前提

- 本機開發使用 Hibernate `ddl-auto=update`。
- 正式環境使用 `ddl-auto=validate`。
- repository 尚未導入 Flyway。
- 正式變更必須先執行可重複驗證的 PostgreSQL migration，再部署新版後端。

### 9.2 Additive migration

1. 備份正式資料庫。
2. 記錄 Card 總數與各 growth status 筆數。
3. 新增 `cards.needs_processing BOOLEAN NOT NULL DEFAULT false`。
4. 歷史 migration 先以 `gardens`、`garden_cards`、`garden_id` 建立資料，再由獨立 rename migration 切換為 Experiment schema；`card_relations`、約束與索引同批建立。
5. 對每位具有非 `UNMARKED` Card 的使用者建立「待重新整理（舊成長狀態）」Experiment。
6. 將 `SEED / GROWING / MATURE` Card 依原值建立 ExperimentCard。
7. `UNMARKED` 不建立 ExperimentCard。
8. 舊 `SEED` 不轉成 `needsProcessing=true`。
9. 比對 migration 前後各使用者與各 stage 筆數。
10. 重複執行 migration，確認沒有重複 Experiment 或 ExperimentCard。

### 9.3 Garden → Experiment rename migration

正式程式碼與 JPA mapping 已改用 `experiments`、`experiment_cards` 與 `experiment_id`。既有資料庫必須執行 `docs/migrations/20260923_rename_garden_to_experiment.sql`，依序改名資料表、foreign key 欄位、索引與可辨識的 constraint。

執行原則：

1. 停止新版後端，避免開發環境的 `ddl-auto=update` 在 rename 前先建立空的 `experiments`／`experiment_cards`。
2. 備份資料庫並記錄 `gardens`、`garden_cards`、`card_relations` 筆數。
3. 若新舊表同時存在，先確認新表確實為空；不得在未核對資料前直接刪表。
4. 以完整 SQL script 執行所有 `DO $$ ... $$;` 區塊，不可只選取其中一段 statement。
5. 任一 statement 失敗後先 `ROLLBACK`，找出第一個實際錯誤；`current transaction is aborted` 只是同一 transaction 已先失敗的後續訊息。
6. 完成後核對新表筆數、foreign key、unique constraint 與索引，再啟動 `ddl-auto=validate` 後端。

rename migration 已撰寫並通過程式碼層檢查；本機既有資料的完整執行與前後筆數驗證仍屬部署待辦，不能因檔案存在就標記為完成。

### 9.4 相容期

相容期內：

- 資料庫保留 `cards.growth_status`。
- 新後端開始提供 Experiment 與 needsProcessing。
- 舊版功能在新 UI 完成前仍可讀取 growthStatus。
- 不得同時把全域 growthStatus 與 Experiment stage 當成兩套可長期維護的正式功能。

### 9.5 舊模型退場

全站切換並驗證後，另開獨立任務移除：

- `cards.growth_status`
- `CardGrowthStatus`
- Card request／response 中的 growthStatus
- `PUT /api/cards/{id}/growth-status`
- Search growthStatuses
- Today「標記種子」舊操作
- 右側欄全域成長狀態統計
- WorkCard response 的 cardGrowthStatus
- Demo growthStatus 測資與初始化

舊欄位移除必須是獨立 migration，不與第一個 additive deploy 綁在同一次不可回復操作中。

### 9.6 Rollback

- Additive 階段 rollback：回退應用程式即可；保留新表與欄位不影響舊版。
- UI 切換階段 rollback：恢復舊 UI，舊 growthStatus 仍在。
- 舊欄位尚未 drop 前，不需逆向重建資料。
- drop 完成後若需回退，必須 forward-fix 或由備份／遷移 Experiment 重建，不依賴單純 image rollback。

## 十、效能與查詢原則

- Experiment list 使用聚合 summary query，不載入所有 Card entity。
- 三種 stage 分別分頁，避免一次載入整座 Experiment。
- ExperimentCard summary 不讀取不需要顯示的長篇 Card content。
- ExperimentCard 以 EntityGraph 同批載入 Card 與 tags，避免逐卡 N+1；三種 stage 數量由單一 group-by query 計算。
- CardRelation 以 EntityGraph 同批載入 Experiment、source Card 與 derived Card，並使用 source／derived index 支援雙向查詢。
- 所有 query 先由 user ownership 或 Experiment ownership 限縮。
- 不將全部 Card、ExperimentCard 或 Relation 載入 JVM／Browser 再篩選。
- 第一版不導入 Redis、Elasticsearch、Neo4j 或背景聚合。

目前「長出新卡」為了多選來源，只有在種入／長出彈窗開啟時才會將三種 stage 的頁面分批載完並合併；一般詳情初始載入仍只取每個 stage 當前頁。若未來單一 Experiment 出現大量 Card，來源選擇應改為後端搜尋與分頁，不把所有來源候選載入 Browser。

## 十一、前端資料與快取策略

現行主要 query keys：

```text
['experiments', filters]
['experiment', experimentId]
['experiment-cards', experimentId, stage, page]
['experiment-source-cards', experimentId]
['card-experiment-context', cardId]

```

Experiment Detail 目前以共用 invalidation helper 處理 mutation：

| 操作 | 目前更新／失效範圍 |
|---|---|
| 編輯／封存 Experiment | `experiment`、`experiment-cards`、`experiment-source-cards`、`experiments` |
| 加入／移除／重新分類 ExperimentCard | `experiment`、全部 stage pages、`experiment-source-cards`、`experiments` |
| 更新 ExperimentCard.note | `experiment`、全部 stage pages、`experiment-source-cards`、`experiments` |
| 長出新 Card | 與 membership mutation 相同，並由建立流程回傳新 Card |
| 永久刪除 Experiment | `experiments`，成功後返回列表 |

Card Detail 的 `card-experiment-context` 是獨立 query，進入或重新掛載詳情時依 TanStack Query 的 stale 規則重新取得。若未來需要跨頁即時同步而不重新掛載，應再補精準 invalidation；目前不維護全域手寫快取。

## 十七、產品觀察與去留條件

### 17.1 需要回答的問題

1. 使用者是否會自然建立 Experiment，而不是只用 Tag 或議題？
2. 把 Card 放在一起是否真的提高新 Card、理解或行動產生機率？
3. 「長出新卡」是否比修改原 Card 更符合真實思考方式？
4. ExperimentCard.note 是否有助於保存放入理由，而非成為重複內容？
5. CardRelation 是否在回看思想來源時產生價值？
6. 同一 Card 在不同 Experiment 使用不同 stage／note 是否真實發生？
7. 三塊土壤是否造成隱性升級壓力？
8. needsProcessing 是否協助找回待整理內容，還是再次形成待辦債務？
9. Experiment 是否和議事廳形成「bottom-up 生成、top-down 推演」的互補循環？

### 17.2 支持保留的證據

- 使用者會主動建立或回到 Experiment，而不是只在測試時使用。
- 至少數次新 Card 明確由 Experiment 中多張來源 Card 長出。
- ExperimentCard.note 在隔一段時間後仍能解釋放入理由。
- Card Detail 的思想脈絡協助回想理解如何形成。
- needsProcessing 被標記後會透過 Search 找回並清除。

### 17.3 縮減或回退訊號

- Experiment 長期只是另一種 Tag 列表。
- 使用者仍只修改原 Card，不使用「長出新卡」。
- 三 stage 造成「每顆種子都必須成熟」的心理債務。
- note 大量重複 Card content，沒有關係層價值。
- lineage 幾乎不被查看。
- needsProcessing 只累積不清理。

若驗證不成立，可移除實驗場主導覽或縮減 stage，但應依實際資料價值判斷是否保留 CardRelation 與 needsProcessing，不因 UI 回退就直接刪除使用者資料。
