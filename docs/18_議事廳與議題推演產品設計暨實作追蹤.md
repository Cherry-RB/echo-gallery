## 一、文件目的

本文件保存 2026-09-04 針對 Echo Gallery 下一階段產品模型的討論結果，並作為後續最小原型、實作追蹤、使用驗證與去留決策的共同基準。

本輪討論從官渡之戰的決策情境出發，逐步區分：

1. 世界或過去的自己留下了哪些值得再次遇見的內容。
2. 使用者目前正在面對哪些需要持續理解的事情。
3. 多份內容、現實條件與新回饋如何形成研判。
4. 使用者最後作了什麼決定，結果又如何改變下一次判斷。

### 1.1 官渡之戰揭示的不是單純智謀高下

本輪討論起點是《三國演義》官渡之戰。若只從結局倒推，很容易把它理解為曹操聰明、袁紹愚蠢；但站在戰爭進行中的曹操視角，情勢並不從容：正面作戰曾經失利，袁軍又以土山、弓弩與地道持續施壓，最後真正迫近失敗的是軍糧不足。曹操甚至曾考慮退回許都，荀彧的勸告也不是保證必勝，而是指出此刻先退的一方會先失去形勢。

許攸帶來烏巢情報後，曹操仍然面對情報可能有詐、親自出擊會使本營承受風險、援軍可能從背後抵達等問題。他的做法不是否認風險，而是在出發前安排留守與伏兵；進入決勝點後，又不讓次要威脅分散主要攻擊力量。

相較之下，袁紹並非完全沒有好方案。田豐、沮授、許攸與張郃分別提出過持久、後方突襲、糧道防守與救援烏巢等重要意見。問題在於：

- 不符合上位者期待的資訊容易被理解為反對。
- 反對容易再被轉譯成動搖軍心或忠誠問題。
- 謀臣之間的責任與利益衝突，會阻斷資訊向上流動。
- 選擇一個方案時，沒有充分處理判斷錯誤的代價。

因此官渡真正呈現的，不只是誰擁有比較多正確答案，而是：

> 一個決策系統能否讓不同資訊、壞消息與反對意見進入議事，形成研判，並轉化為可承擔的決斷與行動。

袁紹不是沒有人知道可能怎麼贏；他所建立的決策環境，使「知道」無法穩定變成「採取行動」。

### 1.2 從組織決策到個人的內在治理

個人的日常生活也不是由單一、清楚、永遠理性的聲音統治。內在可能同時存在：

- 想改變現況的願望。
- 對失敗與失去安全感的恐懼。
- 身體疲憊與注意力不足。
- 長期價值與短期舒適。
- 過去經驗形成的防衛與提醒。
- 外部環境、他人期待與社會比較。

這些聲音不必被簡化成誰真、誰假。疲憊、焦慮、羨慕、厭倦與渴望都可能是重要訊號，但訊號不等於命令。

如果「今天不想做」一出現就直接成為不行動的命令，信息層便跳過推演取得決策權；如果「我已經很累」立刻被內在的上位者斥為懶惰，重要軍情又會像田豐、沮授的意見一樣被排除。

本輪因此形成一個重要的主體性原則：

> 主體性不是沒有矛盾，也不是永遠知道自己要什麼；而是在內部眾聲喧嘩時，仍能主持矛盾、聽見訊號、衡量局勢，最後由自己作出決定。

### 1.3 糧草、地形與制度的日常映射

官渡的比喻也使個人行動中的幾個條件變得具體：

- **時間與精力是糧草**：一套策略聽起來正確，不表示目前補給足以執行。睡眠、工作消耗、通勤與注意力都會決定戰線能維持多久。
- **環境是地形**：手機位置、工具開啟成本、工作空間與娛樂入口會使某些行動更容易、某些行動更困難。
- **習慣是制度**：反覆證明有效的決策若能固定成習慣，就不必每天重新召開一次高成本的內在會議。

同一句「我今天不想做」，可能是補給不足，也可能是環境讓逃避過度容易。自我理解的價值不在於無限分析，而在於提高決策品質。

### 1.4 情報、謀略、決策與行動結果

上述思考被整理成四個不能混為一談的層次：

```text
【情報層】信息／訊號
我看見、感覺或遭遇了什麼？
        ↓
【謀略層】推演／研判
這些情報意味著什麼？
綜合局勢後，有哪些方針、方案與退路？
        ↓
【決策層】決議
整體性地綜合價值、資源與風險，
我現在選擇什麼？
        ↓
【行動層】行動結果
我採取行動後，現實如何回應這個決定？
        ↓
新的信息與下一輪判斷
```

情報可以是外部內容、身體感受、現實限制或世界回饋；推演與研判是理解情報、形成整體方針與比較可能方案的過程；決議才是對其中一種方案作出當下承諾；行動結果則會反過來修正下一輪判斷。

成熟的內在議事不是只聽喜歡的聲音，也不是讓所有聲音輪流當皇帝，而是：

> 先聽訊號，不急著服從；再看資源、限制與風險，最後才決斷。

### 1.5 Echo Gallery 目前停留的位置

Echo Gallery 現有核心流程是：

```text
我曾經認可某份內容
        ↓
收藏成 Card
        ↓
系統避免它沉底
        ↓
未來再次回到眼前
```

這套流程處理的是信息回流，但再次看見不保證內容會自然變成理解、決定或行動。

Card 多半保存社群貼文、文章、影片、觀點、靈感與自建筆記。它們可能提供重要思想，卻不是做決策所需的全部局勢。例如轉職議題還需要近期身心狀態、時間、財務、能力、職缺觀察與面試回饋；這些情境資料通常不值得各自成為未來反覆出現在 Today 的 Card。

因此，本輪沒有把 Card 重新定義成完整情報，也沒有繼續將 Plan、Action、Review 與所有人生資料塞進 Card。需要驗證的是 Card 與真實議題之間是否缺少一個中介層：

```text
Card
值得再次遇見的內容與思想素材
        ↓
議題
我現在正在理解、推進或解決的事情
        ↓
議事紀錄
現況／情報、推演／研判、決議與行動結果
```

現有 WorkCard 已能把多張 Card 聚合到同一個 Work，Work UI 也已試驗性地改稱培育計畫；但單一 description 無法表達盤面如何變化，也不能區分現況、研判、決議與結果。

### 1.6 議事原型要驗證的產品價值

議事廳不是要替使用者自動決策，也不負責判斷哪個內在聲音必然正確。它要驗證的是：

1. 曾經珍視的內容重新回流後，是否需要被帶進一個正在面對的議題。
2. 外部思想素材與當下現實局勢能否在同一處被看見。
3. 情報、謀略、決議與行動結果分開保存，是否能提高判斷品質。
4. 保存「當時為什麼這樣決定」，是否能避免之後重新從零開始焦慮。
5. 決議產生的行動結果，是否會成為下一輪研判的重要輸入。

Echo Gallery 不替使用者當曹操。它所能做的是：

> 不讓重要內容沉沒，不讓反對資訊被遺忘，讓使用者在決定時看得到自己掌握了什麼，並保留最後的決斷權。

本文件與第 16、17 份文件採用相同原則：

- 不因產品模型看起來完整，就一次實作所有可能功能。
- 已經由現行畫面、程式與使用需求確認的部分，可進入實作。
- 尚未確認是否會反覆使用的部分，先以最小設計驗證。
- 沒有真實需求證據的延伸功能，明確排除於本輪範圍之外。

本文件不代表議事廳已永久納入 MVP，也不代表卡片花園、正式 Project／Work 拆分或通用決策管理系統已通過驗證。原型完成後可以依真實使用結果保留、縮減或回退。

## 二、本輪結論摘要

```text
Card
值得保存，並依節奏重新回流的內容單位
        ↓
WorkCard
Card 在某個議題中的用途與採用狀態
        ↓
議事廳
容納多個需要持續探討的議題
        ↓
議題（技術上暫時沿用 Work）
背景、議事焦點、目前研判與結案條件
        ↓
議事紀錄（技術上暫稱 WorkEntry）
現況／情報 → 推演／研判 → 決議 → 行動結果
        ↓
未來可能形成真正的 Work
可完成、可檢視或可分享的具體成果
```

本輪事項依確定程度分成三類。

### 2.1 已確認需要補齊

1. Card 不改造成完整人生情報或決策紀錄。
2. Card 現有資料欄位先保留，只清理 UI 文案與責任邊界。
3. `reason` 同時承接「為什麼留下它」與「我思我長」，但不再混入金句語意。
4. 暫停回流屬於現行產品已確認需求，需補齊實作。
5. 取消封存應恢復封存前的回流狀態。

### 2.2 決定建立最小原型，但尚未確認永久保留

1. 現有 Work 的候選畫面語意由「培育計畫」調整為「議事廳中的議題」。
2. 議題增加議事焦點、背景、目前研判與結案／重議條件。
3. 新增一種議題範圍的時間性紀錄，承接現況／情報、推演／研判、決議與行動結果。
4. 資源盤點與風險評估先透過目前研判的提示結構承接，不建立固定欄位。
5. 後端類別、資料表、API 與路由暫時沿用 Work 命名。

上述功能完成後必須經過真實使用觀察，可以保留、縮減或回退；完成程式實作不等於正式納入長期 MVP。

### 2.3 仍然延後

1. Garden 與 CardGrowthEntry。
2. Task、Todo、截止日期與提醒。
3. AI 自動研判或決策。
4. 真正 Work／Output 模組。
5. 正式 Work／Project／Issue domain migration。

## 三、目前程式與資料模型基準

### 3.1 Card

目前 Card 支援 `NOTE` 與 `LINK`，主要資料包括：

- 標題、類型、來源連結與封面。
- `reason`、`summary`、`content` 三個文字欄位。
- 標籤與成長狀態。
- 回流間隔、下次回流時間、最近提供與回顧紀錄。
- 星標、稍後再看與封存狀態。

現行 Today 已採限量批次：

- 每批最多五張。
- 卡片被提供不等於完成回顧。
- 只有從 Today 進入詳情才推進 `nextShowAt`。
- 從其他看板、查詢或直接網址進入詳情，不改變回流排程。

### 3.2 Work 與 WorkCard

目前後端仍使用：

```text
Work
- title
- description
- status
- externalUrl
- completedAt

WorkCard
- workId
- cardId
- status: CANDIDATE / USED
- note
- linkedAt
- usedAt
```

目前前端已將 Work 顯示為「培育計畫」，並具有：

- 計畫列表與狀態篩選。
- 建立、查看與編輯計畫。
- 素材池與已運用兩種 WorkCard 狀態。
- 依 Card ID 或標題搜尋素材。
- 新增、移除、切換狀態與編輯用途 note。
- 從 Card Detail 查看及加入培育計畫。

本輪不重建上述關聯與素材管理流程。

### 3.3 現行主要缺口

現有 Work 可以保存一段整體 description，也可以聚合多張 Card，但不能清楚保存：

- 某個日期出現的新現況。
- 對多份素材與現況形成的研判。
- 某次決議與當時理由。
- 行動後產生的結果。
- 判斷如何隨時間改變。

將這些內容放進單張 Card 會錯置責任；全部覆蓋在 Work.description 又會失去歷程。因此本輪新增議題範圍的議事紀錄。

## 四、產品術語與責任邊界

### 4.1 待驗證的候選畫面術語

| 層級 | 畫面名稱 | 說明 |
|---|---|---|
| 導覽模組 | 議事廳 | 容納所有進行中或已結案的議題。 |
| 一筆現有 Work | 議題 | 需要持續匯集內容、更新局勢並形成研判的事情。 |
| 建立 Work | 發起議題 | 建立一個新的探討方向。 |
| Work Detail | 議題詳情／議事頁 | 查看議題盤面、素材與歷次議事紀錄。 |
| ProjectEntry | 議事紀錄 | 保存現況／情報、推演／研判、決議或行動結果。 |
| Decision Entry | 決議 | 使用者在某個時點作出的選擇。 |
| Result Entry | 行動結果 | 採取行動後的新事實、現實回饋與反省。 |

「上朝」保留為帶有產品性格的互動文案，不作為核心資料名詞。例如：

- 「今日上朝」：進入議事廳或回顧進行中議題的入口文案。
- 「今日無事退朝」：沒有需要處理內容時的空狀態文案。

第一版不建立每日上朝排程、提醒或待辦數量。

### 4.2 技術名稱暫時不遷移

為避免同時修改資料表、API、路由、Java package、前端型別與既有資料，本輪維持：

```text
Java entity：Work、WorkCard
資料表：works、work_cards
API：/api/works
前端路由：/works
```

議事紀錄第一版技術上使用 `WorkEntry` 與 `work_entries`，產品與 UI 文案使用「議事紀錄」。

待議題模型通過真實使用驗證後，再獨立評估：

```text
Work       → Issue 或 Project
WorkCard   → IssueCard 或 ProjectCard
WorkEntry  → IssueEntry 或 ProjectEntry
/works     → /issues 或 /projects
```

正式名稱不在本輪先行決定。

### 4.3 議題不是通用 Project Management

議題可以是問題、方向、創作、學習或需要推進的事情，但第一版不提供：

- 任務與子任務。
- 負責人與多人協作。
- 截止日期與提醒。
- 看板流程與甘特圖。
- 工時與進度百分比。
- 優先級矩陣。

議事廳的核心是提升「內容如何進入判斷」的可見性，不是取代 Todo 或專案管理工具。

## 五、Card 欄位與 UI 語意

### 5.1 Card 定義

Card 是：

> 值得保存，並依使用者設定節奏再次回流的內容單位。

Card 可以是：

- 外部文章、社群貼文、影片、作品或觀點。
- 使用者自己的筆記、提醒、想法或創作片段。

Card 不負責保存：

- 某個議題的完整現況盤點。
- 多份素材綜合後的策略研判。
- 決議歷史。
- 專案任務與執行清單。
- 與特定議題綁定的一次性結果。

### 5.2 現有資料欄位保持不變

本輪不新增、刪除或重新命名 Card 資料庫欄位。文字欄位透過一致的畫面文案重新定義：

| DB／API 欄位 | 統一 UI 名稱 | 用途 | 不再承擔的語意 |
|---|---|---|---|
| `reason` | 為什麼留下它／我思我長 | 收藏當下與這份內容的關係，以及重遇 Card 時產生的省思、聯想、認同、反對或成長。 | 不混稱來源金句或特定議題的完整研判。 |
| `summary` | 我見我聞／內容重點 | 來源內容摘要、摘錄或主要觀察。 | 不要求承接所有個人感受。 |
| `content` | 延伸筆記／完整內容 | 較長的補充、全文或與卡片本身直接相關的筆記。 | 不再提示 Plan、Action 或 Review。 |

其他欄位維持既有責任：

- `title`：內容識別。
- `type`、`url`、`coverImageUrl`：內容類型與來源。
- `tags`：分類與主動找回。
- `growthStatus`：使用者與這份內容目前的關係。
- `intervalDays`、`nextShowAt`：回流節奏。

### 5.3 快速建立畫面

快速建立 Card 的選填欄位統一顯示：

```text
為什麼留下它／我思我長
我見我聞／內容重點
延伸筆記／完整內容
```

`content` placeholder 不再出現「行動或覆盤」。

### 5.4 Card Detail

Card Detail 的內容區順序建議為：

1. 我見我聞／內容重點。
2. 為什麼留下它／我思我長。
3. 延伸筆記／完整內容。

若實際視覺閱讀更適合先顯示收藏理由，可以保留目前順序；但快速建立、詳情查看與編輯模式必須使用同一組欄位名稱。

### 5.5 成長狀態

`UNMARKED / SEED / GROWING / MATURE` 保留，並維持以下原則：

- 不形成每張 Card 都必須走完的流程。
- 不因加入議題或被標記為 `USED` 自動變更。
- 不影響 Today 回流排程。
- 本輪不新增 CardGrowthEntry、成熟證據或培育方向欄位。

## 六、暫停、恢復與封存回流規則

### 6.1 狀態模型

| 狀態 | `isArchived` | `intervalDays` | `nextShowAt` | Today 資格 |
|---|---:|---:|---:|---|
| 正常回流 | false | 非 null | 非 null | 到期後可進入。 |
| 暫停回流 | false | null | null | 不進入。 |
| 封存且原本正常回流 | true | 保留 | 保留 | 不進入。 |
| 封存且原本已暫停 | true | null | null | 不進入。 |

暫停回流與封存是不同維度：

- 暫停：Card 仍屬於一般內容，只停止主動回流。
- 封存：Card 離開一般使用畫面，但保留原有回流設定，以便取消封存。

### 6.2 暫停回流

暫停時必須設定：

```text
intervalDays = null
nextShowAt = null
```

行為要求：

- Card 仍存在於 All、Search、Tag 與已關聯議題。
- Card 不再進入 Today。
- 不增加 `openCount` 或 `snoozeCount`。
- 不修改 `growthStatus`。
- 重複暫停同一張 Card 應保持冪等。

### 6.3 恢復回流

由於暫停會清除 `intervalDays`，恢復時必須由使用者選擇新的回流間隔。

```text
intervalDays = 使用者選擇的天數
nextShowAt = 台北當日零時 + intervalDays
```

行為要求：

- 回流間隔必須符合既有 Card 驗證規則。
- 重複提交相同間隔不應額外增加互動或回顧次數。
- 恢復回流不等於完成 Today 回顧。

### 6.4 建議 API

為避免一般 Card update 無法明確區分「未傳欄位」與「刻意傳入 null」，第一版採明確動作 API：

```text
PUT /api/cards/{id}/pause

PUT /api/cards/{id}/resume
{
  "intervalDays": 10
}
```

兩個 API 都必須驗證 Card ownership。

在真正修改 endpoint 前，仍需依 repository 協作規則說明該次修改計畫與相容性影響。

### 6.5 封存與取消封存

封存時：

- `isArchived = true`。
- 保留 `intervalDays` 與 `nextShowAt`。
- 不因封存重新計算排程。

取消封存時：

- `isArchived = false`。
- 恢復使用封存前保存的回流狀態。
- 若 `nextShowAt` 已到期，Card 可在下一次 Today 選批時成為候選。
- 若 `nextShowAt` 尚未到期，等待原日期。
- 若封存前已暫停，取消封存後仍維持暫停。

取消封存不一律重算為 `today + intervalDays`，避免封存與取消封存偷偷改變使用者原本設定的節奏。

### 6.6 編輯內容與回流

一般 Card 內容更新暫不視為 Today 回顧：

- 更新 `updatedAt`。
- 不更新 `nextShowAt`。
- 不增加 `openCount`。
- 不重置 `snoozeCount`。

若未來實際使用中多次出現「編輯就是完成本輪整理」的需求，再另行驗證。

## 七、議事廳與議題模型

### 7.1 議事廳

議事廳是現有 Work List 的新產品語意。它顯示多個議題，而不是多件已完成作品。

列表應支援：

- 顯示進行中、已完成與已封存議題。
- 沿用現有狀態篩選。
- 顯示素材池與已運用數量。
- 進入議題詳情。
- 使用「發起議題」建立資料。

第一版不建立「今日必須處理幾個議題」的待辦數字。

### 7.2 議題定義

議題是：

> 一件需要持續匯集內容、補充現況、形成研判，並可能產生決議或成果的事情。

例如：

- Echo Gallery 下一階段應如何設計？
- 我是否應該開始轉職？
- 如何建立閱讀心得的穩定創作循環？
- 官渡之戰的決策系統為什麼形成不同結果？

### 7.3 議題欄位

在既有 Work 上新增 nullable 欄位，以保留舊資料相容性：

```text
Work
- title
- objective             新增
- description           保留，語意調整為背景
- currentAssessment     新增
- outcomeCriteria       新增
- status
- externalUrl
- completedAt
- createdAt
- updatedAt
```

| 技術欄位 | UI 名稱 | 核心問題 | 第一版規則 |
|---|---|---|---|
| `title` | 議題名稱 | 正在討論什麼？ | 必填，沿用現有長度限制。 |
| `objective` | 議事焦點 | 這次真正要回答或推進什麼？ | 選填，純文字。 |
| `description` | 背景 | 為什麼出現這個議題？ | 選填，承接既有資料。 |
| `currentAssessment` | 目前研判 | 根據目前掌握的內容，我怎麼看？ | 選填，保存最新版盤面。 |
| `outcomeCriteria` | 結案／重議條件 | 何時算有結論，或何時重新評估？ | 選填，純文字。 |
| `status` | 議題狀態 | 議題目前在哪一階段？ | 第一版沿用既有 enum 與 DB 值。 |
| `externalUrl` | 相關連結 | 是否有外部工作區或成果？ | 沿用既有欄位。 |

### 7.4 資源盤點與風險評估

第一版不新增以下固定欄位：

```text
resources
constraints
risks
unknowns
options
```

原因：

- 並非每個議題都需要完整資源或風險盤點。
- 固定欄位過多會讓議事廳變成專案管理表單。
- 目前尚未驗證使用者是否會反覆查詢、比較或更新這些資料。

`currentAssessment` 使用以下選填提示：

```text
目前局勢：

可用資源：

限制與風險：

關鍵未知：

目前傾向：
```

這些標題是填寫輔助，不是強制格式。若未來多數議題都自然重複使用其中某些項目，再評估提升為固定欄位。

### 7.5 目前研判與議事紀錄

`currentAssessment` 與 `ASSESSMENT` Entry 刻意同時存在：

- `currentAssessment`：現在這一刻的最新版盤面摘要。
- `ASSESSMENT` Entry：某個時間點形成的推演與研判。

新增 `ASSESSMENT` Entry 時，前端可提供「同步更新目前研判」選項；預設不應在背景中自動覆蓋。

直接編輯 `currentAssessment` 不必自動新增歷史紀錄，避免修正文字也形成一筆事件。

### 7.6 議題狀態

第一版維持既有 `WorkStatus` 值，僅調整 UI 文案，不在本輪 migration enum：

| 既有值 | 建議 UI 文案 |
|---|---|
| `IDEA` | 構想中 |
| `DRAFT` | 整理中 |
| `ACTIVE` | 議事中 |
| `DONE` | 已結案 |
| `ARCHIVED` | 已封存 |

是否需要 `PAUSED`，留待真實使用觀察；第一版不新增狀態。

## 八、議事紀錄模型

### 8.1 第一版資料模型

產品概念稱為 ProjectEntry／議事紀錄；在正式 domain migration 前，後端暫時使用 WorkEntry：

```text
WorkEntry
- id
- workId
- type
- content
- createdAt
- updatedAt
```

第一版不增加 `occurredAt`、附件、標籤、Card 外鍵或額外 metadata。

### 8.2 Entry 類型

| Enum | UI 名稱 | 回答的問題 | 範例 |
|---|---|---|---|
| `CONTEXT` | 現況／情報 | 發生了什麼？目前有哪些條件？ | 本週只有六小時可投入開發。 |
| `ASSESSMENT` | 推演／研判 | 這些情報意味著什麼？有哪些方針、方案與退路？ | 最大風險不是功能不足，而是模型同時膨脹。 |
| `DECISION` | 決議 | 所以現在選擇什麼？ | 先新增議事紀錄，不建立 Task。 |
| `RESULT` | 行動結果 | 採取行動後發生了什麼？現實如何回應？ | 使用一週後，確實留下三次可回看的判斷。 |

### 8.3 欄位與約束

- `work_id`：必填，外鍵指向 `works.id`，刪除 Work 時一併刪除 Entry。
- `type`：必填，字串 enum，最大長度 20。
- `content`：必填，去除前後空白後不可為空，第一版最大 5000 字。
- `created_at`、`updated_at`：由後端管理。
- 所有查詢與異動都必須驗證登入使用者擁有對應 Work。
- 建議建立 `(work_id, created_at DESC, id DESC)` 索引。

### 8.4 建議 API

```text
GET    /api/works/{workId}/entries
POST   /api/works/{workId}/entries
PUT    /api/works/{workId}/entries/{entryId}
DELETE /api/works/{workId}/entries/{entryId}
```

新增／修改 request：

```json
{
  "type": "ASSESSMENT",
  "content": "目前最大的未知是使用者是否會持續留下推演紀錄。"
}
```

response：

```json
{
  "id": 1,
  "workId": 3,
  "type": "ASSESSMENT",
  "content": "目前最大的未知是使用者是否會持續留下推演紀錄。",
  "createdAt": "2026-09-04T20:00:00+08:00",
  "updatedAt": "2026-09-04T20:00:00+08:00"
}
```

列表第一版依 `createdAt DESC, id DESC` 排列，不做分頁。當單一議題紀錄明顯增加後，再評估分頁。

### 8.5 Entry 編輯與刪除

- 使用者可以修改 type 與 content，以修正誤分類或文字。
- 刪除前必須顯示確認對話框。
- 刪除 Entry 不影響 Card、WorkCard、growthStatus 或 currentAssessment。
- 若刪除的 Entry 曾用「同步更新目前研判」更新 Work，第一版不自動回滾 currentAssessment。

### 8.6 第一版輸入提示

`CONTEXT`：

```text
發生了什麼？
有哪些新條件、限制、資源或外部回饋？
```

`ASSESSMENT`：

```text
這些資訊意味著什麼？
目前最大的未知或風險是什麼？
```

`DECISION`：

```text
決定：
理由：
下一步：
重新評估：
```

`RESULT`：

```text
我實際採取了什麼行動？
現實如何回應這個決定？
原本的判斷哪些成立、哪些需要修正？
```

## 九、議題詳情畫面

### 9.1 資訊架構

```text
議題名稱
[議事中]

背景

```

### 9.2 議題盤面

- 查看模式依欄位分段顯示，不再只顯示一大段「計畫設計」。
- 空欄位顯示低干擾提示，不顯示錯誤或欠債狀態。
- 編輯模式可一次修改所有議題欄位。
- `currentAssessment` 使用資源／風險提示模板，但不強制保留模板標題。

### 9.3 參考素材

沿用現有 WorkMaterialManager：

- 素材池 `CANDIDATE`。
- 已運用 `USED`。
- 用途 note。
- 新增、移除、狀態切換與搜尋。

第一版暫不將「已運用」改成「已納入判斷」，因議題也可能用於創作、學習與實作；待實際使用確認哪個語意更普遍。

### 9.4 議事紀錄時間軸

- 最新紀錄顯示在最前面。
- 每筆顯示類型、建立時間、內容、編輯與刪除操作。
- 類型使用不同 icon 或顏色，但不可只依顏色辨識。
- 空狀態說明議事紀錄不是必填日誌。
- 新增成功後，時間軸與右側相關統計若有變動應正確同步。

### 9.5 RWD

桌面版：

- 沿用 Work Detail 的置中內容寬度。
- 議題盤面、素材與時間軸垂直排列，避免三欄同時擁擠。

行動版：

- 所有區塊改為單欄。
- Entry 操作按鈕需可觸控且不依賴 hover。
- 長文字不可造成水平捲動。
- Dialog 在窄螢幕內保留可見的取消與儲存按鈕。

建議手動驗證寬度：

- 375px。
- 768px。
- 1280px 以上。

## 十一、資料庫與相容性策略

### 11.1 Additive migration

本輪資料庫變更應採向後相容的新增方式：

```text
works 新增 nullable 欄位：
- objective
- current_assessment
- outcome_criteria

新增 work_entries：
- id
- work_id
- type
- content
- created_at
- updated_at
```

舊 Work 資料：

- title、description、status、externalUrl 與 completedAt 原樣保留。
- 新欄位初始為 null。
- 前端不能因新欄位為 null 而阻止舊資料顯示或編輯。

### 11.2 正式環境

目前本機開發使用 Hibernate `ddl-auto: update`，正式環境使用 `ddl-auto: validate`。因此：

- 不可只修改 JPA entity 後直接部署。
- 必須先準備可重複檢查、可人工確認的 PostgreSQL migration SQL。
- migration 執行後，再部署使用新欄位的後端。
- 本輪不順便導入 Flyway，除非另開獨立任務並確認範圍。

### 11.3 不進行 destructive rename

本輪不執行：

- `works → issues/projects`。
- `work_cards → issue_cards/project_cards`。
- `/api/works → /api/issues`。
- `/works → /issues`。
- 刪除或搬移既有 Work 資料。

## 十四、實作後觀察計畫

議事原型可使用後，至少以兩個真實議題使用二至四週，記錄自然事件，不為驗證而刻意填滿所有欄位。

### 14.1 最低觀察樣本

- 至少建立兩個語意不同的議題。
- 每個議題至少連入兩張真實 Card。
- 累積至少十筆議事紀錄。
- 至少形成兩筆 DECISION。
- 至少有一筆 RESULT 回到先前決議。

### 14.2 需要回答的問題

1. 「議事廳／議題」是否比「培育計畫」更自然？
2. 議事焦點、背景、目前研判與結案條件是否能清楚區分？
3. `currentAssessment` 是否會被持續更新，還是逐漸過期？
4. 使用者是否自然記錄資源、限制、風險與未知？
5. CONTEXT／ASSESSMENT／DECISION／RESULT 是否容易區分？
6. 哪些 Entry type 最常使用，哪些幾乎不用？
7. 是否需要 `occurredAt`，還是 `createdAt` 已經足夠？
8. 是否需要把 nextAction、reviewAt 或 rationale 結構化？
9. WorkCard 的「素材池／已運用」在議題中是否仍自然？
10. 一個議題是否真的產生多個可獨立管理的 Work？
11. 是否出現任務管理需求，或只是被完整介面誘導出來？
12. 議事紀錄是否提升決策品質，還是增加填寫負擔？

### 14.3 資源與風險欄位的升級門檻

只有符合多項條件，才考慮新增固定欄位：

- 多數真實議題都自然填寫資源或風險。
- 相同資訊反覆散落在 currentAssessment 與 CONTEXT Entry。
- 使用者需要比較前後兩次資源或風險評估。
- 缺少結構化欄位造成決議遺漏重要條件。
- 需要依風險、資源或限制進行搜尋與篩選。

若只是偶爾使用，繼續保留在目前研判與議事紀錄中。

### 14.4 正式 domain migration 門檻

符合以下多項條件後，再規劃技術名稱遷移：

- 至少兩個議題累積真實 Card 與 Entry。
- 議題語意在二至四週使用中保持自然。
- 「培育計畫」或 Work 命名持續造成理解或開發困難。
- 至少一個議題形成兩個以上明確成果。
- 需要獨立管理成果的狀態、素材或外部連結。
- 議題與真正 Work 的關聯語意能清楚區分。

正式遷移必須另立文件與任務，不在本輪追蹤表內直接執行。

## 十六、原型完成與去留定義

本輪需要區分「工程原型完成」與「產品功能通過驗證」。資料表與畫面建立完成，只代表具備真實使用的條件，不代表議事廳永久納入 MVP。

### 16.1 工程原型完成

需同時符合：

1. Card 的內容、議題與議事紀錄責任清楚分離。
2. 使用者可以暫停並恢復 Card 回流。
3. 取消封存能恢復封存前的回流狀態。
4. 現有 Work 資料可無損地以候選議題方式呈現。
5. 議題原型可以保存盤面、聚合 Card 並形成時間性紀錄。
6. 每個任務具備相應自動測試與手動驗證紀錄。
7. 正式環境 schema 變更有受控 migration 與部署順序。
8. 已具備執行本文件第十四章觀察計畫的條件。

### 16.2 產品功能通過驗證

觀察期結束後才判斷是否符合：

1. 議事紀錄在非刻意測試下自然產生。
2. 記錄確實協助使用者形成、回顧或修正判斷。
3. 議題盤面與 Entry 的維護成本沒有高於所得價值。
4. 議事廳提供的價值無法由 Card、Search、Tag 與現有 Work note 輕易取代。
5. 使用者仍希望從主要導覽主動進入此功能。

### 16.3 不通過時的回退方式

若驗證不支持完整議事廳，可依實際結果採取：

- 移除議事廳主導覽，保留既有 Work／培育計畫入口。
- 回退「議事廳／議題」候選文案，不動既有資料。
- 移除或隱藏沒有自然使用的議題欄位。
- 只保留有價值的 Entry type。
- 保留歷史資料為唯讀，停止新增議事紀錄。
- 不進行正式 Work／Project／Issue domain migration。

如果議事紀錄沒有自然產生，本輪不繼續擴張為更完整的決策系統；如果只有部分 Entry 類型產生價值，後續只保留必要部分。
