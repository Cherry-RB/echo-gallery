## 一、文件目的

本文件保存 2026-09-04 針對 Echo Gallery 下一階段產品模型的討論結果，並作為後續最小原型、實作追蹤、使用驗證與去留決策的共同基準。

本輪討論從官渡之戰的決策情境出發，逐步區分：

1. 世界或過去的自己留下了哪些值得再次遇見的內容。
2. 使用者目前正在面對哪些需要持續理解的事情。
3. 多份內容、現實條件與新回饋如何形成研判。
4. 使用者最後作了什麼決定，結果又如何改變下一次判斷。

### 1.1 官渡之戰揭示的不是單純智謀高下

本輪討論起點是《三國演義》官渡之戰。若只從結局倒推，很容易把它理解為曹操聰明、袁紹愚蠢；但站在戰爭進行中的曹操視角，情勢並不從容：正面作戰曾經失利，袁軍又以土山、弓弩與地道持續施壓，最後真正迫近失敗的是軍糧不足。曹操甚至曾考慮退回許都，荀彧的勸告也不是保證必勝，而是指出此刻先退的一方會先失去形勢。

許攸帶來烏巢情報後，曹操仍然面對情報可能有詐、親自出擊會使本營承受風險、援軍可能從背後抵達等問題。他的做法不是否認風險，而是在出發前安排留守與伏兵；進入決勝點後，又不讓次要威脅分散主要攻擊力量。

相較之下，袁紹並非完全沒有好方案。田豐、沮授、許攸與張郃分別提出過持久、後方突襲、糧道防守與救援烏巢等重要意見。問題在於：

- 不符合上位者期待的資訊容易被理解為反對。
- 反對容易再被轉譯成動搖軍心或忠誠問題。
- 謀臣之間的責任與利益衝突，會阻斷資訊向上流動。
- 選擇一個方案時，沒有充分處理判斷錯誤的代價。

因此官渡真正呈現的，不只是誰擁有比較多正確答案，而是：

> 一個決策系統能否讓不同資訊、壞消息與反對意見進入議事，形成研判，並轉化為可承擔的決斷與行動。

袁紹不是沒有人知道可能怎麼贏；他所建立的決策環境，使「知道」無法穩定變成「採取行動」。

### 1.2 從組織決策到個人的內在治理

個人的日常生活也不是由單一、清楚、永遠理性的聲音統治。內在可能同時存在：

- 想改變現況的願望。
- 對失敗與失去安全感的恐懼。
- 身體疲憊與注意力不足。
- 長期價值與短期舒適。
- 過去經驗形成的防衛與提醒。
- 外部環境、他人期待與社會比較。

這些聲音不必被簡化成誰真、誰假。疲憊、焦慮、羨慕、厭倦與渴望都可能是重要訊號，但訊號不等於命令。

如果「今天不想做」一出現就直接成為不行動的命令，信息層便跳過推演取得決策權；如果「我已經很累」立刻被內在的上位者斥為懶惰，重要軍情又會像田豐、沮授的意見一樣被排除。

本輪因此形成一個重要的主體性原則：

> 主體性不是沒有矛盾，也不是永遠知道自己要什麼；而是在內部眾聲喧嘩時，仍能主持矛盾、聽見訊號、衡量局勢，最後由自己作出決定。

### 1.3 糧草、地形與制度的日常映射

官渡的比喻也使個人行動中的幾個條件變得具體：

- **時間與精力是糧草**：一套策略聽起來正確，不表示目前補給足以執行。睡眠、工作消耗、通勤與注意力都會決定戰線能維持多久。
- **環境是地形**：手機位置、工具開啟成本、工作空間與娛樂入口會使某些行動更容易、某些行動更困難。
- **習慣是制度**：反覆證明有效的決策若能固定成習慣，就不必每天重新召開一次高成本的內在會議。

同一句「我今天不想做」，可能是補給不足，也可能是環境讓逃避過度容易。自我理解的價值不在於無限分析，而在於提高決策品質。

### 1.4 情報、謀略、決策與行動結果

上述思考被整理成四個不能混為一談的層次：

```text
【情報層】信息／訊號
我看見、感覺或遭遇了什麼？
        ↓
【謀略層】推演／研判
這些情報意味著什麼？
綜合局勢後，有哪些方針、方案與退路？
        ↓
【決策層】決議
整體性地綜合價值、資源與風險，
我現在選擇什麼？
        ↓
【行動層】行動結果
我採取行動後，現實如何回應這個決定？
        ↓
新的信息與下一輪判斷
```

情報可以是外部內容、身體感受、現實限制或世界回饋；推演與研判是理解情報、形成整體方針與比較可能方案的過程；決議才是對其中一種方案作出當下承諾；行動結果則會反過來修正下一輪判斷。

成熟的內在議事不是只聽喜歡的聲音，也不是讓所有聲音輪流當皇帝，而是：

> 先聽訊號，不急著服從；再看資源、限制與風險，最後才決斷。

### 1.5 Echo Gallery 目前停留的位置

Echo Gallery 現有核心流程是：

```text
我曾經認可某份內容
        ↓
收藏成 Card
        ↓
系統避免它沉底
        ↓
未來再次回到眼前
```

這套流程處理的是信息回流，但再次看見不保證內容會自然變成理解、決定或行動。

Card 多半保存社群貼文、文章、影片、觀點、靈感與自建筆記。它們可能提供重要思想，卻不是做決策所需的全部局勢。例如轉職議題還需要近期身心狀態、時間、財務、能力、職缺觀察與面試回饋；這些情境資料通常不值得各自成為未來反覆出現在 Today 的 Card。

因此，本輪沒有把 Card 重新定義成完整情報，也沒有繼續將 Plan、Action、Review 與所有人生資料塞進 Card。需要驗證的是 Card 與真實議題之間是否缺少一個中介層：

```text
Card
值得再次遇見的內容與思想素材
        ↓
議題
我現在正在理解、推進或解決的事情
        ↓
議題更新
最近有什麼改變、現在怎麼看、接下來做什麼
```

現有 WorkCard 已能把多張 Card 聚合到同一個 Work，Work UI 也已試驗性地改稱培育計畫；但單一 description 無法同時承擔議題的整體說明、最近變化、此刻看法與下一步，也無法保留判斷如何隨時間改變。

本輪最初曾規劃以 `CONTEXT / ASSESSMENT / DECISION / RESULT` 四類議事紀錄分別保存上述過程。重新參考 Linear Project Update、Asana Status Update 與 Basecamp Hill Chart 所代表的成熟互動模式後，決定不要求使用者先替每筆內容分類。抽象的四層模型仍作為思考框架，但日常輸入收斂成一次較自然的「議題更新」。

### 1.6 議事原型要驗證的產品價值

議事廳不是要替使用者自動決策，也不負責判斷哪個內在聲音必然正確。它要驗證的是：

1. 曾經珍視的內容重新回流後，是否需要被帶進一個正在面對的議題。
2. 外部思想素材與當下現實局勢能否在同一處被看見。
3. 每次回到議題時，是否能在十秒內看懂「要處理什麼、最近怎麼樣、接下來做什麼」。
4. 以「最近改變／現在看法／接下來」取代四類 Entry，是否能降低記錄摩擦。
5. 保存不同時間點的更新，是否能避免之後重新從零開始焦慮，並讓行動結果回到下一輪判斷。

Echo Gallery 不替使用者當曹操。它所能做的是：

> 不讓重要內容沉沒，不讓反對資訊被遺忘，讓使用者在決定時看得到自己掌握了什麼，並保留最後的決斷權。

本文件與第 16、17 份文件採用相同原則：

- 不因產品模型看起來完整，就一次實作所有可能功能。
- 已經由現行畫面、程式與使用需求確認的部分，可進入實作。
- 尚未確認是否會反覆使用的部分，先以最小設計驗證。
- 沒有真實需求證據的延伸功能，明確排除於本輪範圍之外。

本文件不代表議事廳已永久納入 MVP，也不代表卡片花園、正式 Project／Work 拆分或通用決策管理系統已通過驗證。原型完成後可以依真實使用結果保留、縮減或回退。

## 二、本輪結論摘要

```text
Card
值得保存，並依節奏重新回流的內容單位
        ↓
WorkCard
Card 在某個議題中的用途與採用狀態
        ↓
議事廳
容納多個需要持續探討的議題
        ↓
議題（技術上暫時沿用 Work）
議題名稱、議題焦點、背景、整體研判與結案條件
        ↓
議題更新（技術上暫稱 WorkProgressUpdate）
最近有什麼改變 → 現在怎麼看 → 接下來做什麼
        ↓
未來可能形成真正的 Work
可完成、可檢視或可分享的具體成果
```

本輪事項依確定程度分成三類。

### 2.1 已確認需要補齊

1. Card 不改造成完整人生情報或決策紀錄。
2. Card 現有資料欄位先保留，只清理 UI 文案與責任邊界。
3. `reason` 同時承接「為什麼留下它」與「我思我長」，但不再混入金句語意。
4. 暫停回流屬於現行產品已確認需求，需補齊實作。
5. 取消封存應恢復封存前的回流狀態。

### 2.2 決定建立最小原型，但尚未確認永久保留

1. 現有 Work 的候選畫面語意由「培育計畫」調整為「議事廳中的議題」。
2. 議題增加議題焦點、背景、整體研判與結案／重議條件，作為相對穩定的整體說明。
3. 新增「議題更新」，以最近改變、現在看法與接下來三個欄位保存時間性變化，不使用 Entry type。
4. 議題詳情右欄直接顯示最新五筆更新，其中第一筆完整、後四筆只摘要最近改變；更新不複製或自動同步到議題整體欄位。
5. 「接下來」只屬於最新議題更新，不建立 Work.nextAction、NextAction entity 或 Todo 流程。
6. 資源盤點與風險評估保留為選填思考角度，不建立固定欄位。
7. 後端類別、資料表、API 與路由暫時沿用 Work 命名。

上述功能完成後必須經過真實使用觀察，可以保留、縮減或回退；完成程式實作不等於正式納入長期 MVP。

### 2.3 仍然延後

1. Garden 與 CardGrowthEntry。
2. Task、Todo、截止日期與提醒。
3. AI 自動研判或決策。
4. 真正 Work／Output 模組。
5. 正式 Work／Project／Issue domain migration。

## 三、目前程式與資料模型基準

### 3.1 Card

目前 Card 支援 `NOTE` 與 `LINK`，主要資料包括：

- 標題、類型、來源連結與封面。
- `reason`、`summary`、`content` 三個文字欄位。
- 標籤與成長狀態。
- 回流間隔、下次回流時間、最近提供與回顧紀錄。
- 星標、稍後再看與封存狀態。

現行 Today 已採限量批次：

- 每批最多五張。
- 卡片被提供不等於完成回顧。
- 只有從 Today 進入詳情才推進 `nextShowAt`。
- 從其他看板、查詢或直接網址進入詳情，不改變回流排程。

### 3.2 Work 與 WorkCard

目前後端仍使用：

```text
Work
- title
- objective
- description
- currentAssessment
- outcomeCriteria
- status
- externalUrl
- completedAt

WorkCard
- workId
- cardId
- status: CANDIDATE / USED
- note
- linkedAt
- usedAt
```

目前前端已將 Work 候選語意調整為「議事廳／議題」，並具有：

- 議題列表與狀態篩選。
- 發起、查看與編輯議題。
- 初版議題盤面。
- 素材池與已運用兩種 WorkCard 狀態。
- 依 Card ID 或標題搜尋素材。
- 新增、移除、切換狀態與編輯用途 note。
- 從 Card Detail 查看及加入培育計畫。

本輪不重建上述關聯與素材管理流程。

### 3.3 現行主要缺口

現有 Work 已能保存議題整體欄位並聚合多張 Card，但還不能保存：

- 相較於上一次，最近出現了什麼變化。
- 使用者在該時間點怎麼理解這些變化。
- 根據這次更新，接下來準備做什麼。
- 判斷如何隨時間改變。

將這些內容放進單張 Card 會錯置責任；反覆覆蓋 Work 的整體欄位又會失去歷程。因此本輪新增議題範圍的「議題更新」，並保持議題整體資料與時間性更新彼此獨立。

## 四、產品術語與責任邊界

### 4.1 待驗證的候選畫面術語

| 層級 | 畫面名稱 | 說明 |
|---|---|---|
| 導覽模組 | 議事廳 | 容納所有進行中或已結案的議題。 |
| 一筆現有 Work | 議題 | 需要持續匯集內容、更新局勢並形成研判的事情。 |
| 建立 Work | 發起議題 | 建立一個新的探討方向。 |
| Work Detail | 議題詳情／議事頁 | 查看議題焦點、最新更新、整體研判、素材與歷次更新。 |
| WorkProgressUpdate | 議題更新／近況更新 | 保存最近改變、當時看法與接下來。 |
| Latest Update | 最新近況 | 議題首頁直接呈現最近一筆議題更新。 |

「上朝」保留為帶有產品性格的互動文案，不作為核心資料名詞。例如：

- 「今日上朝」：進入議事廳或回顧進行中議題的入口文案。
- 「今日無事退朝」：沒有需要處理內容時的空狀態文案。

第一版不建立每日上朝排程、提醒或待辦數量。

### 4.2 技術名稱暫時不遷移

為避免同時修改資料表、API、路由、Java package、前端型別與既有資料，本輪維持：

```text
Java entity：Work、WorkCard
資料表：works、work_cards
API：/api/works
前端路由：/works
```

議題更新第一版技術上使用 `WorkProgressUpdate` 與 `work_progress_updates`；資料概念仍稱「議題更新」，主要操作文案則使用更符合議事語境的「提出近況」。

待議題模型通過真實使用驗證後，再獨立評估：

```text
Work       → Issue 或 Project
WorkCard   → IssueCard 或 ProjectCard
WorkProgressUpdate → IssueUpdate 或 ProjectUpdate
/works     → /issues 或 /projects
```

正式名稱不在本輪先行決定。

### 4.3 議題不是通用 Project Management

議題可以是問題、方向、創作、學習或需要推進的事情，但第一版不提供：

- 任務與子任務。
- 負責人與多人協作。
- 截止日期與提醒。
- 看板流程與甘特圖。
- 工時與進度百分比。
- 優先級矩陣。

議事廳的核心是提升「內容如何進入判斷」的可見性，不是取代 Todo 或專案管理工具。

## 五、Card 欄位與 UI 語意

### 5.1 Card 定義

Card 是：

> 值得保存，並依使用者設定節奏再次回流的內容單位。

Card 可以是：

- 外部文章、社群貼文、影片、作品或觀點。
- 使用者自己的筆記、提醒、想法或創作片段。

Card 不負責保存：

- 某個議題的完整現況盤點。
- 多份素材綜合後的策略研判。
- 決議歷史。
- 專案任務與執行清單。
- 與特定議題綁定的一次性結果。

### 5.2 現有資料欄位保持不變

本輪不新增、刪除或重新命名 Card 資料庫欄位。文字欄位透過一致的畫面文案重新定義：

| DB／API 欄位 | 統一 UI 名稱 | 用途 | 不再承擔的語意 |
|---|---|---|---|
| `reason` | 為什麼留下它／我思我長 | 收藏當下與這份內容的關係，以及重遇 Card 時產生的省思、聯想、認同、反對或成長。 | 不混稱來源金句或特定議題的完整研判。 |
| `summary` | 我見我聞／內容重點 | 來源內容摘要、摘錄或主要觀察。 | 不要求承接所有個人感受。 |
| `content` | 延伸筆記／完整內容 | 較長的補充、全文或與卡片本身直接相關的筆記。 | 不再提示 Plan、Action 或 Review。 |

其他欄位維持既有責任：

- `title`：內容識別。
- `type`、`url`、`coverImageUrl`：內容類型與來源。
- `tags`：分類與主動找回。
- `growthStatus`：使用者與這份內容目前的關係。
- `intervalDays`、`nextShowAt`：回流節奏。

### 5.3 快速建立畫面

快速建立 Card 的選填欄位統一顯示：

```text
為什麼留下它／我思我長
我見我聞／內容重點
延伸筆記／完整內容
```

`content` placeholder 不再出現「行動或覆盤」。

### 5.4 Card Detail

Card Detail 的內容區順序建議為：

1. 我見我聞／內容重點。
2. 為什麼留下它／我思我長。
3. 延伸筆記／完整內容。

若實際視覺閱讀更適合先顯示收藏理由，可以保留目前順序；但快速建立、詳情查看與編輯模式必須使用同一組欄位名稱。

### 5.5 成長狀態

`UNMARKED / SEED / GROWING / MATURE` 保留，並維持以下原則：

- 不形成每張 Card 都必須走完的流程。
- 不因加入議題或被標記為 `USED` 自動變更。
- 不影響 Today 回流排程。
- 本輪不新增 CardGrowthEntry、成熟證據或培育方向欄位。

## 六、暫停、恢復與封存回流規則

### 6.1 狀態模型

| 狀態 | `isArchived` | `intervalDays` | `nextShowAt` | Today 資格 |
|---|---:|---:|---:|---|
| 正常回流 | false | 非 null | 非 null | 到期後可進入。 |
| 暫停回流 | false | null | null | 不進入。 |
| 封存且原本正常回流 | true | 保留 | 保留 | 不進入。 |
| 封存且原本已暫停 | true | null | null | 不進入。 |

暫停回流與封存是不同維度：

- 暫停：Card 仍屬於一般內容，只停止主動回流。
- 封存：Card 離開一般使用畫面，但保留原有回流設定，以便取消封存。

### 6.2 暫停回流

暫停時必須設定：

```text
intervalDays = null
nextShowAt = null
```

行為要求：

- Card 仍存在於 All、Search、Tag 與已關聯議題。
- Card 不再進入 Today。
- 不增加 `openCount` 或 `snoozeCount`。
- 不修改 `growthStatus`。
- 重複暫停同一張 Card 應保持冪等。

### 6.3 恢復回流

由於暫停會清除 `intervalDays`，恢復時必須由使用者選擇新的回流間隔。

```text
intervalDays = 使用者選擇的天數
nextShowAt = 台北當日零時 + intervalDays
```

行為要求：

- 回流間隔必須符合既有 Card 驗證規則。
- 重複提交相同間隔不應額外增加互動或回顧次數。
- 恢復回流不等於完成 Today 回顧。

### 6.4 建議 API

為避免一般 Card update 無法明確區分「未傳欄位」與「刻意傳入 null」，第一版採明確動作 API：

```text
PUT /api/cards/{id}/pause

PUT /api/cards/{id}/resume
{
  "intervalDays": 10
}
```

兩個 API 都必須驗證 Card ownership。

在真正修改 endpoint 前，仍需依 repository 協作規則說明該次修改計畫與相容性影響。

### 6.5 封存與取消封存

封存時：

- `isArchived = true`。
- 保留 `intervalDays` 與 `nextShowAt`。
- 不因封存重新計算排程。

取消封存時：

- `isArchived = false`。
- 恢復使用封存前保存的回流狀態。
- 若 `nextShowAt` 已到期，Card 可在下一次 Today 選批時成為候選。
- 若 `nextShowAt` 尚未到期，等待原日期。
- 若封存前已暫停，取消封存後仍維持暫停。

取消封存不一律重算為 `today + intervalDays`，避免封存與取消封存偷偷改變使用者原本設定的節奏。

### 6.6 編輯內容與回流

一般 Card 內容更新暫不視為 Today 回顧：

- 更新 `updatedAt`。
- 不更新 `nextShowAt`。
- 不增加 `openCount`。
- 不重置 `snoozeCount`。

若未來實際使用中多次出現「編輯就是完成本輪整理」的需求，再另行驗證。

## 七、議事廳與議題模型

### 7.1 議事廳

議事廳是現有 Work List 的候選產品語意。它顯示多個需要持續理解或推進的議題，而不是多件已完成作品，也不是另一套 Todo 看板。

列表應支援：

- 顯示進行中、已完成與已封存議題。
- 議事廳首頁使用全寬單欄議題列表，不以常駐跨議題側欄壓縮主要內容。
- 桌面版每張議題卡在同一卡片內分成左右兩區：左側是議題整體，右側是最新一次更新；狀態移入左側頂端，使右側從卡片頂端開始，不為跨欄狀態預留空白。行動版在同一卡片內改為上下排列。
- 第一層以「進行中／已完成／已封存／全部」篩選生命週期；第二層進行階段不常駐占用版面，點擊「進行中」才以 Popover 浮現「所有階段／探索中／已釐清／推進中」，選取後回寫到原按鈕標籤。素材池與已運用數量維持中性色。
- 議題整體區優先呈現名稱、議題焦點、結案／重議條件、狀態、素材數量、相關連結與議題資料更新日期；最新更新區以清楚但克制的底色呈現完整三欄快照，只有確有近況時才顯示近況日期，內容可依溢位個別展開。
- 移除「議題總覽」、「範圍」及「查看完整議題與歷程」等可由版面或整卡互動理解的提示文字。
- 跨議題「近期動態」降為次要按鈕與 Drawer，需要時才依 `createdAt DESC, id DESC` 查詢最新 12 筆更新；不使用 `Work.updatedAt` 冒充推進紀錄。同一議題的多次更新可各占一筆。
- 議題卡片與跨議題 Drawer 的更新都分別呈現「最近有什麼改變？／現在怎麼看？／所以接下來呢？」三欄，欄位為空時不顯示，內容溢位時可個別展開。
- Work 列表 response 提供查詢時衍生的 `latestProgressAt` 與最新一筆更新內容，不把最新更新複製進 works；議題列日期與排序取 `updatedAt`、`latestProgressAt` 中較新者。
- 議題的外部連結沿用 Card 看板的「鏈結 icon＋網域」語言，避免只顯示無法理解的 icon。
- 標題最多顯示三行，議題焦點最多顯示五行；最新更新三欄依內容溢位提供展開，完整歷程仍到詳情閱讀。
- 進入議題詳情。
- 使用「發起議題」建立資料。

第一版不建立「今日必須處理幾個議題」的待辦數字、完成百分比或定期更新壓力。

### 7.2 議題定義與首頁判準

議題是：

> 一件需要持續匯集內容、補充現況、形成研判，並可能產生決議或成果的事情。

議題首頁採用 Project Overview／Update 類型的成熟設計思想，但不照搬團隊專案管理功能。使用者每次進入後，應在十秒內回答：

1. 我這一輪要處理什麼？
2. 最近發生了什麼、現在怎麼看？
3. 接下來準備做什麼？

「議事廳」是產品語意；「駕駛艙」只描述資訊架構，不作為畫面名稱，避免同時混用兩套隱喻。

### 7.3 議題欄位與責任

既有 Work 以 nullable 欄位保留舊資料相容性：

```text
Work
- title
- objective
- description
- currentAssessment
- outcomeCriteria
- status
- externalUrl
- completedAt
- createdAt
- updatedAt
```

| 技術欄位 | UI 名稱 | 核心問題 | 第一版規則 |
|---|---|---|---|
| `title` | 議題名稱 | 這整件事情是什麼？ | 必填，沿用既有長度限制。 |
| `objective` | 議題焦點 | 這個議題最需要回答、釐清或推進什麼？ | 選填，顯示於標題下方。 |
| `description` | 背景與脈絡 | 哪些經歷、條件或變化使它值得處理？ | 選填，承接既有 description。 |
| `currentAssessment` | 整體研判 | 綜合長期累積的資訊，我如何理解整個議題？ | 選填，由使用者自行維護。 |
| `outcomeCriteria` | 結案／重議條件 | 何時算有結論，或什麼變化出現時需要重議？ | 選填，純文字。 |
| `status` | 議題階段 | 現在偏向探索、釐清、推進或完成？ | 沿用既有 enum 與 DB 值。 |
| `externalUrl` | 相關連結 | 是否有外部工作區、文件或成果？ | 沿用既有欄位。 |

議題整體欄位回答「這整件事是什麼」；議題更新回答「最近走到哪裡」。兩者不可因欄位名稱相近而自動複製或同步。

`objective`、`description`、`currentAssessment` 與 `outcomeCriteria` 在 PostgreSQL 均使用 `TEXT`。前後端保留 50,000 字安全上限，以防止異常請求或意外貼入過大內容；這不是產品內容長度建議。UI 以寫作提示與漸進式展開維持可讀性，不使用小型硬限制迫使使用者刪減思考。

### 7.4 發起議題的漸進式輸入

發起議題的原因通常正是事情還沒想清楚，因此建立 Dialog 不應要求先完成整份議題盤面。

預設只顯示：

- 議題名稱，必填。
- 議題焦點，選填。

「補充背景與條件」展開後才顯示：

- 背景與脈絡。
- 整體研判。
- 結案／重議條件。
- 相關連結。

畫面提示應明確說明「先把事情放上桌，其他內容可以之後再補」。長文字欄位保留 50,000 字安全上限，但平常不持續顯示 `0 / 50000`；達到上限時再由輸入控制與驗證訊息阻止超額內容。

### 7.5 整體研判與思考提示

`currentAssessment` 的 UI 改稱「整體研判」，保存相對穩定、經使用者整理過的綜合性理解。它不是最新近況，也不由最新議題更新自動覆寫。

資源、限制、風險、未知、方案與退路仍不建立固定欄位。需要引導時，提供簡短常駐提示與由使用者主動觸發的「使用研判框架」：

```text
目前局勢：

這可能意味著：

可行方針：

限制、風險與退路：

目前傾向：
```

只有使用者主動選擇時才插入 textarea；不得因點入欄位而消失，也不得在已有內容時直接覆蓋。這些標題是思考輔助，不是必填格式。

### 7.6 議題階段

第一版維持既有 `WorkStatus` 值，不在本輪 migration enum。為表達從降低未知到實際推進的差異，候選 UI 文案調整為：

| 既有值 | 候選 UI 文案 |
|---|---|
| `IDEA` | 探索中 |
| `DRAFT` | 已釐清 |
| `ACTIVE` | 推進中 |
| `DONE` | 已完成 |
| `ARCHIVED` | 已封存 |

階段由使用者自己判斷，不由 Todo 數量、完成百分比或系統推算。是否需要 `PAUSED`，留待真實使用觀察。

## 八、議題更新模型

### 8.1 為何由分類紀錄改成 Update

最初的 `CONTEXT / ASSESSMENT / DECISION / RESULT` 模型能完整對應情報、謀略、決策與行動結果，但日常輸入時會增加「這一筆到底屬於哪類」的分類負擔。

第一版改採 Update，而不是 Log：不要求使用者完整記錄每個事件，而是重新回答「相較於上一次，現在有什麼不同」。一次更新以三個自然問題承接完整循環：

```text
最近有什麼改變？
        ↓
現在怎麼看？
        ↓
接下來做什麼？
```

情報、推演、決策與行動結果仍是產品背後的思考框架，不再成為使用者必須選擇的 enum。

### 8.2 第一版資料模型

```text
WorkProgressUpdate
- id
- workId
- changeSummary
- assessment
- nextStep
- createdAt
- updatedAt
```

第一版不增加 type、health、statusSnapshot、occurredAt、附件、標籤、Card 外鍵或額外 metadata。

### 8.3 欄位與約束

| 技術欄位 | UI 提示 | 規則 |
|---|---|---|
| `changeSummary` | 最近有什麼改變？ | 選填，可記錄事實、回饋、進展或問題。 |
| `assessment` | 現在怎麼看？ | 選填，記錄該時間點的看法。 |
| `nextStep` | 所以接下來呢？ | 選填，只突出一個最能推進事情或降低未知的動作。 |

三個內容欄位至少一項去除前後空白後不可為空。第一版各欄位最大長度於實作前依畫面用途確認，不因資料庫使用 TEXT 就無限制輸入。

其他規則：

- `work_id` 必填，外鍵指向 `works.id`，刪除 Work 時一併刪除更新。
- `created_at`、`updated_at` 由後端管理。
- 所有查詢與異動都必須驗證登入使用者擁有對應 Work。
- 建議建立 `(work_id, created_at DESC, id DESC)` 索引。
- 最新更新由排序結果取得，不在 Work 額外保存 latestUpdateId。

### 8.4 與議題整體資料的邊界

發布、修改或刪除議題更新時：

- 不修改 `Work.currentAssessment`。
- 不修改 `Work.status`。
- 不把 `nextStep` 複製到 Work。
- 不自動產生或更新其他 Work 欄位。

議題首頁直接顯示查詢結果中的最新一筆更新；刪除最新一筆後，排序中的下一筆自然成為最新近況。

### 8.5 CRUD 與建議 API

議題更新保留完整 CRUD：

```text
GET    /api/works/{workId}/updates?page=0&size=5
POST   /api/works/{workId}/updates
PUT    /api/works/{workId}/updates/{updateId}
DELETE /api/works/{workId}/updates/{updateId}
GET    /api/work-updates/recent?limit=12
```

單一議題更新列表 response：

```json
{
  "items": [],
  "page": 0,
  "size": 5,
  "hasNext": false
}
```

新增／修改 request：

```json
{
  "changeSummary": "研究了 Linear、Asana 與 Basecamp 的 Project UX。",
  "assessment": "建立議題應該很輕，完整推演應逐步發生。",
  "nextStep": "把建立 Dialog 縮減成議題名稱與議題焦點。"
}
```

新增／修改 response：

```json
{
  "id": 1,
  "workId": 3,
  "workTitle": "Echo Gallery 下一階段",
  "changeSummary": "研究了 Linear、Asana 與 Basecamp 的 Project UX。",
  "assessment": "建立議題應該很輕，完整推演應逐步發生。",
  "nextStep": "把建立 Dialog 縮減成議題名稱與議題焦點。",
  "createdAt": "2026-09-06T20:00:00+08:00",
  "updatedAt": "2026-09-06T20:00:00+08:00"
}
```

單一議題更新列表使用受限 Slice 回應：`items`、`page`、`size`、`hasNext`。列表依 `createdAt DESC, id DESC` 穩定排序，`page` 最小為 0、`size` 最小為 1 且最大為 20；不為顯示總筆數額外執行 count query。詳情首頁查最新 5 筆，歷次更新 Dialog 每頁查 10 筆。

### 8.6 編輯與刪除

- 使用者可以修改三個內容欄位，以修正錯字或表達。
- `updatedAt` 與 `createdAt` 不同時，UI 顯示「已編輯」。
- 刪除前必須顯示確認對話框。
- 編輯或刪除更新不影響 Card、WorkCard、growthStatus 或議題整體欄位。
- 第一版不將歷史更新設為不可修改的稽核紀錄，因產品仍是個人工具。

### 8.7 「接下來」不是 Todo

`nextStep` 只是某次更新中對眼前下一個動作的描述，不建立獨立 NextAction entity、checkbox、完成時間、期限、提醒或清單。

議題首頁突出最新更新的 `nextStep`，但不提供「完成」或「完成並更新」特殊流程。下一次提出近況時，使用者重新寫下新的接下來；若最新更新沒有 nextStep，首頁不沿用更舊、可能已過期的下一步。

## 九、議題詳情畫面

### 9.1 資訊架構

```text
頁首：返回議事廳                [階段下拉] [編輯議題] [刪除議題]
┌──────────────────────────────┬──────────────────────────────┐
│ 左欄白底：議題整體              │ 右欄灰底：推進與素材            │
│ 議題名稱與階段軌跡              │ [最近推進白卡]                  │
│ 議題焦點／整體研判              │ 最新一筆：完整三欄               │
│ 結案／重議條件／相關連結        │ 較早四筆：摘要與時間同列         │
│ 背景與脈絡／建立與更新時間      │ [參考素材白卡]                  │
│                              │ 素材池／已運用各自分頁            │
└──────────────────────────────┴──────────────────────────────┘
```

桌面版平均分成 1:1 兩欄，並各自捲動。左欄白底固定承擔較穩定的議題整體資訊，以同一連續面板與段落分隔；右欄是灰底工作區，將時間性的更新與參考素材分成兩張白色卡片。階段下拉不放入任一欄，改置於頁首並與編輯按鈕並列；低頻的永久刪除操作同樣位於頁首。行動版改為上下排列；左側階段軌跡負責理解，頁首階段按鈕負責修改。

### 9.2 發起與編輯

- 發起議題預設只顯示議題名稱與議題焦點，降低建立門檻。
- 其他欄位收進可展開的「補充背景與條件」。
- 編輯議題只修改 Work 的整體欄位，不混入議題更新。
- 標題／議題焦點、整體研判、背景、結案／重議條件與相關連結使用各自聚焦的編輯入口；仍保留完整編輯作為低頻操作。
- 左欄階段軌跡負責快速理解推進位置；頁首的階段下拉是可點擊的直接編輯控制，並與「編輯議題」保持同寬。標題旁不另外顯示重複狀態標籤。
- 「刪除議題」是確認後才執行的永久操作：刪除 Work、所屬 WorkProgressUpdate 與 WorkCard 關聯，保留原始 Card；想保留資料但退出主要流程時使用封存。
- 欄位空白不是錯誤或欠債，不顯示完成率。
- 長文字不持續顯示 50,000 字計數；達到安全上限時才由輸入控制與驗證訊息阻止超額內容。

### 9.3 最新近況與整體研判

- 右欄初次只查最新五筆 WorkProgressUpdate：第一筆完整顯示三欄，後四筆沿時間軸只摘要「最近有什麼改變？」；資料不複製進 Work。
- 沒有更新時，以低干擾方式邀請使用者在有變化時再發布，不要求定期打卡。
- 整體研判獨立顯示與編輯，文案明確說明它是較穩定的綜合理解。
- 不顯示 Linear 式 On track／At risk／Off track，也不顯示 stale 或欠更新警告。

### 9.4 參考素材

沿用現有 WorkMaterialManager：

- 素材池 `CANDIDATE`。
- 已運用 `USED`。
- 用途 note。
- 新增、移除、狀態切換與搜尋。
- 素材池與已運用各自以 `status`、`page`、`size` 分頁；初始各 10 筆，單次最多 20 筆，並各自提供載入更多。

「已運用」表示 Card 曾進入思考、創作、決議或行動，不代表使用者同意它；支持、反駁與風險提醒都可以算運用。是否將按鈕改稱「納入議事」，待實際使用確認創作與實作型議題是否同樣自然。

### 9.5 議題更新與時間軸

- 主要操作使用「提出近況」，不使用「新增 Entry」或要求選擇 type；「最近推進」標題上方不再重複顯示「議題更新」分類字樣。
- 三個欄位都選填，但至少需填一項。
- 「查看歷次更新」開啟 Dialog 後才查詢歷程，每頁最多 10 筆並提供上一頁／下一頁；每筆顯示建立時間、最近改變、當時看法、接下來，以及編輯與刪除操作。
- 最新更新同時是右欄第一筆與歷次更新 Dialog 第一頁第一筆；兩處是同一筆資料，不是複製。
- 空狀態說明近況更新不是必填日誌，只有情勢或看法有變時再記錄。

### 9.6 RWD

桌面版：

- 使用等寬雙欄，不再採主內容加窄側欄。
- 左欄只呈現議題整體；右欄呈現最近推進與參考素材，階段下拉位於頁首操作列。
- 最新近況與接下來需在右欄首屏容易辨識。

行動版：

- 所有區塊改為單欄。
- 只縮小頁面與詳情大標題；正文、操作與 metadata 不再因根字級變動而忽大忽小。

### 9.7 全站文字層級

議事廳沿用 Echo Gallery 全站共用 typography，而不是在個別元件中自行決定字級：

| 角色 | 字級 | 主要用途 |
| --- | ---: | --- |
| 頁面標題 | 28px | 議事廳、全部卡片、卡片查詢 |
| 詳情標題 | 26px | 議題與卡片主標題 |
| 區塊標題 | 18px | 最近推進、整體研判、參考素材 |
| 卡片標題 | 17px | 議題列與 Card 標題 |

根字級固定為 16px；一般內容與 Element Plus 元件共用同一套系統字型。HTML heading 只代表文件結構，視覺大小由上述語意角色決定。11px 不再作為一般文字，以維持繁體中文可讀性。
- 等寬雙欄在窄螢幕回到正常上下文件流，不產生水平捲動。
- Update 操作按鈕需可觸控且不依賴 hover。
- 長文字不可造成水平捲動。
- 議題焦點極長時五行收合，整體研判約八行收合，背景與舊更新按需展開；最新近況保持完整可讀。

建議手動驗證寬度：375px、768px 與 1280px 以上。

## 十一、資料庫與相容性策略

### 11.1 Additive migration

本輪資料庫變更應採向後相容的新增方式：

```text
works 新增 nullable 欄位：
- objective
- current_assessment
- outcome_criteria

新增 work_progress_updates：
- id
- work_id
- change_summary
- assessment
- next_step
- created_at
- updated_at
```

舊 Work 資料：

- title、description、status、externalUrl 與 completedAt 原樣保留。
- 新欄位初始為 null。
- 前端不能因新欄位為 null 而阻止舊資料顯示或編輯。
- 議題更新是全新資料，不從既有 description 或 currentAssessment 自動產生。

### 11.2 正式環境

目前本機開發使用 Hibernate `ddl-auto: update`，正式環境使用 `ddl-auto: validate`。因此：

- 不可只修改 JPA entity 後直接部署。
- 必須先準備可重複檢查、可人工確認的 PostgreSQL migration SQL。
- migration 執行後，再部署使用新欄位的後端。
- 本輪不順便導入 Flyway，除非另開獨立任務並確認範圍。

### 11.3 不進行 destructive rename

本輪不執行：

- `works → issues/projects`。
- `work_cards → issue_cards/project_cards`。
- `/api/works → /api/issues`。
- `/works → /issues`。
- 刪除或搬移既有 Work 資料。

## 十四、實作後觀察計畫

議事原型可使用後，至少以兩個真實議題使用二至四週，記錄自然事件，不為驗證而刻意填滿所有欄位。

### 14.1 最低觀察樣本

- 至少建立兩個語意不同的議題。
- 每個議題至少連入兩張真實 Card。
- 累積至少六筆自然產生的議題更新。
- 至少三筆更新包含 nextStep。
- 至少一筆更新記錄先前行動帶來的結果或新情報。

### 14.2 需要回答的問題

1. 「議事廳／議題」是否比「培育計畫」更自然？
2. 議題焦點、背景、整體研判與結案條件是否能清楚區分？
3. 整體研判是否真的被當作綜合性說明，而不是與最新 update 重複？
4. 最新近況是否能在十秒內回答「最近如何、現在怎麼看、接下來做什麼」？
5. 不分類的 Update 是否比四類 Entry 更容易自然產生？
6. changeSummary、assessment、nextStep 哪些欄位最常使用，哪些經常留空？
7. 是否需要 `occurredAt`，還是 `createdAt` 已經足夠？
8. 最新 update 的 nextStep 是否足以推進行動，或真的需要獨立 NextAction？
9. 使用者是否自然記錄資源、限制、風險、不同解讀與退路？
10. WorkCard 的「素材池／已運用」在議題中是否仍自然？
11. 一個議題是否真的產生多個可獨立管理的 Work？
12. 是否出現任務管理需求，或只是被完整介面誘導出來？
13. 議題更新是否提升判斷與行動力，還是增加填寫負擔？

### 14.3 資源與風險欄位的升級門檻

只有符合多項條件，才考慮新增固定欄位：

- 多數真實議題都自然填寫資源或風險。
- 相同資訊反覆散落在整體研判與議題更新。
- 使用者需要比較前後兩次資源或風險評估。
- 缺少結構化欄位造成決議遺漏重要條件。
- 需要依風險、資源或限制進行搜尋與篩選。

若只是偶爾使用，繼續保留在整體研判或議題更新的自由文字中。

### 14.4 正式 domain migration 門檻

符合以下多項條件後，再規劃技術名稱遷移：

- 至少兩個議題累積真實 Card 與 Update。
- 議題語意在二至四週使用中保持自然。
- 「培育計畫」或 Work 命名持續造成理解或開發困難。
- 至少一個議題形成兩個以上明確成果。
- 需要獨立管理成果的狀態、素材或外部連結。
- 議題與真正 Work 的關聯語意能清楚區分。

正式遷移必須另立文件與任務，不在本輪追蹤表內直接執行。

## 十六、原型完成與去留定義

本輪需要區分「工程原型完成」與「產品功能通過驗證」。資料表與畫面建立完成，只代表具備真實使用的條件，不代表議事廳永久納入 MVP。

### 16.1 工程原型完成

需同時符合：

1. Card 的內容、議題整體資料與議題更新責任清楚分離。
2. 使用者可以暫停並恢復 Card 回流。
3. 取消封存能恢復封存前的回流狀態。
4. 現有 Work 資料可無損地以候選議題方式呈現。
5. 議題原型可以保存整體說明、聚合 Card 並形成時間性更新。
6. 每個任務具備相應自動測試與手動驗證紀錄。
7. 正式環境 schema 變更有受控 migration 與部署順序。
8. 已具備執行本文件第十四章觀察計畫的條件。

### 16.2 產品功能通過驗證

觀察期結束後才判斷是否符合：

1. 議題更新在非刻意測試下自然產生。
2. 更新確實協助使用者形成、回顧或修正判斷，並看見下一步。
3. 議題整體欄位與 Update 的維護成本沒有高於所得價值。
4. 議事廳提供的價值無法由 Card、Search、Tag 與現有 Work note 輕易取代。
5. 使用者仍希望從主要導覽主動進入此功能。

### 16.3 不通過時的回退方式

若驗證不支持完整議事廳，可依實際結果採取：

- 移除議事廳主導覽，保留既有 Work／培育計畫入口。
- 回退「議事廳／議題」候選文案，不動既有資料。
- 移除或隱藏沒有自然使用的議題欄位。
- 縮減議題更新欄位，只保留真實有用的問題。
- 保留歷史資料為唯讀，停止新增議題更新。
- 不進行正式 Work／Project／Issue domain migration。

如果議題更新沒有自然產生，本輪不繼續擴張為更完整的決策系統；如果三個更新欄位只有部分產生價值，後續只保留必要部分。
