# Echo Gallery 卡片花園培育方案與 MVP 觀察計畫

> 文件狀態：待驗證產品提案，不代表已排入開發或已成為 MVP 現行需求
> 記錄日期：2026-08-26
> 適用情境：目前唯一使用者針對現行 MVP 進行數週的真實使用觀察

## 一、文件目的

本文件保存 2026-08-25 至 2026-08-26 對卡片成長狀態、花園培育入口、卡片欄位語意與標籤功能的產品討論，並整理「方案六：混合式花園」的具體設計。

目前 Today 每批限制五張卡片與卡片綜合查詢才剛完成，這兩項功能可能改變唯一使用者對回流壓力、卡片找回方式與現有看板價值的判斷。因此本文件不主張立即開發方案六，而是先將它視為一組待驗證假設，透過現行 MVP 的實際使用，判斷其中哪些問題真實、重複且值得投入。

本文件同時提供一套具體的單人產品研究方法，避免「再用幾週看看」最後只留下模糊印象。

---

## 二、現行 MVP 基準與暫不改動原則

觀察開始時，應以以下現行行為作為基準：

1. Today 以一次五張卡片的有限批次進行回流。
2. 使用者可在需要時取得下一批，但不必清空全部到期卡片。
3. 卡片綜合查詢可依 ID、標題、標籤、成長狀態與封存狀態查詢，並提供排序。
4. `UNMARKED` 是一般卡片；`SEED` 是使用者主動留下的培育意圖。
5. 卡片成長狀態不自動影響回流排程。
6. Card 的成長狀態與 WorkCard 的候選／採用狀態彼此獨立。
7. 現有標籤管理保留完整的搜尋、多選、AND／OR、改名與刪除能力。

觀察期間遵循以下原則：

- 除非遇到阻斷使用、資料錯誤或安全問題，先不修改核心流程。
- 正常使用既有功能，不刻意把所有卡片都標成種子或成熟。
- 不為了證明方案六而製造不存在的需求。
- 當下先記錄事實與感受，週末再做解釋，避免邊使用邊修改結論。
- 每個觀察盡量附上日期、入口與 Card ID，使結論能回到具體事件。

## 三、目前形成的產品共識

### 3.1 成長狀態不是內容完整度

成長狀態描述的是外部 input 如何經過使用者，逐漸形成自己的理解並對現實產生影響。

| 狀態 | 核心問題 | 語意 |
|---|---|---|
| `UNMARKED` | 我有要特別培育它嗎？ | 一般卡片，沒有額外整理承諾。 |
| `SEED` 🌱 | 我還想回來處理它嗎？ | 主動想補充、重寫、釐清或驗證。 |
| `GROWING` 🌿 | 它是否已經成為我的東西？ | 已形成自己的理解、延伸、推論或新觀點。 |
| `MATURE` 🌳 | 它是否真的改變了什麼？ | 已促成至少一次可指認的行動、決定、實驗、對話或作品。 |

重要原則：

- 種子不是內容很少，而是存在培育意圖。
- 生長不是字數變多，而是發生認知轉化。
- 成熟不是內容寫完，而是理解已經越過卡片進入現實。
- 並非每張卡片都需要進入成長流程。
- 成熟不代表永遠完成，成熟卡片仍可繼續發展。
- 狀態可以逆向調整，不刪除既有內容或歷程。

### 3.2 現行導覽缺少的是下一步，而非更多列表

目前各入口實際上分屬不同層級：

| 類型 | 功能 |
|---|---|
| 核心活動 | Today、作品 |
| 找回方式 | 全部、查詢、熱門、隨機 |
| 管理工具 | 標籤管理 |
| 狀態或例外處理 | 封存、稍後再看 |

理想產品主線為：

```text
回流：再次遇見
  ↓
培育：形成自己的理解
  ↓
行動／作品：對外部世界產生影響
```

方案六中的花園負責第二段，但在現行 MVP 證據不足前，不預設一定需要新增入口。

### 3.3 現行欄位存在語意衝突

目前資料模型主要為 `reason`、`summary`、`content`，但建立頁、詳情頁與歷史規劃使用不同名稱與解釋。這會讓使用者依字數限制選擇欄位，而不是依內容意義選擇。

已知衝突包括：

- 收藏原因可能同時表示收藏動機與個人觀點。
- 摘要可能同時表示來源重點與客觀觀察。
- 「我思我長／金句」把外部摘錄與個人理解放在一起。
- `Plan／Review／Content` 同時容納計畫、行動結果、原文與長筆記。
- `reason` 300 字、`summary` 600 字、`content` 無明確上限，使容量成為最清楚的選擇依據。

方案六必須先解決內容模型，否則花園只會把使用者帶回語意模糊的文字框。

## 四、方案六：混合式花園

### 4.1 核心概念

每張卡片分成兩種資訊：

```text
穩定內容：描述這張卡現在是什麼、目前如何理解
＋
生長紀錄：保存它如何隨時間形成觀點、行動與結果
```

花園不是另一個成長狀態篩選看板，而是協助使用者每次推進一小步的培育空間。

### 4.2 穩定內容

#### 卡片身份與來源

| 欄位 | 顯示名稱 | 回答的問題 | 適合內容 |
|---|---|---|---|
| `title` | 標題 | 再次看到時，如何快速辨認？ | 可辨識的短標題。 |
| `url` | 來源連結 | 原始內容在哪裡？ | 外部網址。 |
| `sourceNote` | 來源重點 | 這張卡原本在說什麼？ | 摘錄、外部內容重點、背景或自建筆記的原始想法。 |
| `personalRelevance` | 與我的關係 | 為什麼它值得再次出現？ | 收藏動機、觸動、與自身經驗的關係。 |
| `tags` | 標籤 | 它屬於哪些主題？ | 主題分類。 |
| `intervalDays` | 回流頻率 | 多久希望再次遇見？ | 回流間隔。 |

`sourceNote` 與 `personalRelevance` 的差異範例：

```text
來源重點：選項過多會提高比較成本並造成決策疲勞。
與我的關係：我設計功能時常忍不住加入更多設定，這提醒了我。
```

#### 目前穩定理解

| 欄位 | 顯示名稱 | 回答的問題 | 適合內容 |
|---|---|---|---|
| `currentInsight` | 我目前的理解 | 經過消化後，我現在怎麼看？ | 個人觀點、推論、連結、認同、反對或目前結論。 |
| `cultivationIntent` | 想繼續發展 | 下次回來時，我想處理什麼？ | 開放問題、待補充處、想驗證或重寫的方向。 |
| `growthStatus` | 成長狀態 | 這個想法發展到哪裡？ | 未標記、種子、生長、成熟。 |
| `growthStatusChangedAt` | 狀態更新時間 | 何時進入目前階段？ | 系統時間。 |
| `lastCultivatedAt` | 最近培育時間 | 最近何時有實質發展？ | 系統時間。 |

`currentInsight` 是目前版本的理解；使用者不需要從時間軸中尋找最新結論。

`cultivationIntent` 是目前仍未解決的方向，例如：

> 想比較「減少選項」與「改善選項命名」哪一個更能降低選擇疲勞。

### 4.3 生長紀錄

每次發展可新增一筆帶日期的紀錄，不覆蓋過去內容。

| 類型 | 顯示名稱 | 回答的問題 |
|---|---|---|
| `INSIGHT` | 新理解 | 這次形成或修正了什麼觀點？ |
| `PLAN` | 下一步 | 接下來想嘗試、驗證或產出什麼？ |
| `ACTION` | 已採取行動 | 實際做了什麼？ |
| `REVIEW` | 行動回顧 | 結果如何，理解需要如何調整？ |

概念資料結構：

```text
CardGrowthEntry
- id
- cardId
- type: INSIGHT / PLAN / ACTION / REVIEW
- body
- occurredAt
- createdAt
- updatedAt
```

生長紀錄不直接關聯 Work。Card 與 Work 的關係仍只由 WorkCard 表達，避免讓一般生活行動與作品型行動在資料模型中產生不必要的耦合。如果某筆 ACTION 與作品有關，第一版可由使用者在內容中描述，不另外保存 Work 外鍵。

`occurredAt` 是事情實際發生時間；`createdAt` 是何時記入 Echo Gallery。

新增 `INSIGHT` 時，可提供「同時更新目前理解」選項。直接編輯 `currentInsight` 不必自動產生歷史紀錄，避免修正錯字也形成一筆生長事件。

### 4.4 成長狀態規則

#### 標記種子

詢問：

> 下次回來時，你想繼續處理什麼？

可立即填寫 `cultivationIntent`，也可以略過。略過的種子在花園中優先提示補充方向，但不顯示警告或欠債訊息。

#### 標記生長

當使用者更新 `currentInsight` 或新增 `INSIGHT` 後，系統可以建議：

> 這張卡已經開始形成你的觀點，要標記為生長嗎？

系統不自動切換。

#### 標記成熟

新的成熟操作原則上應具有一項行動依據：

- 新增一筆 `ACTION`。
- 選擇既有 `ACTION`。
- 選擇一個已採用此卡片的 Work，並由使用者確認它確實構成影響。

WorkCard 變成 `USED` 不自動使卡片成熟。

既有成熟卡片不因缺少新資料而降級，可顯示「尚未補記成熟依據」。

#### 逆向調整

- 種子可以回到未標記。
- 生長可以回到種子。
- 成熟可以回到生長。
- 狀態調整不刪除生長紀錄。

### 4.5 花園資訊架構

理想結構：

```text
花園
├── 今日培育
├── 成長階段
├── 主題花圃
└── 最近生長
```

第一版若進入開發，只需考慮「今日培育」與「成長階段」。主題花圃與最近生長必須有額外使用證據才加入。

### 4.6 今日培育

核心文案：

> 今天想照顧一個想法嗎？

一次最多提供三張未封存的 `SEED` 或 `GROWING` 卡片，不顯示總欠債數。

候選優先順序可為：

1. 尚未填寫培育方向的種子。
2. 從未培育過的種子。
3. `lastCultivatedAt` 最久以前的卡片。
4. 以 Card ID 保證穩定排序。

使用者可以：

- 開始培育。
- 換一張。
- 今天先不要。
- 移回未標記。
- 調整回流頻率。
- 封存。

花園曝光與培育不更新 Today 的 `nextShowAt` 或 `lastOfferedAt`。

### 4.7 單卡培育流程

培育時先呈現卡片的來源重點、與我的關係、目前理解與培育方向，再只提出一個問題。

種子階段可問：

- 你真正想釐清的是什麼？
- 你同意或不同意哪一部分？
- 它和你的哪段經驗有關？
- 如果只保留一句自己的話，會是什麼？

生長階段可問：

- 目前理解可以如何用一句話表達？
- 有什麼反例可能推翻它？
- 下一個最小驗證方式是什麼？
- 它適合加入哪一件作品？

成熟階段可問：

- 這個觀點最近又影響了什麼？
- 行動結果符合原先理解嗎？
- 哪一部分需要修正？
- 這次結果是否長出了新的種子？

「還沒有想法」是一個合法出口，不代表培育失敗。

### 4.8 卡片詳情頁

詳情頁分成穩定內容與生長紀錄：

```text
卡片標題                                      🌿 生長

來源重點
這張卡原本在說什麼……

與我的關係
為什麼值得再次遇見……

我目前的理解
現在我怎麼看這件事……

想繼續發展
下一次還想處理什麼……

──────────────────────────────────────────

生長紀錄

9/15 ACTION
實際重新安排側邊欄主要入口……

9/02 PLAN
先觀察自己最常使用哪些看板……

[新增生長紀錄]
```

欄位以問題與範例區分，不以字數區分。字數計數僅在接近限制時出現。

### 4.9 快速建立卡片

預設只顯示：

- 卡片類型。
- 標題。
- 來源網址。
- 標籤。
- 回流頻率。

可選補充：

- 來源重點。
- 與我的關係。

不在快速建立時要求目前理解、培育方向或生長紀錄。建立後可選「建立卡片」或「建立並標記種子」。

### 4.10 與 Today 的關係

從 Today 開啟詳情後，可以詢問：

> 這次遇見它之後，你想怎麼處理？

主要選項：

- 完成本次回顧。
- 標記為種子。
- 補充目前理解。
- 加入作品。

次要選項：

- 稍後再看。
- 調整回流頻率。
- 封存。

只有 Today 完成回顧才推進回流排程。培育、查詢或狀態切換不算完成 Today 回顧。

### 4.11 與 Works 的關係

- Card 成長狀態描述想法本身。
- WorkCard 狀態描述卡片是否被特定作品採用。
- 從花園加入作品時先建立 `CANDIDATE`，不自動建立行動紀錄。
- WorkCard 變成 `USED` 時，可詢問是否另外建立一筆 `ACTION`，但兩筆資料不建立直接關聯。
- 使用者確認 ACTION 後，才進一步詢問是否標記成熟。

### 4.12 主題花圃與標籤管理

現有標籤管理完整保留。兩者用途不同：

| 入口 | 目的 |
|---|---|
| 主題花圃 | 從某個主題探索與培育卡片。 |
| 卡片查詢 | 依標籤精準找回卡片。 |
| 標籤管理 | 改名、刪除、整理分類及檢查關聯。 |

主題花圃只提供唯讀摘要與培育入口：

```text
產品設計
全部卡片 18
🌱 4　🌿 5　🌳 3

[培育這個主題] [查看全部卡片] [管理此標籤]
```

「管理此標籤」跳到現有標籤管理並預先選取該標籤；標籤管理則可提供「在花園中查看」。

### 4.13 概念資料遷移

| 舊欄位 | 新位置 | 原則 |
|---|---|---|
| `summary` | `sourceNote` | 語意最接近，可初步搬移。 |
| `reason` | `personalRelevance` | 保留既有收藏原因。 |
| `content` | `legacyContent` | 不自動拆分，避免錯誤分類。 |
| `growthStatus` | 保留 | 不改變既有狀態。 |

舊 `content` 顯示為「原有內容」，讓使用者日後選擇移至來源重點、目前理解、生長紀錄或保留原樣。

正式實作時不可只依賴 Hibernate `ddl-auto: update` 搬動既有資料，需建立可追蹤且可驗證的資料遷移流程。

### 4.14 概念後端能力

若未來進入開發，預期需要：

```text
GET    /api/cards/{cardId}/growth-entries
POST   /api/cards/{cardId}/growth-entries
PUT    /api/cards/{cardId}/growth-entries/{entryId}
DELETE /api/cards/{cardId}/growth-entries/{entryId}

GET /api/garden/candidates
GET /api/garden/topics
```

所有查詢與修改都必須依登入使用者隔離。花園主題摘要應由後端一次聚合，避免前端對每個標籤逐一查詢。

## 五、方案六需求探查：七個可獨立驗證的假設

方案六不是單一功能。觀察時必須拆成七個假設，最後可以只採用其中一部分。

### H1：現有固定欄位確實無法承載清楚語意

#### 假設

使用者在新增或編輯內容時，經常無法依意義判斷應填入 `reason`、`summary` 或 `content`，因此需要新的固定欄位。

#### 需要觀察的事件

- 一段文字同時想放進兩個欄位。
- 因 300／600 字限制而換欄位。
- 把內容放進 `content`，只是因為不知道應該放哪裡。
- 回頭看卡片時，無法分辨哪段是來源、哪段是自己的理解。
- 同一類內容在不同卡片被放入不同欄位。

#### 支持方案六的證據

- 在至少 10 次真實新增或編輯中，有 3 次以上出現語意猶豫。
- 相同困惑跨越至少 3 張不同卡片。
- 使用者自行建立標題符號、段落模板或外部筆記作為補救。

#### 反證

- 經過一段自然使用後，三個欄位已形成穩定個人規則。
- 大部分內容可以在十秒內依意義決定欄位。
- 困惑只發生於少數極長的文檔型卡片。

#### 可能結論

- H1 成立不代表需要完整花園；可能只需要重新定義固定欄位。

### H2：種子需要獨立的培育方向

#### 假設

只標記 `SEED` 不足以保存「為什麼想繼續發展」，過一段時間後會忘記當初意圖，因此需要 `cultivationIntent`。

#### 需要觀察的事件

- 標記種子當下，腦中有清楚的待處理問題。
- 幾天後看到種子，卻想不起當初想補什麼。
- 為了記住培育方向，把一句話塞入 `content`、標題或其他欄位。
- 因為不知道如何記錄培育意圖，最後沒有標記種子。

#### 實際探查任務

每次標記種子時，在研究紀錄中另外寫一句：

> 我希望下次處理的是＿＿＿＿。

一週後先只看卡片本身，不看研究紀錄，回答：

> 我是否仍知道當初想發展什麼？

之後再對照原始紀錄。

#### 支持方案六的證據

- 至少 5 顆真實種子中，有 2 顆以上在一週後無法回想培育方向。
- 多次需要用現有欄位或外部工具保存這句話。

#### 反證

- 卡片現有內容已足以喚起培育方向。
- 種子本身只是一個「日後再看」記號，不需要具體方向。

### H3：使用者需要「目前理解」而不是只有零散補充

#### 假設

回流時，使用者需要快速看到目前最能代表自己的觀點，而不是重新閱讀來源與歷次筆記，因此需要 `currentInsight`。

#### 需要觀察的事件

- 重新看到卡片時，第一個問題是「我現在到底怎麼看？」
- 既有 reason 或 content 混合舊想法，無法代表目前結論。
- 想重寫目前理解，但又不想刪除過去內容。
- 為了快速回想，反覆修改標題或把結論放在最前面。

#### 實際探查任務

挑選至少 5 張曾經修改過的卡片，不先編輯，限時 30 秒回答：

1. 來源主要在說什麼？
2. 它為什麼對我重要？
3. 我目前怎麼理解？
4. 下一步還想處理什麼？

記錄哪一題最難從現有卡片直接回答。

#### 支持方案六的證據

- 至少 3 張卡片無法在 30 秒內辨認目前理解。
- 使用者希望保留舊內容，同時建立一個最新版本摘要。

#### 反證

- 現有收藏原因或摘要已自然成為目前理解。
- 使用者通常不需要整理出單一當前觀點。

### H4：生長過程需要歷次紀錄，而非只保留最新內容

#### 假設

同一張卡片會跨時間形成多個觀點、計畫、行動或反省；覆蓋單一文字欄會造成資訊損失，因此需要生長日誌。

#### 需要觀察的事件

- 想新增一段帶日期的補充，不想改掉舊內容。
- 想知道某個觀點是在行動前還是行動後形成。
- `content` 開始出現人工日期、分隔線或日誌格式。
- 一張卡影響多次行動，需要留下多筆結果。
- 為了保存歷程，改用其他筆記工具。

#### 實際探查任務

選擇 3 張確實會持續發展的卡片，在三週中自然更新。每次更新前詢問：

> 我現在想覆蓋舊內容，還是追加一筆新的時間性紀錄？

記錄選擇與原因，不必為了測試而刻意追加。

#### 支持方案六的證據

- 至少發生 3 次「想追加而非覆蓋」的真實需求。
- 需求同時包含至少兩種紀錄，例如 Insight 與 Action。
- 現有大文字欄已出現人工時間軸 workaround。

#### 反證

- 使用者只關心目前版本，不在意如何形成。
- 所有歷程都可由 Work 或外部文件承接。
- 日誌紀錄被認為增加負擔，沒有回看價值。

### H5：種子與生長卡片需要專門的花園入口

#### 假設

即使查詢能精準找回成長狀態，使用者仍需要一個以培育意圖為中心、一次只提供少量卡片的入口。

#### 需要觀察的事件

- 想培育卡片，但沒有特定 Card ID、標題或標籤。
- 知道有種子，卻沒有動機打開查詢並設定條件。
- 查詢結果正確，但列表過大，不知道先處理哪張。
- 進入查詢只是為了挑一顆種子，而不是精準找某張卡。
- 使用者期待系統替自己提出一個合適的培育起點。

#### 實際探查任務

每週至少安排兩次「我現在有 10 分鐘，可以發展一個想法」的真實情境，嘗試只使用現有 MVP：

1. 從哪個入口開始？
2. 是否知道要輸入什麼查詢條件？
3. 找到第一張想培育的卡花了多久？
4. 查詢結果是否造成選擇壓力？
5. 最後是否真的修改卡片或產生行動？

這不是要求一定完成培育，而是驗證現有查詢是否已足夠承接需求。

#### 支持方案六的證據

- 至少 5 次有培育意圖的情境中，有 2 次以上因不知道從哪張開始而放棄。
- 使用者反覆使用相同的「成長狀態＋最久未更新」查詢組合。
- 查詢能找回資料，卻無法提供下一個思考問題。

#### 反證

- 現有查詢可以快速選出想處理的卡片。
- 種子數量很少，沒有獨立入口的必要。
- 使用者只在特定主題或作品情境下培育，不需要系統推薦。

### H6：成熟狀態需要可指認的行動依據

#### 假設

如果只靠主觀切換 `MATURE`，使用者日後無法理解卡片為何成熟，因此需要 ACTION 或 Work 證據。

#### 需要觀察的事件

- 想標記成熟時，無法說出具體影響。
- 已經採取行動，卻不知道應記在哪個欄位。
- 卡片被 Work 採用，但不確定是否等於成熟。
- 之後看到成熟卡片，無法回想它實際改變了什麼。

#### 實際探查任務

每次想標記成熟時，先在研究紀錄回答：

```text
這張卡促成了什麼？
何時發生？
是否與某個 Work 有關？
我需要保存結果或反省嗎？
```

兩週後重新看成熟卡片，只靠卡片現有內容，確認能否找回答案。

#### 支持方案六的證據

- 至少 3 次成熟判斷中，有 2 次希望記錄具體行動或結果。
- 成熟的理由無法從現有欄位辨認。
- 非作品型行動無處記錄。

#### 反證

- 成熟只是個人當下判斷，日後不需要追溯。
- WorkCard 已足以記錄所有重要外部影響。
- 寫下成熟依據被認為是不必要的額外負擔。

### H7：使用者會從主題出發進行培育

#### 假設

使用者不只會找單一卡片，也會想從某個標籤主題觀察與培育一組想法，因此需要主題花圃。

#### 需要觀察的事件

- 使用者的起點是「我今天想整理產品設計」，而不是某張卡。
- 查看標籤結果時，想知道各成長階段分布。
- 想從某個主題挑一張種子，而不想管理標籤。
- 使用現有標籤管理做內容探索時，覺得管理操作干擾思考。

#### 實際探查任務

每週至少進行一次主題式探索：

1. 先選一個當週真正關心的標籤。
2. 使用現有標籤管理或查詢查看相關卡片。
3. 記錄是否想知道成長狀態分布。
4. 記錄是否找到值得培育或加入作品的卡片。
5. 記錄現有標籤頁是否已經足夠。

#### 支持方案六的證據

- 至少 3 次真實使用從主題而非特定卡片開始。
- 使用者反覆想看同一主題的種子、生長或最近活動。
- 現有標籤管理雖功能完整，但不適合作為培育介面。

#### 反證

- 標籤只被用於精準查詢與資料維護。
- 培育通常由 Today、特定卡片或 Work 觸發。
- 主題花圃只是在看到設計稿後覺得有趣，實際沒有使用情境。

## 六、三至四週的具體觀察安排

觀察以「事件數量」為主要完成條件，週數只是節奏。若某週沒有足夠真實事件，應延長觀察，而不是補寫假想紀錄。

### 第零階段：建立基準

開始前完成一次 30 分鐘盤點：

1. 記錄目前 `UNMARKED / SEED / GROWING / MATURE` 大致數量。
2. 隨機挑 10 張卡片，判斷現有欄位內容各自實際扮演什麼角色。
3. 記錄目前最常進入的三個看板。
4. 記錄目前如何找回特定卡片。
5. 記錄目前是否使用外部工具保存卡片延伸想法或行動結果。

基準盤點只描述現況，不整理舊資料。

### 第一週：驗證 Today 五張批次與欄位語意

#### 必做情境

- 至少使用 Today 4 次，接觸約 20 張卡片。
- 至少開啟 8 張卡片詳情。
- 至少進行 3 次真實內容新增或更新。

#### 每張 Today 卡片快速分類

開啟或看完後，以代碼記錄最符合的反應：

| 代碼 | 反應 |
|---|---|
| `R` | 回流本身已足夠，不需修改。 |
| `E` | 想修改或補充現有內容。 |
| `I` | 形成新的理解或觀點。 |
| `D` | 想進一步發展，但現在不處理。 |
| `A` | 想採取或已採取行動。 |
| `W` | 想加入作品。 |
| `S` | 想稍後再看。 |
| `X` | 不再需要，想封存或降低頻率。 |

同一張可以有兩個代碼，例如 `I+A`。

#### 本週要回答

- 五張是否真的降低回流壓力？
- 看完五張後，是否自然想再取下一批？
- 哪些反應目前沒有清楚出口？
- 新想法發生時，是否知道要放進哪個欄位？
- Today 的價值主要是重新看見，還是會自然引發培育？

主要驗證 H1，並蒐集 H2、H3、H6 的自然事件。

### 第二週：驗證查詢、種子找回與培育起點

#### 五項查詢任務

必須使用真實需求，不以測試資料代替：

1. 用標題或 ID 找一張已知卡片。
2. 用一個標籤找某個主題的卡片。
3. 找出目前所有種子。
4. 找出一張很久以前建立或更新的卡片。
5. 組合標籤與成長狀態找卡片。

每次記錄：

- 是否一次成功。
- 花費多久。
- 是否理解查詢條件。
- 結果是否太多或太少。
- 找到後實際做了什麼。

#### 兩次培育起點任務

在確實有約 10 分鐘空檔時告訴自己：

> 我現在想發展一個過去留下的想法，但沒有指定卡片。

只使用現行功能，觀察從哪裡開始、如何挑卡、是否完成任何實質更新。

#### 種子延遲回想

- 本週至少新增或確認 3 至 5 顆真實種子。
- 在研究紀錄中寫下當下培育方向。
- 一週後只看卡片，檢查能否回想。

主要驗證 H2、H5，並觀察查詢是否已足以取代花園入口。

### 第三週：驗證理解、行動與作品連接

#### 目前理解任務

挑選 5 張曾修改過或反覆回流的卡片，每張限時 30 秒回答：

1. 來源在說什麼？
2. 為什麼對我重要？
3. 我目前怎麼理解？
4. 還想發展什麼？

記錄現有卡片是否足以直接回答，以及答案目前分散在哪些欄位。

#### 行動追蹤任務

當一張卡實際影響工作、生活、決定、對話或作品時，記錄：

- Card ID。
- 具體行動。
- 發生日期。
- 是否有結果或反省。
- 現行產品中最自然的記錄位置。
- 是否需要與 Work 關聯。

至少觀察 2 至 3 個自然事件；若沒有發生，也是一項重要反證，不需刻意製造行動。

#### 作品任務

至少進行一次：

- 從卡片加入作品，或
- 從作品尋找候選卡片，或
- 將候選卡片標記為採用。

記錄 WorkCard 是否已足以說明卡片的外部影響，及是否仍希望在卡片本身留下行動／結果。

主要驗證 H3、H4、H6。

### 第四週：驗證時間歷程與主題視角，可選

如果前三週已累積足夠事件，第四週用於回看，而不是產生更多紀錄。

#### 歷程回看

- 回到三週內曾修改兩次以上的卡片。
- 判斷是否需要知道每次修改的時間與舊內容。
- 判斷只保留目前理解是否已足夠。

#### 主題探索

- 選擇 2 至 3 個當下真正關心的標籤。
- 使用現有標籤管理與查詢探索相關卡片。
- 觀察是否自然想看成長分布、最近生長或從該主題挑一張培育。

主要驗證 H4、H7。

## 九、判斷證據的共同標準

### 強證據

- 相同摩擦在不同日期、不同卡片重複三次以上。
- 一次事件直接阻止高價值成果，且現有功能沒有合理替代方案。
- 使用者已自發建立 workaround，例如日期模板、外部筆記或固定查詢組合。
- 即使沒有想到方案六，仍會自然描述出相同需求。

### 中等證據

- 問題發生兩次，且跨不同卡片或入口。
- 現有 workaround 可用但明顯增加時間或認知成本。
- 使用者多次採取相同路徑，顯示可被產品化。

### 弱證據

- 只發生一次且沒有造成明顯影響。
- 只有看到設計方案時覺得有趣。
- 只有在刻意測試任務中發生，日常從未自然出現。
- 無法指出具體卡片、行為或期待結果。

### 反證同樣重要

- 現有查詢已快速解決找回需求。
- 大部分 Today 卡片只需再次遇見，不需培育。
- 使用者不想保留歷次想法，只關心目前版本。
- 作品已足以承接所有外部行動。
- 標籤主要用於管理與查詢，沒有主題式培育情境。

## 十、方案六分項決策門檻

觀察結束後，不做「整套方案六要或不要」的二元選擇。

| 子方案 | 優先採用條件 | 延後條件 |
|---|---|---|
| 新固定欄位 | H1 或 H3 有強證據。 | 現有欄位已形成穩定語意。 |
| `cultivationIntent` | H2 有中等以上證據。 | 種子內容本身足以喚起意圖。 |
| 生長日誌 | H4 有強證據，且確實會回看歷程。 | 只需要目前理解，不需要時間軸。 |
| 花園入口 | H5 有強證據，查詢無法承接無指定卡片的培育。 | 查詢可快速選出卡片，或培育需求很少。 |
| 今日培育少量批次 | 花園入口成立，且完整種子列表造成選擇壓力。 | 種子數量少，不需要系統挑選。 |
| 成熟行動依據 | H6 有中等以上證據。 | 成熟只需主觀標記，無追溯價值。 |
| 主題花圃 | H7 有強證據。 | 標籤只用於查詢與管理。 |
| Work 行動提示 | 多次從 USED 自然產生另外記錄 ACTION 的需求。 | WorkCard 已足以表達採用。 |

### 可能的部分採用結果

#### 結果 A：只改欄位

若 H1、H3 成立，但 H4、H5 不成立：

- 新增來源重點、與我的關係、目前理解、培育方向。
- 不建立花園與生長日誌。
- 使用查詢找回種子。

#### 結果 B：欄位加輕量花園

若 H1、H2、H5 成立，但 H4 不成立：

- 建立固定欄位。
- 花園只提供少量種子／生長卡片。
- 不建立時間軸，所有內容只保留目前版本。

#### 結果 C：欄位加生長日誌，不做花園

若 H1、H3、H4 成立，但 H5 不成立：

- 卡片詳情支援歷次 Insight、Action、Review。
- 仍由 Today、查詢與 Work 觸發編輯。
- 不新增主要導覽入口。

#### 結果 D：完整混合式花園

若 H1 至 H6 多數有中等以上證據：

- 建立穩定內容、生長紀錄、花園入口與成熟依據。
- H7 另行決定是否加入主題花圃。

---

## 十一、觀察結束後的決策會議

完成最低事件數後，依序回答：

1. 現行 Today 五張批次是否已解決回流壓力？
2. 查詢是否已解決「找回想整理卡片」的問題？
3. 真實使用中有多少卡片需要培育，而不只是再次回流？
4. 欄位混淆是文案問題、資料模型問題，還是少數長文卡片問題？
5. 是否真的需要保留時間歷程？
6. 成熟行動是否值得被記錄與回看？
7. 花園提供的獨特價值是否無法由 Today、查詢與 Works 組合完成？
8. 哪一個最小子方案可以解決最多已觀察問題？

每項候選功能使用下表評估：

| 評估面向 | 問題 |
|---|---|
| 發生頻率 | 相同需求實際出現幾次？ |
| 問題強度 | 是輕微不便，還是導致放棄？ |
| 現有替代 | Today、查詢、標籤或 Works 能否合理解決？ |
| 產品契合 | 是否強化回流、理解與行動主線？ |
| 使用成本 | 是否增加填寫壓力或待辦感？ |
| 開發成本 | 是否需要資料遷移、新 entity 或新流程？ |
| 可逆性 | 若假設錯誤，是否容易撤回？ |

只有同時具有真實事件、現有替代不足與產品定位契合的功能，才進入實作規劃。

## 十二、若方案六通過驗證的建議交付順序

1. 使用真實卡片確認固定欄位語意。
2. 建立新資料欄位與保守資料遷移。
3. 重做快速建立與卡片詳情的內容結構。
4. 視 H4 結果決定是否加入生長紀錄。
5. 視 H6 結果加入成熟行動依據。
6. 視 H5 結果建立最小花園：今日培育與成長階段。
7. 串接 Today 與 Works 的培育出口。
8. 視 H7 結果加入主題花圃。
9. 最後才評估舊欄位移除與標籤管理增強。

第一版明確不做：

- AI 自動產生問題或內容。
- 卡片雙向連結與知識圖譜。
- 自動調整成長狀態。
- 生長分數、成熟率與欠債提醒。
- 複雜日誌搜尋。
- 自動合併標籤。

## 十三、最終產品閉環假設

方案六希望形成的閉環是：

```text
Today 再次遇見
        ↓
標記值得發展的種子
        ↓
Garden 形成目前理解
        ↓
記錄計畫與實際行動
        ↓
Work 或生活中產生影響
        ↓
回到卡片記錄結果
        ↓
未來再次回流
```

觀察期真正要驗證的不是這條流程看起來是否完整，而是唯一使用者是否會在沒有這套設計時，自然反覆嘗試完成其中缺少的環節。

如果缺口沒有自然出現，方案六就應延後；如果只有部分缺口反覆出現，就只實作對應的最小子方案。
