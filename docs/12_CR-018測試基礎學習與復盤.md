# CR-018 測試基礎學習與復盤

## 文件定位

本文件以第一次建立自動化測試基礎的開發者為主要讀者，說明 CR-018 的目的、設計選擇、三個實作 Commit、各手寫檔案的改動意義、驗證方式與後續擴充方向。

這是一份學習與復盤文件，不是新的待辦清單。CR-018 的正式狀態仍以 `11_全專案CodeReview追蹤.md` 為準；未來程式碼若已改變，應先閱讀現況，不可直接照抄本文範例。

## 一、CR-018 到底要解決什麼

CR-018 原本的問題是「專案看似有測試結構，實際上缺乏可穩定執行、能保護重要行為的測試」。它包含兩個層次：

1. 後端原本只有 `contextLoads()`，而且啟動 Spring Context 時需要資料庫；若測試依賴開發者本機的 PostgreSQL、`.env` 或既有資料，換一台電腦就可能失敗。
2. 前端沒有測試框架與測試指令，修改狀態邏輯後只能依賴人工操作，無法快速知道舊功能是否被破壞。

### 只有 `contextLoads()` 為什麼不夠

`contextLoads()` 能確認 Spring Bean 大致可以組裝，但不會主動證明以下行為正確：

- 沒有 JWT 時是否真的回傳 401。
- 過期或格式錯誤的 JWT 是否會被拒絕。
- A 使用者能否讀取、修改或刪除 B 使用者的 Card／Tag。
- 前端登入後是否正確保存狀態。
- 後端登出失敗時，前端是否仍清除本機認證資訊。

換句話說，程式「可以啟動」不等於重要規則「有被驗證」。

### 「穩定執行」代表什麼

本次將它定義為：

- 測試資料庫由測試自行建立與銷毀，不使用開發資料庫。
- 測試不讀取 `.env` 才能成立。
- 每個測試從可預期的資料狀態開始。
- 前端相依套件可以由 lockfile 在乾淨 clone 重新安裝。
- 同一組指令在原工作目錄及全新 clone 都能通過。

### 為什麼 CR-018 優先處理

後續 CR 會修改驗證規則、錯誤格式、API contract 與型別。如果沒有測試保護，每次修改都只能靠人工記憶確認，容易修好一項又破壞另一項。CR-018 的價值不是一次把覆蓋率提高到很高，而是先建立可持續補測試的跑道。

## 二、整體設計

```text
Gradle/JUnit
    └─ IntegrationTestBase
         ├─ 啟用 test profile
         ├─ 啟動臨時 PostgreSQL 容器
         └─ 將容器連線資訊交給 Spring
              ├─ contextLoads
              └─ JWT／多租戶 MockMvc 整合測試

npm/Vitest
    ├─ jsdom 模擬瀏覽器環境
    ├─ Pinia authStore 測試
    ├─ board 純邏輯測試
    └─ V8 產生覆蓋率報告
```

後端選擇整合測試，是因為 JWT、多租戶授權、Controller、Spring Security、Service 與 JPA 必須串在一起才有意義。前端先從純邏輯與 Store 開始，成本較低，也能建立第一批快速回歸測試。

```java

    registry.add("spring.datasource.url", POSTGRES::getJdbcUrl);
    registry.add("spring.datasource.username", POSTGRES::getUsername);
```

- `POSTGRES::get...` 是方法參照；Spring 需要值時才向已啟動容器取得實際連線資料。

## 四、Commit `483ca28`：補上 JWT 與多租戶授權整合測試

### 為什麼使用 MockMvc

`SecurityAndOwnershipIntegrationTests` 使用 `MockMvc` 模擬 HTTP 請求。它不需要真的開啟網路 Port，但仍會經過 Controller、Spring Security Filter、JWT 驗證、Service、Repository 與 PostgreSQL，因此能測到完整後端行為。

### 類別與依賴

```java
@AutoConfigureMockMvc
class SecurityAndOwnershipIntegrationTests extends IntegrationTestBase {
```

- `@AutoConfigureMockMvc` 建立可注入的 `MockMvc`。
- 繼承測試基底，取得完整 Context 與臨時 PostgreSQL。

```java
@Autowired private MockMvc mockMvc;
@Autowired private ObjectMapper objectMapper;
@Autowired private CardRepository cardRepository;
@Autowired private TagRepository tagRepository;
@Autowired private UserRepository userRepository;
@Value("${jwt.secret}") private String jwtSecret;
```

- `MockMvc`：發送模擬 HTTP 請求與驗證 status。
- `ObjectMapper`：把 Java 測試資料轉成 JSON，並解析 API response。
- 三個 Repository：只用於每個測試前清空資料；實際測試操作仍走 HTTP API。
- `jwtSecret`：取得 test profile 的密鑰，用來刻意製造一個已過期但簽章正確的 Token。

### 每個測試前清理資料

```java
@BeforeEach
void cleanDatabase() {
    cardRepository.deleteAll();
    tagRepository.deleteAll();
    userRepository.deleteAll();
}
```

- `@BeforeEach`：每個測試方法開始前執行。
- 刪除順序先 Card、再 Tag、最後 User，避免外鍵關聯造成刪除失敗。
- 每個測試不受前一個測試留下的帳號或資料影響。

### 六個安全測試

1. `protectedEndpointWithoutTokenReturnsUnauthorized`
   - Arrange：不建立 Token。
   - Act：呼叫受保護的 `/api/sidebar/stats`。
   - Assert：必須回傳 401。
   - 保護風險：Security 設定被誤改成允許匿名存取。

2. `malformedTokenReturnsUnauthorized`
   - 帶入 `Bearer not-a-valid-jwt`。
   - 驗證無法解析的字串不會被接受，也不應變成 500。

3. `expiredTokenReturnsUnauthorized`
   - 先透過正式註冊 API 建立使用者。
   - 使用測試密鑰建立簽章正確、但到期時間在過去的 JWT。
   - `issuedAt` 設為目前時間前 120 秒，`expiration` 設為前 60 秒，確保 Token 已過期。
   - 驗證後端不只檢查簽章，也檢查有效期限。

4. `validTokenCanAccessProtectedEndpoint`
   - 透過註冊 API 取得後端真正簽發的 Token。
   - 驗證有效 Token 可取得 200，避免安全設定過度阻擋合法使用者。

5. `userCannotReadUpdateOrDeleteAnotherUsersCard`
   - 建立擁有者與另一位使用者。
   - 擁有者建立 Card，另一位使用者嘗試 GET、PUT、DELETE。
   - 三個操作都必須回傳 403。
   - 同時保護 Card 的讀取、修改與刪除租戶邊界。

6. `userCannotUpdateOrDeleteAnotherUsersTag`
   - 擁有者透過建立 Card 產生 Tag，再取得 Tag ID。
   - 另一位使用者嘗試 PUT 與 DELETE。
   - 兩個操作都必須回傳 403。

- 統一建立註冊 JSON、呼叫 `/api/auth/register`、確認 200 並取出 Token。
- 使用實際 API 而非直接寫入 UserRepository，讓註冊與 Token 簽發流程一起受測。

```java

```

- 使用 Bearer Token 呼叫真正的 Card 建立 API。
- 解析 response 中的 `id`，供跨使用者測試使用。

```java
private long firstTagId(String token)
```

- 以擁有者 Token 取得 Tag 清單。
- 讀取第一個 Tag ID，避免測試直接依賴資料庫內部 ID 產生策略。

```java
private String cardRequestJson(...)
```

- 集中建立符合目前 API contract 的 Card JSON。
- 未來 Card request 改變時，只需集中調整這個 helper。

```java

    return "Bearer " + token;
}
```

- 集中 Authorization header 的格式，避免各測試重複字串拼接。

```java

```

- Java `record` 適合只承載測試輸入資料，不需要 setter 或額外行為。
- 欄位名稱會成為 JSON property，對應目前 API request。

### 為什麼 `package-lock.json` 變更多

`package-lock.json` 是 npm 根據 `package.json` 自動產生的完整依賴樹。新增四個直接依賴後，也會加入它們使用的數百個間接依賴，因此可能出現上千行差異。

重要欄位概念：

- `lockfileVersion`：lockfile 格式版本。
- `packages`：根專案與每個已解析套件的資訊。
- `version`：實際鎖定版本，不只是 `package.json` 的版本範圍。
- `resolved`：套件下載來源。
- `integrity`：內容雜湊，避免下載內容被無聲替換。
- `dependencies`／`peerDependencies`：套件彼此的依賴關係。
- `dev`：標示只用於開發／測試的依賴。

必須提交 lockfile，因為 `npm ci` 會依它安裝相同依賴組合。它不適合人工逐行維護；需要改版時應修改 `package.json` 並由 npm 重新產生。

- Assert：Store 回到訪客，`localStorage` 的 Token 與 username 被移除。
- 意義：即使後端或網路失敗，使用者按登出後也不應繼續顯示為已登入。

## 八、警告如何判讀

- Lombok `@Builder` 忽略欄位初始值：既有正式程式警告，未使編譯或測試失敗，應由其他維護任務處理。
- deprecated API：代表某些測試或依賴使用即將淘汰的 API，這輪沒有造成失敗。
- `glob@10.5.0` deprecated：間接開發依賴警告；npm audit 顯示 0 vulnerabilities。未來可隨上游套件更新處理。
- Vite chunk 超過 500 kB：正式 build 成功，但提示未來可做 code splitting；它是效能議題，不是 CR-018 失敗。
- Docker blkio／seccomp：Docker Desktop 環境能力警告，Testcontainers 已正常執行。

「有 warning」不等於可以永遠忽略；正確做法是判斷它是否影響本次完成條件，再放入對應 CR，而不是讓任務無限制擴張。

## 九、CR-018 沒有完成什麼

- 沒有把全專案覆蓋率提高到理想值；初始行覆蓋率仍低。
- 沒有補齊 validation、統一錯誤 schema 或所有 Card 業務測試。
- 沒有處理 CR-017 的 localStorage user ID key。
- 沒有改 API endpoint、正式資料庫 schema 或正式 JWT 策略。
- 沒有建立 CI pipeline；乾淨 clone 已證明目前可重建，CI 可作為後續自動化。

CR-018 完成的是「可穩定執行的測試基礎與第一批核心回歸保護」，不是「從此測試全部完成」。每次修正其他 CR，都應把相關測試加到這套基礎上。

## 十、未來新增測試的判斷方式

修改行為時，至少詢問：

1. 哪一個輸入或狀態會觸發這個行為？
2. 成功時應觀察到什麼結果？
3. 失敗、未授權或邊界值應得到什麼結果？
4. 測試需要完整 Spring／資料庫，還是純函式即可？
5. 測試能否獨立執行，不依賴順序與舊資料？

後端跨 Security、Controller、Service、Repository 的規則適合整合測試；單一 Service 計算可用單元測試。前端純函式優先直接測試；Store 可 mock API；元件互動再使用 Vue Test Utils。

## 十一、測試失敗時的排查順序

### 後端

1. `docker info`：確認 Docker daemon 可用。
2. 確認 Docker 能取得 `postgres:16-alpine` image。
3. 執行 `./gradlew.bat test --info` 取得更多資訊。
4. 查看 `echo-gallery-backend/build/reports/tests/test/index.html`。
5. 確認測試啟用 `test` profile，且沒有讀取 `.env`。
6. 檢查失敗是環境啟動、資料清理、HTTP status 還是斷言差異。

### 前端

1. 確認在 `echo-gallery-frontend/` 執行指令。
2. 使用 `npm ci` 依 lockfile 重建相依套件。
3. 執行單一檔案，例如 `npm run test:run -- src/stores/authStore.test.ts`。
4. 確認 mock 是否在每個測試前清除。
5. 若 `window` 或 `localStorage` 不存在，檢查 Vitest 是否使用 jsdom。
6. 若測試通過但 build 失敗，另外處理 TypeScript 或 Vite 建置錯誤。

## 十二、復盤結論

這次最重要的不是新增了 11 個檔案變更或 11 個測試案例計數，而是形成一條可重複的安全網：

```text
修改程式 → 執行聚焦測試 → 執行完整測試／build → 在乾淨環境驗證 → 記錄證據
```

測試的目的不是證明程式永遠沒有錯，而是把已知的重要規則變成可以反覆執行的檢查。當未來的修改違反這些規則時，開發者能在推版前得到明確訊號，這就是 CR-018 對後續所有 Code Review 修正的基礎價值。
