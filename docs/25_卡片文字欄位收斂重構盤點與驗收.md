# 卡片文字欄位收斂重構盤點與驗收

> 狀態：程式實作與本機資料庫 migration 完成；正式資料庫 migration 與瀏覽器手動回歸待執行
>
> 建立日期：2026-09-28
> 目的：追蹤 Card 文字欄位由 `reason`／`summary`／`content` 收斂為 `cardNote`／`content` 的資料庫、前後端 contract、UI 與驗證工作。本文件記錄需求與驗收基準，不以文件文字取代實際程式、SQL 與手動驗證。

## 1. 需求與決策

### 1.1 改動緣由

既有建立卡片流程提供「留下原因」300 字、「內容重點」600 字與無限制內容三個文字欄位。實際使用時，填寫位置常由剩餘字數決定，而不是由欄位語意決定；這使建立與回顧時都增加了不必要的判斷成本。

本次收斂為兩個欄位：

| 技術欄位 | 資料表欄位 | UI 名稱 | 限制 | 用途 |
|---|---|---|---|---|
| `cardNote` | `card_note` | 卡片筆記 | 1000 字 | 記錄留下原因、內容重點、個人解讀與再次遇見時的想法；列表與回顧優先閱讀。 |
| `content` | `content` | 更多內容 | 無限制 | 儲存完整原文、延伸筆記、探索紀錄或需要保留的長內容。 |

`content` 的無限制特性不代表每張卡片都必須填寫長內容；它是卡片筆記不足時的可選延伸空間。

### 1.2 既有資料合併規則

| 原 `reason` | 原 `summary` | 目標 `card_note` |
|---|---|---|
| 有值 | 有值 | `reason + "\n\n" + summary` |
| 有值 | 空值 | `reason` |
| 空值 | 有值 | `summary` |
| 空值 | 空值 | `NULL` |

原欄位長度為 `reason VARCHAR(300)` 與 `summary VARCHAR(600)`；即使兩者皆達上限，合併後最多 `300 + 2 + 600 = 902` 字。因此 `VARCHAR(1000)` 可完整相容既有合法資料，無須截斷、摘要或以 AI 改寫文字。

### 1.3 範圍界線

本次只處理 Card 的文字內容模型。議題更新、實驗場說明、HTML `<summary>`、查詢結果摘要、API Page `content` 陣列等同名概念均不在本次欄位重構範圍。

實驗場將探索紀錄附加至 Card `content` 的既有行為保留不變；其內容仍屬「更多內容」。

## 3. 實作與資料遷移順序

### 3.1 一次性 migration

1. 備份正式環境資料庫。
2. 先執行 preflight query，確認所有既有資料合併後不超過 1000 字；若有例外，停止 migration 並先處理資料。
3. 新增 `cards.card_note VARCHAR(1000)`。
4. 依 1.2 規則回填 `card_note`。
5. 移除 `cards.reason` 與 `cards.summary`。
6. 查核 Card 筆數、`card_note` 內容、`content` 內容與 schema。

SQL 是一次性、不可逆的資料結構調整。應先在本機資料庫完成 migration、啟動新版程式與手動測試後，再於正式環境依相同順序執行。

### 3.2 部署限制

新版後端依賴 `card_note`，舊後端依賴 `reason` 與 `summary`；移除舊欄位後，舊後端不能繼續運作。前端 request／response contract 也同步改名，因此應在維護窗口內依序執行 migration，再同時部署新版後端與前端，避免新舊版本交叉存取。

本次 SQL 依既有推版策略只供本機與正式環境手動執行，是否提交至 repository 另由使用者決定。
