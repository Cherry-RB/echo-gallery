## 一、文件目的

本文件保存 Echo Gallery「資訊轉化觀測台」的產品目的、現有資料能力、指標語意、頁面資訊架構、前端原型策略、未來 API 與事件模型評估、效能原則、任務拆分及去留條件，供後續設計、實作、Code Review 與產品驗證使用。

本功能並非一般生產力 Dashboard，也不以完成率、成熟率、每週產量或健康分數評價使用者。它希望協助使用者理解：

1. 系統現在保存了哪些內容與狀態。
2. 過去留下的內容最近是否重新參與思考。
3. 哪些材料產生了以前不存在的新 Card。
4. 哪些議題已留下可往前走的方向。
5. 哪些明確摩擦或資料異常值得看一眼。

文件責任分工：

- `ECHO_GALLERY_MVP.md`：保存產品定位、MVP 決策與歷史演進。
- 第 18、20 份文件：分別保存議事廳與實驗場的領域設計。
- 本文件：保存跨 Card、回流、Tag、Experiment 與 Work 的觀測設計。
- 目前程式碼、正式 schema 與測試：判斷實際系統行為的主要依據。

## 二、決策背景

### 2.1 先前儀表板為何撤回

2026-09-20 曾撤回尚未提交的回流與成長儀表板原型。問題不是統計永遠沒有價值，而是原型主要呈現資料庫存量、回流負載與異常數字，沒有充分回答：

- 這些資訊為何值得注意？
- 它如何協助使用者重新理解內容？
- 以前留下的內容是否正在產生新的東西？
- 使用者知道這個數字後，可以做什麼？

本次重新設計不沿用健康度、成熟率、種子債務或產量 KPI，而改以「描述系統正在發生什麼」為核心。

### 2.2 Echo Gallery 想觀察的循環

資訊可能經歷：

```text
遇見／輸入
  ↓
保存
  ↓
重新遇見
  ↓
重新理解／加工
  ↓
建立關聯
  ↓
產生新的理解
  ↓
形成議題／研判
  ↓
形成下一步
  ↓
接觸現實
  ↓
得到新的經驗／資訊
  ↓
重新回到系統
```

這不是每張 Card 都必須完成的漏斗。Card 可以只是記憶、素材、觀點、尚在醞釀的問題、已完成使命的紀錄，或單純值得保存的東西。

### 2.3 三個跨模組觀測維度

#### Flow｜流動性

關心過去留下的內容是否重新參與現在的思考，例如完成 Today 回顧、獲得價值確認、加入 Experiment、加入 Work 或成為生成來源。

流動性不是越高越好；長期沉睡也可以是合理狀態。

#### Generativity｜生成性

關心既有材料是否產生以前不存在的新理解。目前最明確的依據是 `CardRelation` 所保存的 source Card 與 derived Card。

單純新增收藏 Card 不算生成；一張 derived Card 即使有多個來源，也只算一張生成結果。

#### Closure｜閉環性

關心思考是否有機會走向現實，而現實帶來的新資訊是否重新修正理解。

目前系統只能可靠知道 WorkProgressUpdate 是否留下 `nextStep`，以及同一 Work 之後是否又留下更新；不能知道 nextStep 是否真的執行，也不能判斷後續更新是否屬於現實回饋。因此第一版只能呈現「閉環線索」，不能計算完成率或閉環率。

## 三、產品設計原則

1. **描述，而不是評分。**
2. **促進重新理解，而不是催促完成。**
3. **允許醞釀，但讓真正的摩擦變得可見。**
4. **讓使用者看見以前留下的內容正在產生新的東西。**
5. **`nextStep` 是方向，不是 Todo。**
6. **沒有唯一的健康狀態。**大量輸入、長期醞釀或一段時間集中輸出都可能合理。
7. **不要因為數字可以計算，就把它顯示出來。**
8. **不要讓觀測系統本身製造新的維護工作。**
9. **具體內容通常比抽象比率更重要。**
10. **先建立能幫助真實使用的 MVP，再考慮完整 Analytics。**

禁止使用的呈現方式包括：

- 健康分數。
- 成熟率與未成熟警告。
- 行動轉化率越高越好的暗示。
- Seed 逾期或種子債務。
- 每週產量與生產力 KPI。
- 紅黃綠績效燈號。
- 以 Card 數量遞減解讀成功或失敗的 funnel。
- Work stale、欠更新或 nextStep 逾期警告。

## 四、現行資料模型盤點

### 4.1 Card 與 Today

現有重要欄位：

| 欄位 | 現行語意 | 歷史能力 |
|---|---|---|
| `createdAt` | Card 建立時間 | 可作期間統計 |
| `updatedAt` | Card 最近一次任何持久化更新 | 不能等同內容編輯 |
| `intervalDays` | 完成回顧後的回流間隔 | current state |
| `nextShowAt` | 下一次取得 Today 資格的時間 | current state |
| `lastOfferedAt` | 最近一次被選入 Today 批次 | 只保留最後一次 |
| `lastOpenAt` | 最近一次完成 Today 回顧 | 只保留最後一次 |
| `openCount` | 完成 Today 回顧的累積次數 | 累積值，沒有逐次時間 |
| `lastLikedAt` | 最近一次點亮星標 | 只保留最後一次正向事件 |
| `likeCount` | 目前累積星標數 | 取消星標會遞減，非歷史事件數 |
| `lastInteractionAt` | 目前只由 read／Like 更新 | 不是所有互動時間 |
| `snoozeCount` | 自上次完成回顧後累積延後次數 | 完成回顧後歸零，沒有逐次時間 |
| `needsProcessing` | 使用者主動留下的待整理提示 | current state |
| `isArchived` | 是否封存 | current state，沒有狀態歷史 |
| `growthStatus` | 舊全域成長狀態 | legacy，相容期欄位 |

Today 的重要規則：

- Card 被提供不等於完成回顧。
- 選入批次只更新 `lastOfferedAt`。
- 只有從 Today 進入詳情並成功執行 read action 才更新 `lastOpenAt`、`openCount` 與 `nextShowAt`。
- 同一次 `lastOfferedAt` 的 read 保持冪等。
- 使用者要求下一批時，尚未處理的本批 Card 也會增加 `snoozeCount`。
- 因此 `snoozeCount` 不完全等於逐張點擊「稍後再看」的次數。

### 4.2 Tag

Tag 目前只與 Card 建立多對多關係，可以回答目前有哪些 Tag、每個 Tag 目前包含哪些 Card，以及沒有 Tag 的 Card。系統沒有保存：

- Card 過去曾有哪些 Tag。
- 事件發生當時的 Tag。
- Work 或 Experiment 自己的 Tag。

### 4.3 Experiment、ExperimentCard 與 CardRelation

| Entity | 可用資料 | 主要限制 |
|---|---|---|
| Experiment | 建立／更新時間、封存狀態、假設、識別色 | `updatedAt` 不能代表材料加入或生成 |
| ExperimentCard | Card、stage、note、`addedAt` | stage 更新會覆寫；移除後紀錄消失 |
| CardRelation | Experiment、source、derived、relationType、`createdAt` | 關係或 Card 刪除後歷史消失 |

現行 grow transaction 會在同一個 Experiment 中：

1. 建立一張新 Card。
2. 將新 Card 加入該 Experiment。
3. 對每張來源 Card 建立一筆 `DERIVED_FROM` relation。

因此：

- 生成結果數必須 `COUNT DISTINCT derivedCardId`。
- relation row count 代表來源邊數，不代表生成次數。
- 現行流程不支援一次跨多個 Experiment 取來源，因此「跨 Experiment 生成」目前不能成立。

### 4.4 Work、WorkCard 與 WorkProgressUpdate

| Entity | 可用資料 | 主要限制 |
|---|---|---|
| Work | current status、整體研判、建立／更新／完成時間 | 狀態歷史未保存；重新開啟會清空 `completedAt` |
| WorkCard | Card、status、note、`linkedAt`、`usedAt` | 移除後紀錄消失；回到 CANDIDATE 會清空 `usedAt` |
| WorkProgressUpdate | changeSummary、assessment、nextStep、建立／更新時間 | 可編輯、可刪除；沒有結果類型或 Card 外鍵 |

`nextStep` 只存在於某一筆 WorkProgressUpdate，不複製到 Work。最新 Update 沒有 nextStep 時，不應沿用更舊、可能已過期的 nextStep。

### 4.5 可直接使用的時間資料

相對可靠的建立時間：

- `Card.createdAt`
- `Experiment.createdAt`
- `ExperimentCard.addedAt`
- `CardRelation.createdAt`
- `Work.createdAt`
- `WorkCard.linkedAt`
- `WorkProgressUpdate.createdAt`

只能代表最後一次或目前狀態：

- `Card.lastOfferedAt`
- `Card.lastOpenAt`
- `Card.lastLikedAt`
- `Card.updatedAt`
- `Card.snoozeCount`
- `ExperimentCard.stage`
- `WorkCard.status`／`usedAt`
- `Work.status`／`completedAt`

對「以現在為終點」的近 7／30／90 天，可以用最後一次時間回答「是否至少發生過一次」。不能用它們回答完整事件次數，也不能可靠還原已結束的歷史區間。

### 4.6 Legacy 與文件差異

`Card.growthStatus` 仍存在於 Entity、Search、Card Detail、WorkCard response、Demo 與右側欄統計，但最新產品模型已將 `SEED / GROWING / MATURE` 定義為 `ExperimentCard.stage` 的情境角色。

觀測台不得使用全域 growthStatus 建立：

- Card 成熟率。
- 成長速度。
- Seed 積壓。
- 全域內容健康度。

此外，第 20 份文件記載 migration SQL，但目前 repository 工作區沒有 `docs/migrations/`。後續實作索引或 schema 變更前，必須查驗實際 production schema，不能只依文件或 JPA annotation 推定。

## 五、觀測資訊分類

觀測內容不只依 Card、Tag、Work、Experiment 模組區分，也依它回答的問題分成六類：

### 5.1 存量與結構

回答「現在系統裡有什麼」，例如 Card 總數、各狀態數、Tag 數、Work 數與 Experiment 數。

### 5.2 排程與運轉

回答「回流機制現在如何安排、資料是否一致」，例如週期分布、未來排程與欄位異常。

### 5.3 使用與注意力

回答「哪些內容最近重新出現或被使用」。目前因事件歷史不足，只能部分觀測。

### 5.4 關聯與生成

回答「既有內容是否進入新脈絡或長出新內容」，核心資料為 ExperimentCard、CardRelation 與 WorkCard。

### 5.5 方向與後續

回答「哪些議題已形成 nextStep，之後是否又留下資訊」，但不將其解讀為任務完成。

### 5.6 維護與資料品質

回答「有哪些使用者主動留下的整理訊號或技術資料異常值得檢查」。

行動版建議順序：系統現況 → 可以往前走 → 值得看一眼 → 期間三項觀測 → 兩個內容清單 → 完整活動。具體內容與下一步優先於抽象活動分布。

頁面採「一眼現況、立即行動、再回看變化」的層級：不再為每個區塊重複配置長標題、說明與摘要；固定解釋改收進 `ⓘ`，完整活動改預設收合。這使觀測台不退化成報表，也讓具體內容與可前往的方向保有最高閱讀權重。

Flow／Generativity／Closure 是產品與資料設計使用的內部概念，不是 UI 名稱。原型驗證顯示直接顯示英文與抽象名詞會提高理解門檻；畫面應改以使用者能直接回答的問題呈現：

- 以前留下的卡，有重新回到現在嗎？
- 它們有長出新的東西嗎？
- 有哪些想法已經可以往前走？

## 八、V1 各區塊設計

### 8.1 A｜這段時間發生了什麼

第一版採固定模板與可靠數值，不使用 AI，也不先分類為輸入期、生成期、停滯期或健康狀態。此摘要與 B、C、D 是期間觀測；E、F 與頁面最上方「現在的系統」是 current stock，不隨時間篩選切換。摘要與三個觀測問題放在同一個「回看近期」區塊，避免以不同卡片重複描述同一批資料。

範例：

> 近 30 天，12 張較早建立的 Card 再次參與；從既有材料長出 3 張 Card；2 個議題在先前下一步後留下了新更新。目前另有 4 張 Card 被標為待整理。

只顯示非零句段。若沒有資料：

> 近 30 天沒有留下足以描述資訊流動的紀錄。這不代表系統停滯，也可能只是近期較少使用，或現有資料尚未記錄某些互動。

避免「表現良好、健康、不健康、活躍不足、轉化偏低、停滯、負擔過重、應該整理、生成效率」等價值判斷。

### 8.2 B｜Flow／Generativity／Closure 線索

本節標題僅用於文件分類；實際 UI 必須使用上述三個提問，不顯示 Flow、Generativity、Closure、流動性、生成性或閉環線索。

#### Flow

「舊 Card」候選定義為 `Card.createdAt < periodStart`。

「可觀測重新參與」以 unique Card 計算，來源為：

- `lastOpenAt` 落在期間內。
- `lastLikedAt` 落在期間內。
- 期間內仍保留的 ExperimentCard membership。
- 期間內仍保留的 WorkCard membership。
- 期間內成為 CardRelation source。

不使用 `updatedAt`，因為它不能區分內容編輯與其他持久化操作；目前也不能可靠納入 Snooze。

#### Generativity

- 衍生 Card：期間內 `COUNT DISTINCT derivedCardId`。
- 來源 Card：期間內 `COUNT DISTINCT sourceCardId`。
- relation row count 只可稱為來源關係數，不能稱為生成次數。

#### Closure

第一版顯示「閉環線索」，不顯示閉環率：

- active Work 最新 Update 具有 nextStep 的數量。
- 期間內有新 Update，且同一 Work 在此之前曾留下 nextStep 的 distinct Work 數。

後者只能表示方向之後又留下新紀錄，不能證明 nextStep 已執行、完成或造成後續更新。

### 8.3 C｜最近留下的活動紀錄

使用 activity distribution，不使用 funnel。此區預設收合為「查看近 N 天的完整近期紀錄」；只有使用者想追溯近期活動時才展開，避免首次閱讀被大量數字打斷：

- 新增 Card：unique Card。
- Today 再次出現：unique Card。
- 完成 Today 回顧：unique Card。
- 放入實驗場：期間內新增的 ExperimentCard record count；它表示材料加入實驗場，不能稱為生成。
- 帶入議題：期間內新增的 WorkCard record count；它表示素材進入議題脈絡，不能稱為生成。
- 長出新 Card：distinct derived Card。
- 議題更新：WorkProgressUpdate row count。

各項保留自己的單位，不計算階段轉換百分比，不以數量較少判斷阻塞。

### 8.4 D｜最近長出的東西

這是 V1 優先級最高的內容區塊之一。每張卡顯示：

```text
「我需要的不是小公司，而是 ownership」

來自「理想工作型態」實驗主題
9/23 長出

來源
• 銀行工作感受
• 理想君臣關係
• 產品團隊想像

[職涯] [ownership]
```

互動：

- 點衍生 Card → Card Detail。
- 點來源 → 來源 Card Detail。
- 點 Experiment → Experiment Detail。
- archived Card 仍可保留於歷史觀測，但顯示低干擾標記。

正式查詢應先取得最近 3～6 個 distinct derived Card，再批次取得 relation、source、Experiment 與 tags；不能在多來源 join 後直接 limit。

### 8.5 E｜現在可以往前走

規則：

- 只納入 `IDEA / DRAFT / ACTIVE` Work。
- 排除 `DONE / ARCHIVED`。
- 只有最新一筆 Update 的 `nextStep` 非空才顯示。
- 最新 Update 沒有 nextStep 時，不沿用更舊的 nextStep。
- 依最新 Update `createdAt DESC` 排序。
- 一次顯示 3～5 個。
- 顯示議題名稱、nextStep 與最近更新時間。
- 點擊進入 Work Detail。

不加入 checkbox、期限、優先級、逾期或完成狀態。

### 8.6 F｜值得看一眼

這不是警告中心。V1 候選只保留明確訊號：

#### needsProcessing

顯示 current stock，點擊後進入 Search 並套用 `needsProcessing=true`。

#### 尚未完成回顧的累積延後

目前只能依 `snoozeCount` 顯示「自上次完成回顧後累積延後」，不能寫成近 7／30／90 天的 Snooze 次數。

#### 有近期材料、目前沒有保留中衍生關係的 Experiment

候選條件：

- 未封存。
- 目前有 Card。
- 期間內仍有 retained ExperimentCard 加入。
- 目前沒有 CardRelation。

文案應是：

> 這個實驗主題最近加入了一些材料，目前還沒有保留中的衍生 Card。也許值得重新看看它們之間是否出現新的關係。

不得稱為零產出、生成異常、未成熟或低效率 Experiment。

V1 不做 nextStep 長時間未更新、dead link、duplicate Card、功能使用率與主觀維護負荷問卷。

## 九、模組詳細觀測候選

### 9.1 卡片與回流

#### 卡片現況

| 指標 | 建議定義 |
|---|---|
| 卡片總數 | 所有未刪除 Card，包含封存 |
| 使用中／回流池 | 未封存且 `intervalDays`、`nextShowAt` 不為空 |
| 已暫停 | 未封存且 `intervalDays`、`nextShowAt` 皆為空 |
| 已封存 | `isArchived=true` |
| 從未提供 | `lastOfferedAt IS NULL` |
| 從未完成回顧 | `lastOpenAt IS NULL` 或 `openCount=0` |
| 待整理 | `needsProcessing=true` |
| 排程異常 | 回流與互動欄位彼此矛盾 |

「從未回顧」建議拆成：從未進入 Today、曾進入 Today 但未完成回顧、曾完成至少一次回顧。

#### 回流週期分布

只計算未封存且回流中的 Card：

- 1–7 天。
- 8–14 天。
- 15–30 天。
- 31–60 天。
- 61–90 天。
- 91–180 天。
- 181 天以上。

適合水平長條圖。它描述目前回流池偏向頻繁重遇或長期保存，不能解讀為越短、越平均越健康。

#### 累積延後分布

避免區間重疊：

- 1–2 次。
- 3–4 次。
- 5–10 次。
- 11 次以上。

名稱使用「尚未完成回顧的累積延後」，不使用「最近 Snooze 次數」。

#### 未來回流預覽

可顯示今天、明天、第 2～7 天、8～14 天與 15～30 天。文案使用「依目前排程預計取得回流資格」，不是「未來必須處理」。使用者回顧、延後、暫停、封存或調整週期都會改變預覽。

#### 第二層 Mock 畫面決議

第一階段同步建立 `/overview/cards` 的「卡片與回流」前端 Mock，作為概覽頁的第二層，而非新增左側主選單項目。概覽頁的「查看卡片與回流狀態」可進入此頁，並可返回概覽。

畫面依序呈現：

1. **目前狀態**：回流中、暫停中、已封存、待整理、從未回顧、排程需留意；全部是 current stock，不套用近 7／30／90 天。
2. **回流節奏**：七個回流間隔區間的目前分布；水平長條只幫助閱讀數量，不表示任一節奏比較健康。
3. **接下來一週**：依目前 `nextShowAt` 預計重新出現的日別數量；這是節奏預覽，不是待辦日曆。
4. **稍後再看**：以 3–5、6–10、超過 10 次呈現累積延後的示意分布；文案保留醞釀與重新決定兩種可能，不標記為滯留。
5. **值得再看一眼**：待整理、反覆稍後與排程資料訊號，各自保留未來 drill-down 的入口。

本頁所有數字目前均為固定示意資料；正式版仍須依本文件的資料定義、聚合 API 與資料缺口評估實作。

#### 排程與資料異常

候選檢查：

- `intervalDays IS NULL` 但 `nextShowAt IS NOT NULL`。
- `intervalDays IS NOT NULL` 但 `nextShowAt IS NULL`。
- `openCount > 0` 但 `lastOpenAt IS NULL`。
- `openCount = 0` 但 `lastOpenAt IS NOT NULL`。
- 互動時間早於 `createdAt`。
- 非預期負數計數。

技術異常正常時完全隱藏，不以一般績效指標常駐。

### 9.2 標籤

候選內容：

- Tag 總數。
- 沒有 Tag 的 Card 數。
- 沒有任何 Card 的空 Tag。
- 每張 Card 平均 Tag 數。
- 只有一張 Card 使用的 Tag 數。
- 各 Tag Card 數量分布。
- 最常共同出現的 Tag 組合。
- 幾乎完全重疊的 Tag。
- 各 Tag 下的使用中、暫停、封存、待整理、從未回顧 Card。
- 各 Tag 下進入 Experiment、Work 或曾成為生成來源的 Card。

「近期注意力」若實作，應以期間內有可觀測活動的 unique Card，再按目前 Tag 分組。同一 Card 在同一 Tag 只算一次；多 Tag Card 會同時進入多個 Tag，因此各 Tag 數量不能相加當作 Card 總數。

因為使用的是目前 Tag，且編輯與 Snooze 缺少可靠時間，近期注意力列為 V1.1 候選。

### 9.3 議事廳

候選內容：

- Work 總數與 `IDEA / DRAFT / ACTIVE / DONE / ARCHIVED` 分布。
- 近 30／90 天留下更新的 distinct Work。
- 近 30／90 天 WorkProgressUpdate 數。
- 從未留下更新的 Work，僅作內容入口，不作警告。
- active Work 的最新 nextStep 內容。
- 先前 nextStep 後又留下新 Update 的 Work。
- 素材池與已運用 Card 數。
- 近 30／90 天新增素材的 Work。
- 同一 Card 被多個 Work 引用。
- derived Card 後來被加入 Work。

「derived Card 進入 Work」是 Generativity 走向 Closure 的重要跨模組線索，但不能證明已在現實中採取行動。

### 9.4 實驗場

候選內容：

- Experiment 總數、未封存、已封存、空 Experiment。
- 最近 30／90 天仍有新材料加入的 Experiment。
- 每個 Experiment 的 Card 數與數量區間。
- ExperimentCard stage 分布，只表示情境角色，不表示成熟率。
- 同一 Card 出現在多個 Experiment。
- 期間內 distinct derived Card。
- 期間內 distinct source Card。
- 有保留中生成關係的 Experiment。
- 每張 derived Card 的來源數。
- derived Card 後來是否進入其他 Experiment 或 Work。
- 既是 derived Card、後來又成為下一次 source 的 Card。

最後一項可協助使用者看見真正的資訊循環：過去生成的理解又成為下一輪生成材料。

### 9.5 跨模組資訊轉化

跨模組觀測是本功能相較一般模組統計最重要的差異：

```text
較早建立的 Card
  ├─→ Today 再次出現／完成回顧
  ├─→ 加入 Experiment
  ├─→ 成為生成來源
  ├─→ 長出 derived Card
  └─→ 加入 Work／參與議題研判
```

可以觀察：

- 同時存在於 Experiment 與 Work 的 Card。
- 存在於多個 Experiment 的 Card。
- 存在於多個 Work 的 Card。
- derived Card 後來進入 Work。
- derived Card 後來又成為 source Card。
- Work 形成 nextStep 後又加入的新素材或新 Update。

所有 sequence 都只能描述時間先後與目前保留中的關係，不能宣稱因果。

## 十一、時間範圍

V1 支援：

- 近 7 天。
- 近 30 天，預設。
- 近 90 天。

原因：

- 7 天雖然較短，但能讓使用者辨識非常近期的變化；它只是一個觀測視窗，不是要求系統每週都要有產出。
- 最後一次時間欄位只適合以現在為終點的 rolling period。
- 「今年」或任意歷史區間容易讓人誤以為有完整 event history。
- 「全部」會混合 current stock 與歷史活動。

適用時間篩選：

- Card 建立。
- Today 提供／完成回顧的 unique Card。
- ExperimentCard 加入。
- CardRelation 建立。
- WorkCard 加入。
- WorkProgressUpdate 建立。

不套時間篩選：

- needsProcessing。
- 目前 snoozeCount。
- active Work 最新 nextStep。
- Experiment 目前素材數。
- Card、Work、Experiment 現行狀態。

UI 必須清楚區分「近 7／30／90 天」與「目前」；篩選器只能影響歷史觀測，不能改變 current stock、目前 nextStep 或維護訊號。

## 十二、現有 API 與前端計算邊界

### 12.1 可作 drill-down 或暫時重用的 API

| API | 可用用途 | 限制 |
|---|---|---|
| `GET /api/sidebar/stats` | 少量 current stock | 含 legacy growthStatus，缺少期間與 needsProcessing |
| `GET /api/sidebar/tags/top` | 現有 Tag 存量排行 | 不是近期注意力 |
| `GET /api/cards/search` | 待整理 drill-down | 沒有互動時間篩選 |
| `GET /api/works` | 每個 Work 最新 Update 與 nextStep | 回傳所有 Work，非 bounded overview projection |
| `GET /api/work-updates/recent` | 最近議題更新內容 | 不提供 sequence 聚合 |
| `GET /api/experiments` | Experiment 與 stage count | 沒有生成統計 |
| `GET /api/cards/{id}/experiment-context` | 單卡脈絡 | 不可對所有 Card 逐張呼叫 |

### 12.2 不應由前端計算

- distinct derived Card 與完整來源。
- 跨表重新參與 Card 去重。
- 每個 Experiment 是否有生成。
- nextStep 後是否有較新的 Update。
- 活躍 Tag 的 unique Card 聚合。
- 多模組活動分布。

前端若下載全部 Card、逐頁載入三種 stage，或對每張 Card 查 context，會造成資料不完整、大量 request 或類 N+1。正式版本應由後端 aggregate。

## 十三、第一階段前端 Mock 原型

### 13.1 已確認決議

第一階段只建立前端畫面，用示意資料驗證產品形態。整體產品、資料與 API 規劃仍保持完整，不將各區塊拆成彼此無關的小功能。

原型預計包含：

- 「資訊轉化觀測台」路由與導覽入口。
- 可由概覽進入、專注於 current stock 與回流安排的「卡片與回流」第二層 Mock。
- 完整桌機、手機與暗色模式。
- current snapshot 與近 7／30／90 天切換；時間切換只影響對應 mock 情境。
- 現在的系統分為「內容目前怎麼被安放」與「目前有哪些脈絡與方向」；後者並列活躍實驗場與已有 nextStep 的議題。
- 「回看近期」區塊中的期間系統狀態摘要與三個觀測問題。
- 預設收合的完整近期紀錄。
- 最近長出的 Card。
- 現在可以往前走。
- 值得看一眼。
- 可連到既有 Card、Experiment、Work 詳情的示意互動。
- loading、empty、error 與長文字狀態。
- 清楚標示「介面原型／目前為示意資料」。

第一階段不包含：

- 新後端 endpoint。
- Repository aggregate query。
- schema 或 index 修改。
- ActivityEvent。
- 正式指標門檻。
- 從前端下載所有資料自行運算。
- 將 mock 數字混入正式使用者統計。

### 13.2 前端架構原則

先定義預期正式 DTO：

```ts
interface OverviewSnapshot {
  generatedAt: string
  period: OverviewPeriod
  flow: FlowMetrics
  generativity: GenerativityMetrics
  closure: ClosureMetrics
  activity: ActivityDistribution
  recentDerivedCards: DerivedCardPreview[]
  currentNextSteps: NextStepPreview[]
  signals: ObservationSignal[]

```

展示元件只接收 props，不知道資料來自 mock 或 API：

```text
InformationObservatory.vue
        │
        ├─ mockOverviewData（原型期）
        │
        └─ GET /api/overview（正式期）
                 ↓
        同一組展示元件
```

避免在各 component 直接硬編數字，也不要在原型期先建立假的 API request。

### 13.3 Mock 情境

至少準備：

1. **一般使用情境**：有回流、生成、nextStep 與少量待整理。
2. **輸入較多、尚未生成**：確認畫面不暗示使用者表現不好。
3. **長期醞釀**：數字較少，但仍有值得閱讀的具體內容。
4. **全空情境**：不能產生 0 分或失敗感。
5. **極端內容**：長標題、多來源、長 nextStep、大數字與封存內容。

### 13.4 原型要驗證的問題

- 首頁是否仍太像一般數據 Dashboard？
- 數字是否過多？
- 具體衍生 Card 是否比統計更有價值？
- Flow／Generativity／Closure 是否容易理解？
- Closure 保守措辭是否仍造成誤讀？
- 系統狀態摘要是否替使用者亂下判斷？
- 「值得看一眼」是否產生被催促感？
- Card 詳細統計應留在首頁或第二層？
- 是否真的需要 Tag、Work、Experiment 的獨立統計頁籤？
- 行動版是否資訊密度過高？
- 暗色模式是否仍能維持層級，而不依賴過強警示色？

## 十四、未來 API Proposal

Mock 驗收後，V1 建議依兩層頁面的時間語意提供兩支 aggregate API：

```http
GET /api/overview?periodDays=30
GET /api/overview/card-return
```

2026-09-26 已實作這兩支僅限登入使用者的 aggregate API。概覽只接受 `periodDays=7|30|90`，回傳 current stock、期間 metrics、活動清單、衍生卡來源脈絡與最新有效 nextStep；第二層回傳 current card state、週期分布、未來七天排程與「自上次完成回顧後」的連續 Snooze 分布。兩支 API 都由後端限縮 current user，不回傳整個 Card library 給前端計算。

目前 `lastOfferedAt` 與 `lastOpenAt` 都只保留最後一次時間。因此期間活動中「最後一次在 Today 出現」與「最後一次完成回顧」是 distinct Card 的 retained-state 觀測，不是完整歷史 event count。SnoozeCount 會在完成回顧時歸零，也不可解讀為生涯累積延後次數。

概覽另提供 `recentExperimentMaterials`：它只列出期間內新建立 `ExperimentCard` 關係、且在同一實驗場沒有作為 `DERIVED_FROM` 結果的 Card。這讓「近期進入實驗場的材料」與「近期長出的東西」並列閱讀，前者代表材料正在聚集，後者才代表已保留來源譜系的新理解；兩者不得重複計算。

概覽 endpoint 的理由：

- 所有區塊共用一致時間邊界與 `generatedAt`。
- 避免前端協調多支 API 的 loading 與部分失敗。
- 各內容列表可設定 3～6 筆硬上限。
- 適合目前小型個人專案的維護成本。
- 一支 endpoint 不代表一支巨大 SQL；後端可用數個清楚 projection query 組合 DTO。

卡片與回流 endpoint 描述 current stock 與未來排程，不能與受 `periodDays` 影響的概覽混在同一 response；其詳細理由與 drill-down 規則見本節後段。

Response 草案：

```json
{
  "generatedAt": "2026-09-25T20:00:00+08:00",
  "period": {
    "days": 30,
    "from": "2026-08-27T00:00:00+08:00",
    "to": "2026-09-26T00:00:00+08:00",
    "timeZone": "Asia/Taipei"
  },
  "flow": {
    "offeredExistingCards": 18,
    "reviewedExistingCards": 7,

    "derivedCards": 3,

  "activity": {
```

未來只有在最近衍生 Card、Activity timeline 等區塊需要獨立分頁、不同更新頻率或獨立錯誤恢復時，才再拆出 `/overview/derived-cards`、`/overview/activity` 等 API。

「卡片與回流」第二層不應塞進受 `periodDays` 影響的概覽 response。它主要描述 current stock 與未來排程，正式實作候選為：

```http
GET /api/overview/card-return
```

其 response 至少包含卡片狀態、回流間隔分布、未來七天排程、累積延後分布與明確維護訊號；不回傳全部 Card。各數字的具體內容則透過 Card Search 的正式篩選條件 drill-down，例如 `returnState`、`intervalBucket`、`scheduledFrom`／`scheduledTo`、`snoozeBucket`、`scheduleIssue`。不得以「metric 名稱」建立無條件的通用查詢 endpoint，也不得讓前端先下載所有卡片再自行篩選。

正式實作前，需先在 OBS-004 查核既有 Search contract 是否足以承接上述篩選；不足時才擴充明確的 Card Search query parameter 與對應測試。

修改或新增 endpoint 前，必須依 repository 規則重新向產品 owner 說明最終 contract 與影響範圍。

## 十五、Event model 評估

### 15.1 V1 不建立 Event table

現有資料足以先驗證：

- 使用者是否會進入觀測台。
- 衍生 Card 內容是否有價值。
- nextStep 是否適合集中呈現。
- 部分 Flow 是否足夠提供理解。
- 維護訊號是否促進有意義的處理。

在畫面與需求尚未驗證前建立完整事件系統，會增加 schema、寫入流程、索引、刪除語意與資料解讀成本。

### 15.2 未來最小方案

若真實使用證明需要完整歷史，建議使用跨領域 `ActivityEvent`，而不是只服務 Card 的 `CardActivityEvent`：

```text
activity_events
- id
- user_id
- event_type
- card_id nullable
- experiment_id nullable
- work_id nullable
- related_card_id nullable
- metadata jsonb nullable
- created_at
```

使用明確 nullable foreign key，優先於無 referential integrity 的 `contextType/contextId`。

`metadata` 只保存低頻補充，例如事件來源、defer 原因或 previous／next 狀態；不複製 Card 內容與標題。未來會作固定查詢的資料應提升為正式欄位，不應長期藏在 JSON。

### 15.3 候選事件

值得記錄：

- `CARD_REVIEWED`：read API 確實增加 openCount 時。
- `CARD_DEFERRED`：區分手動、切換下一批與排程調整。
- `CARD_CONTENT_EDITED`：真正內容或 Tag 改變。
- `CARD_LIKED`。
- `CARD_PROCESSING_MARKED`／`CLEARED`。
- `ADDED_TO_EXPERIMENT`／`REMOVED_FROM_EXPERIMENT`。
- `DERIVED_CARD_CREATED`：一次 grow action 一筆，不依來源數重複。
- `ADDED_TO_WORK`／`REMOVED_FROM_WORK`。

不記錄：

- GET Card Detail。
- 頁面曝光、滾動與搜尋。
- 每次 API fetch 或 TanStack Query refetch。
- component mount。
- 每一筆 CardRelation 再複製成一筆生成事件。

### 15.4 CARD_REVIEWED 定義

只在以下條件同時成立時記錄：

- 使用者由 Today 進入 Card Detail。
- `/read` 確實更新 openCount。
- 同一個 `lastOfferedAt` 尚未被處理。

單純 GET、Search 後開啟或直接網址不算。

### 15.5 Event model 仍不能解決的語意

事件表可以知道某次 WorkProgressUpdate 被建立，卻不能自動知道內容是否代表現實回饋，也不能證明它與先前 nextStep 具有因果關係。若未來真的需要辨識現實回饋，必須另行設計明確且低負擔的產品輸入，而不是從事件順序假裝推導。

## 十六、效能與索引原則

### 16.1 明顯風險

- CardRelation 目前只有 source／derived index，缺少 Experiment＋createdAt 的期間聚合 index。
- ExperimentCard 的 `(experiment_id, stage, added_at)` 不適合未指定 stage 的近期加入查詢。
- WorkCard 缺少 `(work_id, linked_at)`。
- Card Entity 未宣告 user＋各活動時間 index，實際 production schema 尚待確認。
- Tag attention 若跨多表 union 再 join `card_tags`，需避免重複列爆炸。
- 最近 derived Card 若直接 join source rows 後 limit，會因多來源錯誤分頁。

### 16.2 候選索引

正式實作前依 production `pg_indexes` 與 execution plan 確認：

```text
cards(user_id, created_at)
cards(user_id, last_offered_at)
cards(user_id, last_open_at)
cards(user_id, last_liked_at)

experiment_cards(experiment_id, added_at)
card_relations(experiment_id, created_at, derived_card_id)

work_cards(work_id, linked_at)
work_progress_updates(work_id, created_at, id)

card_tags(card_id, tag_id)
card_tags(tag_id, card_id)
```

`needsProcessing` 與 snooze index 視實際資料量與查詢計畫再決定是否建立 partial index。

### 16.3 現階段不需要

- Redis。
- Elasticsearch。
- Kafka。
- OLAP。
- materialized view。
- 每日預計算表。
- 背景統計 job。

數百至數千張個人 Card，以 user-scoped aggregate query、合理索引與 bounded content list 為優先。不得把全部 Card、ExperimentCard、CardRelation 或 WorkProgressUpdate 載入 JVM／Browser 再篩選。

## 十七、V1、後續與明確不做

### 17.1 V1 候選

V1 由概覽與「卡片與回流」第二層構成。

概覽最多六個區塊：

1. 事實型系統狀態摘要。
2. Flow／Generativity／Closure 線索卡。
3. 活動分布，不做 funnel。
4. 最近長出的 Card。
5. 現在可以往前走。
6. 值得看一眼：needsProcessing、累積延後與 Experiment 重新觀看提示。

時間支援近 7／30／90 天，預設近 30 天；三者都是以現在為終點的滾動期間，不是自然週、自然月或自然季。

「卡片與回流」固定包含 current stock、回流週期分布、未來一週預覽、累積稍後再看分布與明確排程／維護訊號。所有 V1 指標應可透過既有或擴充後的 Search、Card、Experiment、Work 詳情 drill-down，不另做一組與既有資料頁重複的通用統計清單。

### 17.2 V1.1／V2

- Tag 結構、交集與近期活動。
- Work／Experiment 詳細統計頁籤。
- 與既有 Search／詳情無法合理共用時，才新增獨立的 drill-down 分頁。
- 保留中關聯 timeline。
- Work 在 nextStep 後新增素材的提示。
- 使用者主觀維護感受。
- 經驗證後的 ActivityEvent。

### 17.3 暫時不要做

- Flow／Generativity／Closure 綜合分數。
- 生成率、閉環率與成熟率。
- funnel conversion。
- 每週產量。
- nextStep 完成率。
- Work stale／逾期。
- Seed 債務。
- 近 30 天 Snooze 次數。
- 現實回饋數。
- dead link 與 duplicate Card。
- 跨 Experiment 生成統計。
- AI 系統氣象判讀。
- 完整 Analytics Platform。

## 二十、原型與正式功能驗收

### 20.1 前端 Mock 原型完成

### 20.3 產品功能通過驗證

1. 觀測台是否協助使用者理解系統，而不是只看到數字？
2. 最近長出的內容是否讓使用者感受到過去保存具有價值？

7. 使用者是否希望深入 Card、Tag、Work 或 Experiment 詳細統計？
8. 現有資料缺口是否真的值得建立 ActivityEvent？

若答案不支持完整頁面，應優先縮減為「最近長出的內容＋現在可以往前走＋明確維護訊號」，而不是增加更多統計。

以下問題尚待正式 Metric／drill-down contract 與 production schema 查驗決定：
