# 1. 最終產品定義

## 1.1 議事廳負責什麼

議事廳只負責：

1. 這一輪要回答什麼？
2. 現在系統怎麼運作？
3. 目前最限制推進的是什麼？
4. 如果只能介入一個地方，應該動哪裡？
5. 行動後需要等待什麼訊號？
6. 哪些短期波動暫時不值得反應？
7. 世界最新回傳了什麼？
8. 真正執行要去哪裡？

它**不負責**：

- Todo。
- 子任務。
- checklist。
- sprint。
- deadline。
- 任務完成率。
- habit tracker。
- XP / 等級。
- Trello 替代品。

正式分工：

```text
Card
= 保存思想、知識、經驗、成果、情報。

Experiment
= 假設、試法、探索、資源點。

Issue / 議事廳
= 主線系統判讀、瓶頸、槓桿、決策、回饋。

Trello / GitHub / 稿件 / 現實
= 專案拆解、任務管理、真正執行。
```

# 4. 每個欄位的最終語意

## 4.1 `title`（既有）

意義：

一輪需要持續理解、決策與取得現實回饋的 Campaign。

---

## 4.2 `status`（既有）

本輪 **不新增 enum**。

維持：

```text
IDEA
DRAFT
ACTIVE
DONE
ARCHIVED
```

但 UI label 改成：

```text
IDEA      → 探索
DRAFT     → 建模
ACTIVE    → 介入／觀察
DONE      → 收斂
ARCHIVED  → 封存
```

### 重要

不要再畫「passed」或「已完成前面階段」的線性 phase track。

Status 表示：

> **我現在正在用什麼模式面對這個問題。**

不是：

> 完成百分比／等級。

ACTIVE 暫時同時承擔：

- 已採取介入。
- 正等待介入後的回饋。

若真實使用後證明需要獨立 `OBSERVING`，另開未來任務；本輪不得偷加。

DONE backend 既有 `completedAt` 等 domain 行為，必須先 audit 再保留相容，不得只因 UI 改叫「收斂」就破壞既有 lifecycle。

---

## 4.3 `objective`（既有）

UI：

> 本輪系統問題

意義：

> **這一輪需要靠什麼現實資料，讓我比現在更接近答案？**

不是人生願景。

不是「我要成為更好的人」。

例：

```text
如何取得足夠的產品型市場回饋，校準目前版本的市場位置？
```

# SYSTEM SNAPSHOT

## 4.4 `keyStates`（新增）

UI：

> 關鍵狀態

回答：

> 現在有哪些最重要的存量／狀態正在累積、停滯或耗損？

範例：

```text
市場資訊：↑ 正在增加
工程能力：→ 暫時穩定
可用能量：↓ 偏低
可證明作品：↑ 緩慢增加
```

第一版是自由文字。

不做 numeric KPI。

不做自動 trend 計算。

不做專用 array / JSON schema。

---

## 4.5 `dominantLoops`（新增）

UI：

> 主導迴路

回答：

> 哪一條因果循環目前最能解釋系統為什麼變成這樣？

範例：

```text
市場接觸
→ 真實回饋
→ 能力缺口更清楚
→ 學習更聚焦
→ 面試能力提升
→ 能接觸更好的市場
```

或：

```text
工作消耗
→ 下班能量下降
→ 求職行動下降
→ 留在原環境時間增加
→ 工作消耗持續
```

注意：

- 這裡的箭頭可以由使用者直接輸入文字。
- **本輪不做 draggable causal loop diagram。**
- 不自動解析因果節點。

## 4.9 `nonInterventionNote`（新增）

> 暫不介入／延遲提醒

回答：

> 哪些結果本來就具有延遲？哪些短期波動現在不值得觸發大幅策略修正？



# 6. Issue Update 的最終語意

## 6.1 新訊號

原：

> 最近有什麼改變？

新：

> **出現了什麼新訊號？**

helper：

> 新事件、結果、現實回饋，或關鍵資源／限制的變化。只記和上一次相比不同的地方。

---

## 6.2 模型更新

原：

> 現在怎麼看？

新：

> **這讓系統模型怎麼變？**

helper：

> 哪個原本判斷被支持、被挑戰，或哪個關鍵變數／迴路需要重新理解？若模型沒有改變，也可以明確寫「目前不改」。

---

## 6.3 介入／等待

原：

> 所以接下來呢？

新：

> **現在要介入，還是等待？**

helper：

> 若要行動，只留下最重要的介入方向；若樣本不足或存在延遲，也可以明確選擇繼續等待某個訊號。

# 8. Issue 和 IssueUpdate 不得自動同步結論

非常重要。

例如新 Update：

```text
新訊號：
連續三間公司都問 system design。

模型更新：
system design 可能比原先預期更重要。

介入／等待：
下一輪面試前做一次 Echo Gallery system design review。
```

**不要自動把：**

```text
primaryConstraint = system design 不足
```

事件 != 結論。

使用者看完新訊號後，應自行判斷是否值得修改 system snapshot。

因此本輪禁止：

- Update 自動覆寫 Issue system fields。
- AI 自動摘要後寫回。
- CRUD side effect 猜測模型。

請依 repo 現有 migration framework 建立 **新的 additive migration**。

不得修改已經套用過的舊 migration。

```sql

  ADD COLUMN dominant_loops TEXT NULL,
  ADD COLUMN primary_constraint TEXT NULL,
  ADD COLUMN leverage_point TEXT NULL,
  ADD COLUMN watch_signals TEXT NULL,
  ADD COLUMN non_intervention_note TEXT NULL;
```

實際語法、version、檔名以 repo 現況為準。

### 禁止

```text
destructive migration
```

請把六個欄位一路接通：


命名：

## 13.3 API compatibility

既有 request payload 不帶新欄位時：

> 必須仍能正常 create / update。

這些欄位全為 optional / nullable。

不要讓舊 client 或舊資料因新增欄位壞掉。

### 注意 PUT semantics

目前 frontend `UpdateIssueRequest` 看起來是整體 update。

Codex 必須檢查 backend PUT 是：

- full replace？
- merge？
- null overwrite？

新增欄位後，`statusMutation` 等所有舊的 `updateIssue(...)` call site 都必須帶上必要的現有 system field，避免只切 status 時把新欄位清空。

**這是本輪高風險點，必須有測試。**
