## 一、簡介

Echo Gallery 是一個讓使用者自行控制內容回流節奏的個人化瀑布流網站。
> Echo Gallery 是一個個人化內容推播與複習工具，解決使用者收藏內容後不再回看的問題。使用者可以建立外部連結卡片或自建筆記卡片，設定推播頻率，讓有價值的影音、圖文、想法與筆記在未來自動回到個人瀑布流中。專案包含卡片管理、標籤分類、週期性推播、熱度紀錄與星標冷卻機制，目標是讓使用者重新掌握內容再出現的節奏，而不是被平台演算法決定注意力。

### 解決痛點

1. **收藏死亡**：使用者常在 Bilibili、Twitter/X、Facebook、文章、影片、貼文中看到好內容，會收藏、轉存、截圖、丟 Notion。但大多數內容收藏後就死了，不會回頭去看。Echo Gallery 能讓使用者再次遇見收藏內容。
2. **演算法不可控**：現在的社群平台會推播內容，但推播權在平台手上。平台關心的是停留時間，不一定是使用者真正想複習、想反覆吸收的內容。Echo Gallery 能讓使用者將推播權拿回來，讓使用者自己設定這張卡片多久出現一次。
3. **有價值內容需要反覆出現**：很多內容不是看一次就夠。例如：觀念、金句、技術文章、學習影片、閱讀筆記、心理提醒、創作靈感、職涯方向、喜歡的作品分析。它們需要週期性回來，才能真的進入生命或知識系統。Echo Gallery 提供間隔重複的影音圖文與社群內容，讓使用者可以專注於接收值得收藏的、有價值的資訊。
4. **自建筆記也能變成推播**：Echo Gallery 不只處理外部平台收藏，也處理內部輸出，使用者可以把自己的想法、閱讀筆記、日記片段、提醒、創作靈感，做成卡片，然後它會重新出現在瀑布流裡。這就變成：「我不只是被外部內容推播，我也可以被過去的自己推播。」

### 設計理念
> 我如何讓有價值的內容，不只是被收藏後沉沒，而是可以適時的重新出現在瀑布流推播，與我相遇？

## 二、使用方式

### A、建立卡片方式

#### 卡片類型與來源

1. **連結類卡片(具體的內容來源)**：像是在notion建立筆記或知識庫一樣，複製社群平台的網址，建立一張像是貼文/卡片的內容，方便使用者之後可以直接透過點選跳轉到該內容來源。如：Bilibili、YouTube、Twitter/X、Facebook、Instagram、Threads、微博、其他網站等等。
2. **筆記類卡片(自建內容的卡片)**：像是在notion建立筆記或知識庫一樣，建立屬於自己的筆記卡片。如：思考想法、閱讀筆記等等。

#### 填寫內容

卡片的標題、為什麼留下它／我思我長、我見我聞／內容重點、延伸筆記／完整內容、類型、連結網址、封面圖片網址、分類標籤、回流頻率等等。

### B、推播方式

應用具備瀑布流推播的看板功能。有以下幾種類型的看板：
1. **今日看板**：從已到期且未封存的卡片中，每次選出最多 5 張形成限量回流批次。卡片被選入只代表系統提供本次相遇機會，不代表使用者已完成回顧；使用者可主動選擇「今天想多看一批」。
2. **時間序**：卡片建立日期，會顯示最新建立的卡片。
3. **熱度(星標數)**：按照卡片的星標數量，由多到少地顯示。
4. **隨機**：隨機顯示任何未封存的卡片。
5. **已封存**：顯示已封存的卡片，卡片表面直接提供還原操作，並顯示封存前保存的回流狀態。
6. **稍後再看**：稍後再看次數累積超過 10 次的卡片。卡片顯示累積延後次數與下次回流日，並引導使用者調整回流頻率、暫停回流、封存或刪除，而不是再次無意識延後。
7. **查詢**：可依卡片 ID、標題文字、標籤與成長狀態進行複合查詢，並選擇標籤 AND / OR、排序欄位與升冪 / 降冪；查詢屬於主動探索，不會被視為完成 Today 回顧。

### C、互動方式

#### 基礎互動

1. **回流**：使用者可在建立或編輯卡片時設定回流頻率，系統會依此計算卡片「下一次出現的日期」。
2. **開啟連結**：當點選連結類卡片的來源連結，將新開視窗、跳轉至來源網頁。
3. **查看/編輯卡片詳情**：點選出現在推播牆的卡片，可進入卡片詳情頁查看與編輯卡片的完整內容。
4. **完成 Today 回顧**：只有從今日看板點進卡片詳情，才會推進下一次回流日期；卡片單純出現在批次、從其他看板或查詢頁進入詳情，都不算完成本輪回顧。

#### 進階互動

1. **星標**：星標代表喜好度與內容價值程度。同一張卡片，使用者可以重複點擊星標，星標一段時間(如：一週)後就會恢復可以點選的功能，就像bilibili的點讚功能一樣。
2. **封存**：不希望再出現在推播牆的卡片，可以選擇封存起來。
3. **稍後再看**：針對出現在推播牆的卡片，如果目前沒有打算看，但是又希望下次回流時依然可以出現在推播牆，可以點選「稍後再看」，該卡片欄位會自動更新欄位「下一次出現的日期」。
4. **今天想多看一批**：目前批次看完或想繼續探索時，由使用者主動要求下一批；系統不會因卡片離開畫面而自動補滿。
5. **標記種子**：使用者可將內容尚未滿意、之後想補充的卡片主動標記為 `SEED`；此操作不等於回顧，也不改變回流排程。
6. **暫停回流**：使用者可保留 Card，但清除 `intervalDays` 與 `nextShowAt`，使其不再進入 Today；恢復時需重新選擇回流間隔。
7. **取消封存**：取消封存時恢復封存前保存的回流狀態；原排程已到期時可再次成為 Today 候選，原本已暫停的 Card 仍維持暫停。
8. **加入議題**：使用者可從未封存卡片的更多選單直接將 Card 加入既有議題素材池。這是議事廳原型的低摩擦入口，不代表議事廳已永久納入 MVP。

### D、側邊欄

1. **左側導覽列**：新建卡片按鈕、導覽向各種看板的菜單、個人資料、設定、登入、登出
2. **右側狀態列**：
    * 統計資訊：未封存卡片總數、卡片成長狀態、作品總數、未完成作品數、稍後再看次數大於 10 的卡片數
    * 標籤排行、該標籤下的卡片數量

### 技術選型前提與限制

Echo Gallery 的技術選型以「完成 MVP 核心閉環」為優先，而不是追求完整企業級架構。

目前主要考量：

1. **先完成 MVP 功能**：優先完成卡片 CRUD、瀑布流、詳情頁、回流、星標、稍後再看、封存與登入驗證。
2. **同時作為作品集與自用工具**：技術選型需要兼顧面試展示價值與長期維護成本。
3. **預留多使用者可能性**：即使初期主要自用，仍在資料模型中保留 `user` 概念，避免未來資料隔離與多裝置同步時大幅重構。
4. **成本必須可控**：第一版不直接長期部署在 AWS，先以免費或低成本方案完成上線；AWS 作為後續雲端練習與作品集加分項。
5. **避免過度設計**：MVP 暫不導入 Spring Cloud、Redis、Message Queue、Kubernetes、複雜 Batch Job 等工具。

##### TanStack Query 引入原因

一開始專案先以自定義 composable 封裝單次 API 呼叫時的 loading、error 與 execute 狀態。
但 Echo Gallery 的核心畫面是瀑布流推播牆，後續會遇到一般單次 API 封裝不容易處理的情境：

* 使用者從推播牆進入詳情頁後，返回時希望保留原本資料與位置。
* 星標、稍後再看、封存等互動需要讓畫面即時更新。
* API 失敗時需要回復原本畫面或重新取得資料。
* 卡片列表與卡片詳情需要保持同步。

因此逐步導入 TanStack Query，用來管理從後端取得的伺服器資料狀態，例如資料快取、分頁載入、資料變更操作（mutation）與互動後資料同步。

TanStack Query 不取代 Axios；Axios 仍負責 API 請求封裝，TanStack Query 則負責管理 API 資料在前端的快取與同步。

Pinia 目前暫不作為核心工具，後續若有明確的全域 UI 狀態需求，再正式導入。

### 1. 2026.05.08 瀑布流卡片顯示資訊與排版

#### 待釐清需求描述：
瀑布流中卡片需要顯示哪些的資訊？哪些是重點？排版要如何設計？

#### 考量釐清：
* **卡片視圖**：Echo Gallery 的定位為建立起可以跨平台回顧收藏與個人輸出筆記的連結橋接平台。圖片、影音等多媒體資源不是儲存的重點，但在瀑布流中，仍然需要 notion gallery 視圖彈性，提供使用者可以依據偏好，自行選擇以文字為主還是圖片為主的卡片顯示方式。
* **內文長度**：考量到筆記卡片類型的內文長度可能較長，但瀑布流不能顯示太長內容。參考 twitter 或 threads 這種有字數限制的貼文卡片，可以透過下一篇貼文展開敘寫，但是本產品對「卡片」定位是一篇篇各自獨立的內容收藏，彼此之間並沒有轉發或回覆這種關聯性。因此，決議卡片需要再獨立出簡介欄位，再透過詳情頁承接長內容。參考 bilibili 的影片簡介區塊。
* **卡片重點**：不管使用者是否已經看過卡片內容、對卡片有沒有印象，收藏瀑布流的卡片顯示重點，應該要放在提醒使用者為何會選擇收藏這個內容。實際的完整內文或許不用在瀑布流顯示，但是新增「簡介」欄位是需要的，可幫助使用者快速回憶內容，「收藏理由」欄位更是需要的，這是整個產品核心。

#### summary、content、reason 區分：
* summary：給瀑布流看的簡短介紹，有字數上限。
* content：完整內容 / 長筆記。給詳情頁看的完整內容。
* reason：收藏理由。提醒使用者「當初為什麼存這個」。

優先顯示順序：reason > summary > content

> 因為在 Echo Gallery，最重要的是「為什麼這張卡值得再次出現？」

### 2. 2026.05.20 推播牆推播卡片的方式

#### 待釐清需求描述：
* 「今日看板」是否應該只顯示當天到期的卡片？考量到可能收藏夾裡的內容不多的情境，是否需要補上未來即將回流、過去已到期的卡片？
* 卡片只要出現在看板中，是否就代表使用者已經看過、應該自動更新卡片欄位 `nextShowAt`？還是需要設計「已回顧」按鈕，讓使用者逐張點選，以用來更新 `lastShownAt` 或 `nextShowAt`，使得卡片真的具備回流功能？

#### 考量釐清：

##### 1. `nextShowAt` 的定位：回顧卡片
卡片欄位 `nextShowAt` 為卡片下一次出現的日期。如果這個欄位小於或等於當日日期 (`nextShowAt <= today`)，就會出現在「今日看板」中。「今日看板」目的是讓使用者重新看見並回顧已到期的卡片。
##### 2. 已回顧的依據/更新 nextShowAt 時機：有效互動
* 不以「出現在推播牆」作為已回顧依據，避免：使用者可能根本沒有滑到該卡片、使用者可能只是快速略過而沒有真正閱讀、曝光判斷會引入額外複雜度 (如：重新 render 可能導致重複計算)。
* 不特地設計「已回顧」按鈕：這樣會讓 Echo Gallery 變得像待辦清單或 Anki 複習系統，增加使用者操作成本，也不符合產品想要建立的「輕量重新遇見」體驗。設計上不要求使用者逐張完成回顧，而是透過自然互動判斷卡片是否仍具有價值。
* 「已回顧」判斷方式：當使用者重新與卡片建立**有效互動**時，代表使用者重新接住這張卡片，卡片可以依照原本回流頻率安排下一次出現。
* **有效互動回顧**包含：
    * **查看卡片詳情**
    * **開啟連結類卡片連結來源**
    * **點擊星標**
    * **更新卡片內容**
> 註：此處為當時對「有效互動」的初步定義；後續第 3 點已重新釐清星標、開啟來源連結與查看詳情的互動語意，實作時以第 3 點為準。
* 第一版MVP就暫時不做後端自動更新回流時間的批次排程功能。
##### 3. 今日看板不只顯示當天到期卡片 (第一版MVP可能暫時不考慮)
* 如果推播牆只顯示當日到期的卡片，當收藏內容不多或當天到期卡片不足時，畫面可能會顯得空洞；但如果直接顯示未來才到期的卡片，又會削弱 `nextShowAt` 的意義，讓「回流日期」失去控制節奏的作用。
* 採用「回流優先，補充探索」的混合規則 (MVP 第一版可暫時先不做)：
    1. 優先顯示已到期回流卡片 (越接近今天，排序越前面)。
    2. 若數量不足，補上最近新增卡片。
    3. 若仍不足，補上隨機卡片。
* 這樣可以兼顧：
    * 回流機制的產品核心。
    * 推播牆不為空的使用體驗。
    * 內容重新發現的探索感。
##### 4. 過去到期卡片的處理方式：新增卡片互動
* 過去已到期但尚未互動的卡片，會自然符合`nextShowAt <= today`，因此會持續具備進入推播牆的資格。這樣可以確保使用者不會錯過已到期內容。
* 但若使用者一直不想互動，卡片可能長期堆積在推播牆中。因此需要提供卡片出口，讓使用者能夠主動處理不想立即互動的卡片，用來避免推播牆變成過期卡片堆積場。
* 新增卡片互動功能：「暫停回流」、「封存」、「稍後再看」功能。
#### 推播牆混合推播規則(第一版MVP暫時不做)
##### 1. 推播牆顯示優先順序
後續版本可採用以下推播牆顯示優先順序：
```text
1. 到期回流卡片：nextShowAt <= today，依 nextShowAt 由近到遠排序
2. 若數量不足，補最近新增卡片
3. 若仍不足，補隨機卡片
```
排除條件：
```text
1. 已封存卡片不進入推播牆
2. 暫停回流卡片不進入推播牆
3. 未來到期卡片不作為主推播內容
```
MVP 第一版暫時不考慮做固定比例混合流，例如 60% 到期、25% 最近新增、15% 隨機。
###### 第一優先：到期回流卡片
條件：
```ts
!card.isArchived &&
card.nextShowAt !== null &&
card.nextShowAt <= today
```
排序：
```text
nextShowAt 越接近今天，越前面
```
這樣可以讓推播牆保有「今日回流」的新鮮感，而不是變成處理 backlog 的任務清單。
###### 第二優先：最近新增卡片
如果到期回流卡片數量不足，則補上最近新增的卡片。已封存與已暫停回流的卡片，不會被補進推播牆。
```ts
!card.isArchived &&
card.nextShowAt !== null
```
###### 第三優先：隨機卡片
如果到期回流卡片與最近新增卡片仍不足，則補上隨機卡片。
隨機卡片同樣需要排除：
```ts
card.isArchived === true
```
以及：
```ts
card.nextShowAt === null
```
原因是：
* 已封存卡片代表使用者不希望它出現在主要流程。
* `nextShowAt === null` 代表卡片已暫停回流，不應再被推播牆主動顯示。

#### 新增卡片出口：暫停回流、封存、稍後再看
##### 暫停回流
暫停回流代表卡片仍存在於一般看板中，只是不再進入「今日看板」的推播。
```ts
// 資料狀態：
intervalDays = null
nextShowAt = null
```
##### 封存 `isArchived`
封存不是刪除，而是將卡片從主要推播牆與一般瀏覽流程中移出，不再參與回流。可能只出現在「已封存看板」或查詢頁。當使用者不需要再看到這張卡，但仍希望保留資料，不想刪除它，即可封存它。
```ts
// 資料狀態：
isArchived = true
```
##### 稍後再看 `snoozeCount`
稍後再看代表使用者不打算在本輪回顧回流的卡片，但是未來仍想再次遇見這張卡片，便可選擇透過稍後再看功能，讓卡片直接進入到下輪回流中，也避免過去到期但使用者不想互動的卡片持續堆積。
因此，稍後再看不代表使用者已完成回顧，而是代表使用者選擇短期延後這張卡片，所以也會更新 `nextShowAt`，但不視為有效回顧。
並新建欄位 `snoozeCount` ，代表這張卡被使用者點擊「稍後再看」的累積次數。
```ts
// 資料狀態：
snoozeDays = 3 // MVP 第一版暫定 3 天後再看
nextShowAt = today + snoozeDays // 更新下次顯示日期
snoozeCount += 1 // 代表被點擊「稍後再看」的累積次數
lastSnoozedAt = today
```
當一張卡被多次稍後再看，代表它可能不是單純「現在沒時間看」，而是使用者需要重新評估：
* 這張卡是否仍有價值？
* 是否需要更新內容？
* 是否應該暫停回流？
* 是否應該封存？
* 是否應該刪除？

MVP 第一版可先在單張卡片達到門檻 (如：`snoozeCount > 10` )時顯示提醒「這張卡已被多次稍後再看，建議重新評估是否仍有收藏價值。」。後續版本可再新增「待整理」看板，集中顯示 `snoozeCount` 達到門檻的卡片。

當使用者重新與卡片建立有效互動時，代表這張卡仍具有價值，可以重置 `snoozeCount`。
```ts
snoozeCount = 0
```
封存與刪除屬於清理型行為，不一定需要重置 `snoozeCount`。保留 `snoozeCount` 反而可以作為歷史訊號，表示這張卡可能是因為多次稍後再看而被清理。
`snoozeDays`：後續可再評估是否改為依照 `intervalDays` 或 `snoozeCount` 動態調整延後天數。
#### 卡片排程更新時機
> 註：以下為當時的初步排程規則；後續第 3 點已重新釐清星標、開啟來源連結、稍後再看與查看詳情的互動語意，實作時以第 3 點的「卡片互動與欄位更新暫定表」為準。
```text
有效回顧互動：
1. 查看詳情：重置 snoozeCount，依 intervalDays 更新 nextShowAt
2. 開啟連結：重置 snoozeCount，依 intervalDays 更新 nextShowAt
3. 星標：重置 snoozeCount，更新 likeCount，依 intervalDays 更新 nextShowAt
4. 更新卡片內容：重置 snoozeCount，視為使用者已重新整理卡片，可依 intervalDays 更新 nextShowAt
延後處理互動：
1. 稍後再看：snoozeCount + 1，短期延後 nextShowAt
2. 暫停回流：intervalDays = null，nextShowAt = null
清理型互動：
1. 封存：isArchived = true
```
#### 小結
卡片依照 `nextShowAt` 取得回流資格，但不因單純曝光而自動重新排程。只有當使用者產生有效回顧互動、選擇稍後再看，或執行暫停回流 / 封存等卡片出口操作時，系統才會更新卡片的回流狀態。其中「有效回顧互動」的實際定義與欄位更新時機，已於第 3 點重新整理。
後續可透過「到期回流 + 最近新增 + 隨機補充」的推播順序，讓 Echo Gallery 維持內容流動感；MVP 第一版可先以到期回流卡片為主，待資料量與使用情境確認後，再加入最近新增與隨機補充機制。
透過「稍後再看、暫停回流、封存」等操作，使用者可以整理不想立即互動的卡片，避免推播牆變成過期內容堆積場。

### 3. 2026.06.20 卡片互動方式與更新下次顯示欄位的時機

#### 待釐清需求描述：

* 原本規劃中，只要使用者與卡片產生互動，就可能代表使用者已經重新看見或重新接觸這張卡片，因此曾經考慮將點選星標、開啟連結類卡片來源、查看卡片詳情、點選稍後再看、更新卡片內容等行為，都視為更新 `nextShowAt` 的觸發時機。
* 但是在實際設計瀑布流互動時，發現「有互動」不一定等於「完成回顧」。不同互動背後代表的使用者意圖不同，如果全部都視為完成回顧，可能會造成不符合使用者預期的體驗。
* 因此，本次需求釐清的重點，是重新定義：什麼情境下才算使用者完成本輪回顧？哪些互動只是價值確認、來源查看、延後處理或清理卡片？

#### 需求與限制：

##### 1. 使用者體驗限制

Echo Gallery 的核心體驗不是讓使用者像完成待辦事項一樣逐張打勾，而是讓有價值的卡片以輕量方式重新出現在瀑布流中，讓使用者再次遇見它。

因此，卡片不能因為任何輕微互動就立刻從瀑布流中消失。

例如：

* 使用者在瀑布流中點擊星標，可能只是因為看到這張卡片後，再次肯定它的價值。此時使用者可能還想繼續點進卡片詳情，查看完整內容、收藏理由或筆記。如果點擊星標後卡片立刻消失，會造成使用者困惑。
* 使用者點擊連結類卡片的來源連結，可能只是想先回憶原始文章、影片或貼文內容。使用者仍可能希望回到 Echo Gallery 後，再查看卡片詳情，理解當初自己收藏這張卡片的原因。如果開啟來源連結後卡片立刻消失，也會造成使用者錯愕。
* 稍後再看代表使用者現在不想處理，但未來仍想再次遇見它，因此它是延後處理，不是完成回顧。
* 封存代表使用者想把卡片移出主要流程，是清理行為，不是完成回顧。

因此，MVP 第一版不應將所有卡片互動都視為完成回顧。

##### 2. 開發設計限制

目前 Echo Gallery 的看板仍以共用瀑布流元件為基礎。不同看板雖然有不同語意，例如今日看板、時間序看板、熱度看板、隨機看板、已封存看板、稍後再看看板與查詢結果，但它們在前端仍可能共用同一套卡片顯示與互動元件。

理想上，後續可以根據使用者是從哪一種看板進入卡片詳情，決定是否要更新 `nextShowAt`。

例如：

```text
從今日看板進入卡片詳情：
代表完成本輪回顧，更新 nextShowAt。

從時間序、熱度、查詢等其他看板進入卡片詳情：
可能只是瀏覽、管理或查找，不一定代表完成今日回顧。
```

但是如果 MVP 第一版就要精準區分不同看板來源，需要額外處理：

```text
1. 看板元件需要知道目前是哪一種 boardType。
2. 卡片元件需要知道自己是從哪一種看板被點擊。
3. 前端資料快取需要區分不同看板資料。
4. readCard API 需要只在特定看板情境下觸發。
5. 後端取得卡片詳情與更新回流狀態的責任需要進一步拆分。
```

這些設計較適合放在 MVP 後續版本逐步調整。

因此，MVP 第一版先採用較簡化的規則：暫時不完整區分看板來源，但仍先釐清不同互動的語意，避免星標、來源連結、封存等行為被錯誤視為完成回顧。

##### 3. MVP 第一版的簡化原則

MVP 第一版的目標是先完成 Echo Gallery 的核心閉環：

```text
卡片依照 nextShowAt 出現在看板
→ 使用者點進卡片詳情重新接觸卡片
→ 系統依照 intervalDays 安排下一次回流
→ 卡片未來再次出現
```

因此，MVP 第一版暫定：

> 使用者從未封存看板進入卡片詳情時，先視為完成本輪回顧，並更新 `nextShowAt`。

這是第一版的簡化設計，不代表最終版本一定會維持這個判斷。後續若看板語意與使用情境更明確，再進一步調整為「只有從今日看板進入詳情才算完成本輪回顧」。

#### 考量釐清：

##### 互動語意分類

* **完成本輪回顧**：查看卡片詳情

MVP 第一版暫時不完整區分看板來源，只要使用者從未封存看板點進卡片詳情，就先視為有效回顧。後續若看板語意更清楚，再調整為只有從今日看板進入詳情才更新 `nextShowAt`。

```ts
openCount += 1
lastOpenAt = now
lastInteractionAt = now
nextShowAt = now + intervalDays
```

* **價值確認**：點擊星標

星標代表使用者再次肯定這張卡片的價值，不代表使用者已完成本輪回顧。

```ts
likeCount += 1
lastLikedAt = now
likeAvailableAt = now + cooldownDays
lastInteractionAt = now

// 不更新 nextShowAt
// 不讓卡片立刻從看板消失
```

* **來源查看**：開啟連結類卡片的來源連結

開啟來源連結代表使用者想回到原始內容查看或回憶，不一定代表完成回顧。使用者可能仍希望回到 Echo Gallery 後查看卡片詳情與收藏理由。

```ts
// MVP 第一版不更新 nextShowAt
// 不讓卡片立刻從看板消失
```

* **延後處理**：稍後再看

稍後再看代表使用者現在不想處理這張卡，但未來仍想再次遇見它，因此是延後處理，不是完成回顧。

```ts
snoozeCount += 1
lastSnoozedAt = now
nextShowAt = now + snoozeDays
```

* **清理型互動**：封存

封存代表使用者想將卡片移出主要流程，不代表完成回顧。

```ts
isArchived = true
```

* **內容整理型互動**：更新卡片內容

更新卡片內容代表使用者重新整理這張卡片，可能屬於有效互動。

```ts
updatedAt = now
lastInteractionAt = now
```

但目前卡片更新欄位中可能也包含封存狀態，因此需要區分：

```text
內容整理型更新：可能算有效互動。
封存清理型更新：不算完成回顧，應走封存邏輯。
```

是否因更新卡片內容而同步更新 `nextShowAt`，後續再依使用情境調整。

### 4. 2026.08.04 卡片欄位結構重新設計與 OTPAR 思考框架引入

#### 待釐清需求描述：

* 實際使用 EchoGallery 一段時間後，發現回顧卡片時停留在「看看」的狀態，沒有促成有生產力的行動。
* 今日看板卡片持續堆積（總卡片 120 張，今日回流累積 20 張），回顧時常常只能模糊辨認出「這是我喜歡的、有價值的內容」，卻無法清楚說出當初為何收藏這張卡，也不知道該如何用自己的話表達出來。
* 原有欄位 reason / summary / content 在實際使用中界線模糊：建卡片時習慣把看到的內容全部複製貼入，想篩選金句卻難以取捨；最後常因字數限制才決定填哪個欄位，而非依照欄位本身的設計意圖填寫。回顧時又往往懶得把 content 全部看完，導致欄位設計的原本意圖未能發揮。
* 長期將 EchoGallery 當成文檔儲存庫使用，把 AI 對話紀錄、長篇筆記等完整內容直接塞入卡片欄位，混淆了「筆記軟體」與「回流工具」的定位。卡片應該儲存的是「這個內容如何影響了我、與我有何關係」，而非內容本身的備份。
* 思考是否引入 Digital Garden 概念或其他框架，提升卡片的思考深度與行動力。

#### 考量釐清：

##### 1. EchoGallery 的定位校正：回流工具，不是文檔儲存庫

原有使用方式將卡片當成內容備份的地方，把大段原文複製貼入 content，導致：
* 卡片變成「原文備份」而非「使用者與內容的關係」。
* 回顧時看到大段原文，懶得看完，回顧失去意義。
* 完整的 AI 對話紀錄、長篇筆記等，不適合直接塞入卡片欄位。

**正確定位**：卡片儲存的是「這個內容對我做了什麼」，完整內容存放於外部（Notion、HackMD、本地文件），卡片只作為那份關係的入口。

```text
建議做法：
長篇內容（AI 對話、閱讀筆記）→ 存外部，卡片只放連結與摘要
卡片欄位 → 填使用者自己的感受、解讀、想法
```

##### 2. 卡片性質分類

使用者的卡片天然分成幾種性質，不是所有卡片都需要往輸出方向走：

| 性質 | 例子 | 目的 |
|---|---|---|
| 自我理解型 | 生活覺察、八字解析 | 回顧自己、提醒自己 |
| 情緒補給型 | 搞笑內容、輕鬆連結 | 讓自己開心 |
| 素材儲備型 | 三國章節、金句 | 未來可能用到 |
| 觀念吸收型 | 產品思考、技術文章 | 內化後可能產出 |

只有「觀念吸收型」才真的適合往輸出方向走，其他三種回顧本身就是目的。

##### 3. Digital Garden 概念的引入與取捨

Digital Garden 是一種個人知識管理的概念，核心精神是「想法可以生長，不需要一次到位」。與傳統部落格的「完成才發布」不同，Digital Garden 強調內容從收藏到輸出是一個持續演進的過程，並以成熟度標示（種子 🌱 / 生長 🌿 / 成熟 🌳）來反映一則筆記目前的思考深度。

EchoGallery 的回流機制與 Digital Garden 的精神天然契合：卡片不是靜態的收藏，而是會隨時間重新出現、被重新接觸、逐漸被消化的內容。因此決定借用 Digital Garden 的成長狀態概念，但不全面引入其雙向連結、知識圖譜等複雜機制，只取最輕量的部分融入現有卡片結構：

* 以**成長狀態欄位**（🌱🌿🌳）標示卡片目前的思考深度，取代強迫每張卡片都要有完整輸出的壓力。
* 以**標籤**作為卡片之間的主題連結，不另外建立雙向連結圖。
* 卡片的「生長」體現在回顧時補充 think / plan / review 欄位，而非要求建立新的輸出文件。

###### 成長狀態欄位設計

新增獨立欄位 `growthStatus`，非必填、單選，用於標示卡片目前的思考深度：

```text
🌱 種子 → 只是收藏，還沒消化
🌿 生長 → 有想法，但還沒整理
🌳 成熟 → 已經內化，或已產出某個東西
```

成長狀態與欄位顯示的關係：
* 所有欄位在任何狀態下都可填寫，不強制鎖住。
* 🌿 生長時，plan 欄位在詳情頁主動顯示於前景。
* 🌳 成熟時，review 欄位在詳情頁主動顯示於前景。

> 設計原則：不用成長狀態「鎖住」欄位，而是用成長狀態「提示」欄位。避免使用者因為「還沒到🌿」而永遠不填 plan，錯失當下冒出的想法。

###### 標籤功能補強

* 新增標籤輸入下拉選單，讀取現有標籤供選擇，避免「心理」「心理學」「心理健康」等重複標籤持續累積。
* 標籤定位維持單一功能：**分類**。不將專案輸出目的或成長狀態混入標籤，避免標籤列表語意混亂。
* 完成下拉選單後，進行一次性標籤整理合併，不需事先設計完整分類體系。

##### 4. 引入 OTPAR 思考框架

OTPAR（Observe、Think、Plan、Act、Review）是一種「觀察—思考—計畫—行動—反省」的學習與解決問題框架。引入此框架的目的，是透過寫卡片練習把模糊的感受說清楚，提升思考與寫作的清晰度，而非強迫每張卡片都走完完整循環。

###### OTPAR 對應欄位設計

```text
Observe（觀察） → observe 欄位：客觀事實、背景脈絡、我看到了什麼
Think（思考）   → think 欄位：這個內容對我做了什麼、我的感受與解讀
Plan（計畫）    → plan 欄位：我想怎麼做、延伸想法
Act（行動）     → 行動發生在 EchoGallery 外部，不設獨立欄位
Review（反省）  → review 欄位：行動後的反省與結果紀錄
```

###### 新欄位結構定案

| 欄位 | 類型 | 必填 | 字數限制 | 定位說明 |
|---|---|---|---|---|
| title | VARCHAR | 是 | 255 | 快速回想這是什麼，可直接使用原始標題 |
| quote | VARCHAR | 否 | 500 | 最打動你的那一句話（金句佳句） |
| observe | VARCHAR | 否 | 1000 | 客觀觀察與事實、背景脈絡 |
| think | VARCHAR | 否 | 1000 | 個人想法與感受，這個內容對你做了什麼（原 reason 核心功能） |
| plan | VARCHAR | 否 | 1000 | 延伸想法、下次可以怎麼做 |
| review | TEXT | 否 | 無限制 | 行動後的反省與結果，可跨時間多次補充 |
| content | TEXT | 否 | 無限制 | 完整原文、長篇筆記、或不知道放哪裡的東西 |

> PostgreSQL 中 VARCHAR(n) 與 TEXT 效能幾乎無差異；字數限制的依據是業務邏輯上的填寫需求，而非效能考量。observe / think / plan 設定 1000 字，是為了讓填寫時感覺寬鬆，不因快到上限而打斷思考流程。

##### 5. 現有欄位對應關係（驗證期過渡方案）

### 5. 2026.08.16 從內容回流走向作品孵化的最小垂直切片

#### 背景與驗證目的

Echo Gallery 原有流程能讓收藏與想法重新出現，但「重新看見」不一定會自然變成具體輸出。本次新增的 Work 功能不把系統擴張成通用專案管理工具，而是驗證一個較小的產品假設：

> 讓 Card 可以自然進入一個或多個具體 Work，並區分候選素材與已採用素材，是否能提高舊內容最後成為作品一部分的機率？

此假設仍需透過實際使用觀察，不應視為已證實成果。

#### 目前產品模型

##### Card：可長期回流、重複利用的原子素材

Card 仍是 Echo Gallery 的核心資產，不直接隸屬單一作品。Card 可以持續回流、補充內容、調整成長狀態，並被不同 Work 重複使用。

Card 目前使用獨立的 `growthStatus`：

```text
SEED    🌱 種子
GROWING 🌿 生長
MATURE  🌳 成熟
```

資料庫欄位為必填，既有與新 Card 的預設值為 `SEED`；使用者可在 Card Detail 主動修改。成長狀態描述的是「卡片本身發展到哪裡」，不會因為 Card 被作品採用就自動改變。

##### Work：具體輸出或作品

Work 代表一個可以逐步完成的具體輸出，例如文章、軟體成果、短篇故事、影片、簡報或作品集 Case Study。

目前欄位包括：

```text
title
description     optional
status
externalUrl     optional
completedAt     optional
createdAt
updatedAt
```

Work status：

```text
IDEA / DRAFT / ACTIVE / DONE / ARCHIVED
```

新 Work 預設為 `IDEA`。進入 `DONE` 時記錄 `completedAt`；回到進行中的狀態時清除。`ARCHIVED` 表示保留資料的封存；低頻的永久刪除會刪除 Work、其更新與素材關聯，但不刪除原始 Card。作品內容可繼續寫在 HackMD、Notion、GitHub 或其他外部工具，Echo Gallery 透過 `externalUrl` 保存入口。

##### WorkCard：Card 與 Work 的顯式關聯

Card 與 Work 是多對多關係，透過顯式 join entity `WorkCard` 表示：

```text
Card   N <------> N   Work
          WorkCard
```

WorkCard 目前欄位：

```text
workId
cardId
status       CANDIDATE / USED
note         optional
linkedAt
usedAt       optional
```

關聯規則：

- 同一張 Card 可以加入多個 Work。
- 同一組 `(workId, cardId)` 不可重複，資料庫 unique constraint 是最後防線。
- `CANDIDATE` 表示可能使用；`USED` 表示已被該作品採用。
- `CANDIDATE → USED` 會設定 `usedAt`。
- `USED → CANDIDATE` 會清除 `usedAt`。
- 每個 WorkCard 的狀態彼此獨立。
- 移除 WorkCard 只解除關聯，不刪除 Card 或 Work。
- 封存 Work 不刪除 Card 或既有 WorkCard。
- 所有查詢與修改皆以登入使用者 ownership 隔離。

`note` 用來記錄「這張 Card 在這件作品裡為什麼有用」。資料模型與 API 使用 nullable 欄位；素材卡可直接新增、編輯或清除用途備註。

#### Card growthStatus 與 WorkCard status 必須獨立

兩種狀態描述不同維度：

| 狀態 | 描述問題 | 範例 |
| --- | --- | --- |
| `Card.growthStatus` | 這個想法本身發展到哪裡？ | `SEED / GROWING / MATURE` |
| `WorkCard.status` | 這張 Card 在某一件作品裡是否已被採用？ | `CANDIDATE / USED` |

合法組合例如：一張 `SEED` Card 已被 Work A 實際採用，因此 Work A 的 WorkCard 是 `USED`；同一張 Card 在 Work B 中仍可能是 `CANDIDATE`。系統不會自動把 `USED` 等同於 `MATURE`。

#### 第一版使用流程

##### 從 Work 整理素材

1. 從導覽進入作品列表。
2. 建立 Work，填寫名稱及選填的說明、外部連結。
3. 進入 Work Detail，從既有未封存 Card 中選擇素材。
4. 可用 Card ID 或標題模糊搜尋素材。
5. 新加入的 Card 預設為 `CANDIDATE`。
6. Card 被實際使用後切換為 `USED`，也可移回候選。
7. 可以編輯用途備註或解除關聯；Card 本身不會被刪除。

##### 從 Card 加入作品

1. 進入 Card Detail 查看「所在作品」。
2. 查看每個 Work 中的 `CANDIDATE / USED` 狀態。
3. 使用「加入作品」將 Card 加入其他尚未關聯、未封存的 Work。
4. 點擊關聯項目可前往 Work Detail。

目前前端不提供把 Card 加入封存 Work 的選項；後端尚未把「封存 Work 禁止新增素材」定義為強制 domain rule，需依實際使用再決定是否限制。

#### 本次明確不實作

- Project entity、Parent Work 或 Sub Work。
- Work type、分類與標籤。
- Work 素材拖曳排序、章節大綱或複雜 role taxonomy。
- 內建長文編輯器。
- 自動依 Card 欄位、WorkCard status 或互動紀錄調整 growthStatus。
- OTPAR 正式資料庫 schema 拆分。
- 熱度圖、Streak、今日創作桌與靈感碰撞。

1. 建立 Work 後，是否會自然把既有 Card 加入？
2. Card 回流時，「加入作品」是否比繼續補充大量文字更自然？
3. Work 聚集多張舊 Card 後，是否更容易開始創作？

### 6. 2026.08.23 卡片成長語意、主動查詢與限量回流調整

#### 背景與待解決問題

實際使用後發現，將每張新卡片預設為 `SEED`，容易讓「種子」從可選的整理提示變成所有卡片都必須持續培育的待辦；今日看板若直接顯示全部已到期卡片，也容易隨存量增加而形成無法清空的債務感。

本次調整的目的不是建立完整的卡片健康度或歷史流量分析系統，而是先完成三件事：

1. 讓成長狀態回到使用者主動賦予的語意，不要求每張卡片都持續成長。
2. 將 Today 從「全部到期清單」改為「有限、可繼續但不必清空的相遇批次」。
3. 補上可主動找回卡片的綜合查詢，讓尚未滿意的卡片不必只依賴 Today 再次出現。

#### 現行實作基準

調整前的 Today 會查詢所有未封存且 `nextShowAt` 早於明日零時的卡片，並以前端無限滾動分頁載入。卡片單純出現在看板上不會更新資料；只有從 Today 點進卡片詳情時，前端才會呼叫 read API，更新回顧紀錄並推進 `nextShowAt`。

因此，本節沿用「曝光不等於完成回顧」的核心原則，但把 Today 的取得方式改為限量批次。第 3 節中「從任一未封存看板進入詳情都算回顧」的早期決議，不再作為本次實作依據；主動搜尋、其他看板與直接開啟詳情都不應改變回流排程。

#### 成長狀態語意調整

`growthStatus` 保留在 Card 上，但新增 `UNMARKED`，並改為以下語意：

| 狀態 | 顯示 | 語意 |
| --- | --- | --- |
| `UNMARKED` | 不顯示成長標記 | 一般卡片，沒有額外整理承諾。 |
| `SEED` | 種子 | 使用者已察覺內容尚未滿意，想在之後主動補充或重寫。 |
| `GROWING` | 生長 | 內容正在持續發展。 |
| `MATURE` | 成熟 | 目前內容已相對完整。 |

調整規則：

- 新建 Card 預設為 `UNMARKED`。
- 既有 `SEED` 在 migration 中一次轉為 `UNMARKED`，避免把歷史預設值誤解為使用者的主動選擇。
- 既有 `GROWING` 與 `MATURE` 保持不變。
- Today 卡片可提供「標記種子」快捷操作，供使用者先記下不滿意的內容，之後再透過查詢找回。
- 切換成長狀態不算完成回顧，不更新 `nextShowAt`。
- 成長狀態不自動推導，也不影響 Card 是否到期或 WorkCard 的 `CANDIDATE / USED` 狀態。

#### 回流欄位責任

限量批次需要區分「卡片何時有資格回來」、「今天是否已提供過」與「使用者是否真的回顧」：

| 欄位 | 責任 |
| --- | --- |
| `intervalDays` | 完成回顧後，要間隔幾天再取得回流資格。 |
| `nextShowAt` | Card 下一次取得 Today 資格的時間。只有完成回顧、稍後再看或明確修改排程時才更新。 |
| `lastOfferedAt` | Card 最近一次被選入 Today 批次的時間，用於同日去重、公平輪替與辨識目前批次。可為 `null`。 |
| `lastOpenAt` | 最近一次從 Today 進入詳情並完成回顧的時間。欄位名稱沿用目前實作，畫面文案應表達回顧語意。 |
| `openCount` | 從 Today 完成回顧的累積次數。欄位名稱沿用目前實作。 |
| `lastInteractionAt` | 最近一次會影響互動排序的時間，維持既有用途。 |
| `snoozeCount` | 使用者執行稍後再看的累積次數；完成回顧後歸零。 |

`lastOfferedAt` 不取代 `nextShowAt`。前者回答「今天是否已經提供過這張卡片」，後者回答「這張卡片是否已到回流時間」。卡片被選入 Today 批次時只更新 `lastOfferedAt`；若此時就推進 `nextShowAt`，系統會把尚未發生的閱讀誤判成已完成回顧。

#### 限量回流流程

##### 今日第一批

1. 使用者在某個實際使用日第一次進入 Today。
2. 系統先確認當日是否已有目前批次；若有，重新整理仍回傳同一批。
3. 若沒有，從符合資格的 Card 中選出最多 5 張。
4. 同一批卡片寫入相同的 `lastOfferedAt`，作為目前批次識別。
5. 卡片只因被選入批次，不更新 `nextShowAt`，也不增加 `openCount`。

目前批次以當日最新一組 `lastOfferedAt` 辨識。後端先確認這組批次存在，再回傳其中仍到期且未封存的 Card；完成回顧的 Card 因 `nextShowAt` 已推進而從畫面消失，封存的 Card 也不再顯示，但兩種情況都不會自動補入新 Card。即使整批 Card 都已回顧或封存，系統仍視為今天已有目前批次，不會因回傳空列表而自動建立下一批。

##### 今天想多看一批

1. 使用者主動點選「今天想多看一批」。
2. 前端帶上目前批次的識別時間，避免連點或重複請求跳過多個批次。
3. 系統排除今天已被提供過的 Card，再選出最多 5 張並取代畫面上的目前批次。
4. 系統不會因使用者只開啟其中幾張、離開頁面或卡片離開可視範圍而自動補滿。
5. 當日已被提供過的 Card 不會在下一批重複出現；隔日只要仍到期，就可再次取得資格。
6. 若已沒有下一批，API 回傳空的 `cards`，不更新任何 Card；前端保留目前批次並顯示「今天沒有更多新卡片了」。重新整理後仍恢復目前批次。

##### 候選卡片規則

候選 Card 必須同時符合：

- 屬於目前登入使用者。
- 尚未封存。
- `nextShowAt` 不為 `null`，且早於明日零時。
- `lastOfferedAt` 為 `null`，或早於今日零時。

候選卡片優先選擇最久未被提供的項目；尚未提供過的 Card 視為最優先，再以現有回流時間與 Card ID 建立穩定排序。查詢只取得最多 5 張，不計算全部到期數量，也不要求使用者清空所有候選。

##### 使用情境

- 第一批有 5 張、使用者只開啟 2 張：2 張完成回顧並推進 `nextShowAt`；另外 3 張當天不重複出現，隔天仍到期時可重新參與輪替。
- 使用者多日未開啟系統：不會累積需要逐張清空的今日批次；下次實際進入時才選出最多 5 張。
- 使用者高頻率進入但都不開卡片：重新整理只看到目前批次；只有主動要求下一批才會繼續探索。未開啟卡片不會被誤記為回顧，也不會套用固定冷卻天數。
- 當日沒有更多候選：保留目前批次並顯示「今天沒有更多新卡片了」，不清空畫面、不顯示剩餘筆數，也不自動循環撈取同一批卡片。

#### 卡片互動與欄位更新

| 使用者行為 | `lastOfferedAt` | `nextShowAt` | 其他主要更新 |
| --- | --- | --- | --- |
| Card 被選入 Today 批次 | 更新 | 不更新 | 不算回顧。 |
| 從 Today 進入 Card Detail | 不更新 | 每次提供最多推進一次 | 首次回顧依 `intervalDays` 推進，更新 `lastOpenAt`、`openCount`、`lastInteractionAt`，並將 `snoozeCount` 歸零。 |
| 從其他看板、查詢或直接網址進入詳情 | 不更新 | 不更新 | 不算 Today 回顧。 |
| 稍後再看 | 不更新 | 依既有規則延後 | `snoozeCount += 1`。 |
| 星標或開啟外部連結 | 不更新 | 不更新 | 維持各自既有互動紀錄。 |
| 切換成長狀態或快速標記 `SEED` | 不更新 | 不更新 | 只更新 `growthStatus`。 |
| 封存 | 不更新 | 不更新 | Card 不再成為 Today 候選。 |

#### 卡片綜合查詢

查詢頁用於主動找回已知或想整理的 Card，第一版支援：

- Card ID 精確查詢。
- 標題文字模糊查詢。
- 一個或多個標籤，並可選擇 AND / OR。
- 一個或多個成長狀態。
- 依 `UPDATED_AT / CREATED_AT / NEXT_SHOW_AT / ID` 排序。
- 升冪或降冪。
- 後端分頁及總筆數。

Card ID 與其他條件同時存在時，仍需套用 ownership 與其他篩選，不得繞過使用者資料隔離。查詢結果進入詳情不算 Today 回顧。

標籤管理畫面仍負責建立、改名、刪除與檢視標籤；綜合查詢只負責用標籤找 Card，兩者不重複。Work 素材選擇器可維持較輕量的 ID / 標題搜尋，不要求在本次同步成完整查詢頁。

#### 配套修正

1. 修正 `snoozeCard()`：執行稍後再看時，除了更新 `nextShowAt`，還必須執行 `snoozeCount += 1`；完成回顧時維持歸零。
2. Card 回流與日界線計算改用注入的 `Clock`，避免 service 直接呼叫 `LocalDate.now()` 或 `ZonedDateTime.now()`，並以 Asia/Taipei 驗證 23:59、00:00 與跨日行為。本次不擴大修改到無關的 Work 時間欄位。
3. 右側欄移除「全部已到期卡片數量」，避免限量回流完成後仍以總欠債數字施加壓力；保留未封存卡片總數、`SEED / GROWING / MATURE`、作品與高 snooze 次數等摘要。
4. 右側欄不新增 `UNMARKED` 數量；`UNMARKED` 是無需處理的正常狀態，不應再次成為待辦指標。
5. 所有看板的 CardTextMode 統一不顯示 `nextShowAt`，避免同一張 Card 在不同看板呈現不同資訊層級；完整排程資訊保留在 Card Detail，並新增唯讀顯示 `lastOfferedAt`。

### 7. 2026.09.04 議事廳、議題推演與回流出口

#### 背景與待解決問題

本輪需求不是從「MVP 還缺一個專案管理模組」開始，而是來自一次閱讀《三國演義》官渡之戰後，對決策系統與個人日常治理的連續思考。

##### 從官渡之戰看到的不是單純智謀高下

如果只看結果，官渡之戰很容易被描述為曹操神機妙算、袁紹不斷犯錯；但站在當時視角，曹操曾正面受挫、被土山與地道壓迫、軍糧將盡，甚至考慮退回許都。許攸提供烏巢情報時，襲糧也不是毫無風險的標準答案，而是在「不行動同樣可能失敗」的局勢下作出的高風險決斷。

袁紹的問題也不只是沒有聰明人。田豐、沮授、許攸、張郃都曾提出重要資訊、反對意見或替代方案。真正的差異在於兩套決策系統如何處理：

- 不符合上位者期待的資訊。
- 壞消息與資源不足。
- 多個互相衝突的方案。
- 判斷錯誤時的風險與退路。
- 已經作出決斷後，是否能集中力量完成主要目標。

袁紹陣營不是沒有人知道可能怎麼贏，而是不同意見容易被轉譯成立場與忠誠問題，導致正確資訊無法進入決策；曹操則會讓荀彧、荀攸、許攸、張遼等人的不同判斷進入議事，最後由自己衡量局勢並承擔決斷。

因此，官渡之戰在本輪討論中被提煉為：

> 一個系統的差異，不只在於其中是否存在正確資訊，而在於它能否讓不同資訊進入議事，形成研判，轉化成決斷與行動。

##### 從組織決策映射到個人的內在治理

一個人的日常生活也不是只有一個清楚、統一且永遠理性的聲音。內在可能同時存在：

- 想改變生活的願望。
- 對安全與失敗的恐懼。
- 身體疲憊與注意力不足。
- 長期價值與短期舒適。
- 過去經驗形成的提醒。
- 外部環境、他人期待與社會比較。

這些聲音未必誰是假的。疲憊、焦慮、羨慕、厭倦與渴望都可能提供重要訊號，但訊號不等於命令；如果任何感受一出現就直接成為行動，第一層資訊便越過理解與權衡而取得決策權。反過來，若所有不符合既定意志的感受都被解釋成懶惰、逃避或不忠於目標，個人也會像袁紹陣營一樣，使重要資訊無法進入決策。

本輪因此形成對主體性的理解：

> 主體性不是永遠知道自己要什麼，也不是消滅矛盾，而是在內部眾聲喧嘩時，仍能主持這些矛盾，聽見訊號、形成研判並作出自己的決定。

##### 個人決策還受到糧草、地形與制度影響

官渡的比喻繼續映射到日常生活：

- 時間與精力像糧草。策略本身正確，不代表目前補給足以執行。
- 外部環境像地形。工具位置、手機干擾、通勤與工作環境會改變行動難度。
- 習慣與固定安排像制度。已反覆證明有效的決定若能制度化，就不必每天重新議決。

因此，「我今天不想做」可能表示補給不足，也可能只是環境讓另一種行為過度容易。自我理解的目的不是無止境分析，而是提高判斷品質：先辨認訊號，再看資源、限制與風險，最後才決定如何行動。

##### 從分層模型回看 Echo Gallery

上述思考可以整理成：

```text
【情報層】信息／訊號
我看見、感覺或遭遇了什麼？
        ↓
【謀略層】推演／研判
這些情報意味著什麼？
綜合局勢後，有哪些方針、方案與退路？
        ↓
【決策層】決議
整體性地綜合價值、資源與風險，
我現在選擇什麼？
        ↓
【行動層】行動結果
我採取行動後，現實如何回應這個決定？
        ↓
新的信息與下一輪判斷
```

目前 Echo Gallery 的核心能力集中在第一層：使用者曾經認可並收藏某份內容，系統避免它沉底，讓它在未來重新回到眼前。這個能力已經解決「收藏死亡」的一部分問題，但再次看見不保證內容會自然進入自己的理解、決定或生活。

現有 Card 主要是社群貼文、文章、影片、觀點、靈感與自建筆記。它們可以提供思想素材，卻不是完整的現實局勢。做出「是否轉職」之類的判斷時，還需要近期身心狀態、時間、財務、面試回饋與市場反應；這些一次性、情境性的資料通常不值得各自成為未來反覆回流的 Card。

因此不能把 Card 直接重新定義為完整情報，也不應把 Plan、Action、Review 與所有人生資料繼續塞進單張 Card。真正需要驗證的是 Card 與現實議題之間是否缺少一個中介層：

```text
Card
值得再次遇見的內容與思想素材
        ↓
議題
我此刻正在理解、推進或解決的事情
        ↓
議題更新
最近有何改變、現在怎麼看、接下來往哪裡走
```

現有 WorkCard 已能將多張 Card 聚合到同一個 Work，前端也曾將 Work 試驗性地呈現為「培育計畫」。本輪已替 Work 補上議題的整體欄位，但仍缺少一種低摩擦、可保留時間點快照的更新方式，讓使用者看見盤面如何變化，以及當時準備往哪裡走。

##### 本輪設計希望驗證的核心

議事廳不是要替使用者成為另一個曹操，也不是由系統自動判斷哪個聲音正確。它希望驗證：

1. 曾經珍視的內容重新回流後，是否需要被帶進一個正在面對的議題。
2. 外部思想素材與使用者當下的現實局勢能否在同一處被看見。
3. 每次更新只回答「最近有何改變、現在怎麼看、接下來呢」，是否比要求分類每一筆紀錄更容易持續使用。
4. 保存當時的改變、判斷與下一步，是否能避免之後重新從零開始焦慮。
5. 行動產生的結果，是否會自然進入下一次議題更新與研判。

因此，本次不將 Echo Gallery 直接定位為通用人生資料庫、專案管理工具或永久決策系統，而是準備一個最小且可回退的議事原型。只有真實使用中反覆出現價值，才考慮將它保留為 MVP 的長期功能。

#### Card 欄位語意

本輪不新增或搬移 Card 資料欄位，先統一現有 UI 文案：

| 欄位 | 最新 UI 語意 |
|---|---|
| `reason` | 為什麼留下它／我思我長 |
| `summary` | 我見我聞／內容重點 |
| `content` | 延伸筆記／完整內容 |

`reason` 同時承接收藏當下「為什麼留下它」，以及重遇 Card 時產生的個人省思、聯想、認同、反對與成長；來源原句或金句則放入 `summary` 或 `content`。Card Detail 與快速建立不再使用「我思我長／金句」、「Plan／Review／Content」或「行動與覆盤」等混合標示。特定議題的整體說明與時間性變化，分別由議題欄位與議題更新承接。

`growthStatus` 維持現有獨立語意，不因 Card 加入議題、WorkCard 變成 `USED` 或新增議題更新而自動更新。

#### 暫停與恢復回流

暫停回流是已確認需求：

```text
intervalDays = null
nextShowAt = null
```

暫停 Card 仍可由一般看板、查詢、標籤與議題開啟，但不進入 Today。恢復時由使用者重新選擇回流間隔，並以台北當日零時加上該間隔計算新的 `nextShowAt`。暫停與恢復不算 Today 回顧，也不修改回顧、稍後再看或成長狀態計數。

為避免一般 update API 無法清楚區分未傳值與刻意清空，後續實作優先評估明確的 pause／resume action API；實際 endpoint 於對應任務開始前確認。

#### 封存與取消封存

封存時只將 Card 排除於一般使用與 Today 候選，保留原本 `intervalDays` 與 `nextShowAt`。

取消封存時恢復封存前的回流狀態：

- 原 `nextShowAt` 已到期：可在下一次 Today 選批時成為候選。
- 原 `nextShowAt` 尚未到期：等待原日期。
- 封存前已暫停：取消封存後仍維持暫停。

取消封存不一律將排程重算成 `today + intervalDays`。

#### 議事廳與議題

現有 Work 的產品語意由「單一作品」與「培育計畫」進一步收斂為議事廳中的「議題」：

> 議題是一件需要持續匯集內容、補充現況、形成研判，並可能產生決議或成果的事情。

待驗證原型的候選畫面術語：

- 左側導覽與列表：議事廳。
- 一筆 Work：議題。
- 建立 Work：發起議題。
- Work Detail：議題詳情／議事頁。
- WorkProgressUpdate：議題更新。

「今日上朝」與「今日無事退朝」可作為帶有產品性格的輔助文案，但第一版不建立每日議事排程或待辦數字。

為控制 migration 風險，本輪暫時保留後端 `Work`、`WorkCard`、`works`、`work_cards`、`/api/works` 與 `/works` 等技術名稱。

#### 議題整體說明與概覽

議題本身負責保存較穩定、整體性且由使用者主動維護的說明。現有 Work 新增：

```text
objective
currentAssessment
outcomeCriteria
```

與既有欄位共同形成：

| 技術欄位 | UI 語意 |
|---|---|
| `title` | 議題名稱 |
| `objective` | 議題焦點 |
| `description` | 背景與脈絡 |
| `currentAssessment` | 整體研判 |
| `outcomeCriteria` | 結案／重議條件 |
| `status` | 議題狀態 |
| `externalUrl` | 相關連結 |

資源、限制、風險、選項與關鍵未知第一版不建立固定欄位，而是作為 `currentAssessment` 的選填思考角度。使用者需要引導時可主動展開提示，系統不因聚焦欄位而要求逐題填寫，也不在輸入框取得焦點時清空引導。只有真實使用中反覆需要獨立比較、搜尋或更新時，才升級為結構化資料。

`objective`、`description`、`currentAssessment` 與 `outcomeCriteria` 在 PostgreSQL 使用 `TEXT`，完整保存使用者輸入。前後端另設 50,000 字安全上限，目的只在攔截異常請求或意外貼入過大內容，不是建議使用者把思考壓縮成短文。畫面平常不持續顯示 `0 / 50000`；達到上限時再由輸入控制與驗證訊息阻止超額內容。

議事廳首頁使用全寬單欄議題列表，不讓跨議題動態永久占據主畫面。桌面版每張議題卡在同一卡片內分成左右兩區：左側以「議題焦點／結案或重議條件」呈現較穩定的整體資料，右側以具有清楚對比但不搶眼的底色呈現該議題最新一次更新的「最近有什麼改變？／現在怎麼看？／所以接下來呢？」。狀態放入左側內容頂端，右側不為全卡狀態預留空白；整張卡片可進入詳情，不另外顯示「查看完整議題與歷程」。行動版在同一卡片內改為上下排列。名稱最多三行、議題焦點最多五行，更新內容依實際溢位個別提供展開。左側標示議題資料自身的更新日期，右側只在確有近況時顯示近況日期，避免兩個日期來源混淆。列表 API 以衍生欄位 `latestProgressAt` 與最新一筆更新內容提供畫面快照；日期與排序取它和一般 `updatedAt` 中較新者，但不把更新內容複製進議題資料表。

主要範圍篩選維持「進行中／已完成／已封存／全部」。進行階段不是常駐的第二排控制項；使用者點擊「進行中」後，才以 Popover 浮現「所有階段／探索中／已釐清／推進中」，選取後在原按鈕顯示目前條件。跨議題近期動態降為次要入口，開啟 Drawer 時才載入最近 12 筆更新。每張議題卡的最新更新區提供「提出近況」快捷操作，直接開啟與詳情頁共用的近況 Dialog。

跨議題「近期動態」降為頁面上的次要入口，需要時才開啟 Drawer，且只有開啟後才查詢資料。第一版固定取得最新 12 筆更新紀錄，而非 12 個不同議題；同一議題的多次更新可以各自出現。每筆完整呈現三個可選欄位，長內容可個別展開。這項功能保留跨議題時間回顧的可能性，但不與各議題卡片競爭主畫面。

議題篩選使用兩層結構：第一層為「進行中／已完成／已封存／全部」生命週期範圍；點擊進行中時，第二層才以 Popover 顯示「所有階段／探索中／已釐清／推進中」。列表不再顯示「議題總覽」與「範圍」等可由畫面位置理解的提示文字。

議題詳情桌面版平均分成兩欄。左欄以白底連續面板承擔議題整體資訊：名稱、階段軌跡、議題焦點、整體研判、背景與脈絡、結案／重議條件、相關連結與時間資訊，並以分隔線建立閱讀層級。右欄使用灰底工作區，將「最近推進」與「參考素材」各自放入白色卡片；兩欄在桌面版可獨立捲動。可直接修改的階段下拉移至頁首，與「編輯議題」並列；左側軌跡負責理解整體進程。行動版才改為上下排列，不使用不適合探索型議題的百分比進度。

議題詳情頁提供低頻的「刪除議題」操作，必須先經確認對話框。`DELETE /api/works/{id}` 會永久刪除該議題、全部議題更新與 WorkCard 素材關聯，但不會刪除原始 Card；需要保留議題資料時應使用 `ARCHIVED` 封存狀態。

參考素材依 `CANDIDATE` 與 `USED` 分成兩個獨立分頁來源。每欄初始取得 10 筆，可各自載入更多；單次 `size` 最多 20。API 回傳 `items`、`page`、`size`、`totalElements` 與 `totalPages`，讓畫面顯示完整數量而不一次渲染全部素材。

建立議題時先只要求 `title`，並鼓勵填寫 `objective`；其他欄位可展開後補充。`objective` 的 UI 名稱為「議題焦點」，空狀態提示為「這個議題最需要回答、釐清或推進什麼？」。詳情閱讀以內容實際溢位為準提供「展開全文／收起」；議題焦點、整體研判、背景、結案／重議條件與相關連結各自提供聚焦編輯，避免每次修改一項內容都打開整份大型表單，同時保留完整編輯入口。

全站文字採共用語意階層，不再由各頁自行指定零散字級：頁面標題、詳情標題、區塊標題、卡片標題、重點、正文、操作、說明與 metadata 各有固定 token。根字級固定為 16px，中文正文為 15px、操作為 14px、metadata 不低於 12px；行動版只縮小頁面與詳情大標題，不再改變根字級。一般內容與 Element Plus 元件共用同一套系統字型。

#### 議題更新

2026.09.06 重新檢視成熟 Project UX 後，本輪不再要求使用者先判斷一筆內容屬於現況、研判、決議或結果。這種分類在概念上完整，但會把記錄近況變成分類工作，增加「這筆到底是哪一類」的摩擦。

第一版改為新增一種不需選擇類型、以時間點快照為目的的議題更新：

```text
WorkProgressUpdate
- id
- workId
- changeSummary
- assessment
- nextStep
- createdAt
- updatedAt
```

新增更新時以三個問題引導，欄位皆不要求逐一填滿，但至少需有一項內容：

| 技術欄位 | UI 引導 | 用途 |
|---|---|---|
| `changeSummary` | 最近有什麼改變？ | 保存新事件、回饋、結果、資源或限制的變化。 |
| `assessment` | 現在怎麼看？ | 保存此刻對變化的解讀、研判或暫時決定。 |
| `nextStep` | 所以接下來呢？ | 保存目前最值得推進的一個方向或動作。 |

`currentAssessment` 與更新中的 `assessment` 不互相同步：前者是使用者整體性、綜合性地維護的議題說明；後者是某個時間點的判斷快照。發布、修改或刪除議題更新時，都不回寫或覆蓋 Work 欄位。

議題詳情右欄初次只查詢最新五筆更新：第一筆完整顯示三個欄位，後四筆以時間軸只摘要「最近有什麼改變？」。這些更新不需要原樣複製到議題資料表；整體研判仍由使用者在左欄獨立整理。兩者並存，而不是彼此取代。

議題更新保留完整 CRUD：可新增、檢視、編輯與刪除。完整歷程改由 Dialog 顯示，只有開啟時才分頁查詢，每頁 10 筆；後端以 Slice 回應並將單次 `size` 限制在 20 筆，不為顯示總數額外執行 count query。編輯與刪除只影響被操作的更新；刪除最新一筆後，畫面改顯示剩餘更新中時間最新者，沒有更新時則回到空狀態。

`nextStep` 不是 Todo：第一版不提供完成勾選、截止日期、提醒、優先級、子任務或工作清單。議題首頁只呈現最新一筆更新中的 `nextStep`，用來回答「依據這次研判，現在準備往哪裡走」。若最新更新沒有下一步，不回頭擷取較舊更新，以免把已失效的方向誤認為現在的下一步。

#### 本輪原型明確不實作

- Card `currentInsight`、`cultivationIntent` 與 CardGrowthEntry。
- Garden、主題花圃與知識圖譜。
- 自動調整 Card growthStatus。
- 正式 Work／Project／Issue entity 與資料表更名。
- 真正 Work／Output 模組。
- 分類式 `WorkEntry` 與 `CONTEXT / ASSESSMENT / DECISION / RESULT` type。
- Work `nextAction` 欄位或獨立 NextAction entity。
- Task、Todo、完成勾選、截止日期與提醒。
- Project health、stale update 提醒與自動狀態推斷。
- 資源、風險、限制與選項的固定欄位。
- AI 自動研判或決策。

#### 驗證原則

本輪原型實作完成後，仍需以真實議題驗證，並依結果決定保留、縮減或回退：

1. 「議事廳／議題」是否比「培育計畫」更自然。
2. 議題焦點、背景與脈絡、整體研判、結案／重議條件是否能清楚分工。
3. 不分類的議題更新是否能自然產生，而不是增加填寫負擔。
4. 資源與風險是否真的需要獨立欄位。
5. 最新更新與整體研判同時顯示時，是否能兼顧即時性與整體性，而不造成重複感。
6. 單一 `nextStep` 是否足以促進行動，又不會將產品推向 Todo 管理器。
7. 一個議題是否會形成多個值得獨立管理的 Work。
8. 正式 domain migration 是否有足夠證據與價值。

如果議題更新沒有自然產生價值，可以移除議事廳導覽與候選文案、縮減議題欄位或撤回更新模組；完成原型不代表此功能永久納入 MVP。

完整資料模型、畫面設計、API 草案、相容性策略、任務拆分與驗收條件，見 [議事廳與議題推演產品設計暨實作追蹤](18_議事廳與議題推演產品設計暨實作追蹤.md)。

### 8. 2026.09.05 看板卡片情境資訊與議題入口

#### 待解決問題

各看板雖然具有不同目的，現行前端卻共用幾乎相同的 Card 外觀與更多選單。使用者能看見標題、單一文字預覽、標籤、星標與通用連結，卻不一定知道卡片為何出現在目前看板，也需要進入詳情頁才能暫停或恢復回流。稍後再看看板尤其缺少 `snoozeCount`，無法說明卡片已被延後多少次；其更多選單又繼續提供相同的「稍後再看」，與重新評估的看板目的相衝突。

#### 本輪實作原則

卡片維持共用骨架，但依看板顯示一條情境資訊，並只將該看板最重要、低風險的操作放在表面：

| 看板 | 卡片情境資訊 | 表面主要操作 |
|---|---|---|
| Today | 回流間隔與本次已到期 | 稍後再看 |
| 全部／查詢／標籤／幸運 | 回流中、已暫停與下次日期 | 沿用星標與來源 |
| 熱度 | 累積星標次數 | 沿用星標與來源 |
| 稍後再看 | 累積延後次數與下次日期 | 調整回流 |
| 已封存 | 封存前保存的回流狀態 | 還原 |

共用卡片另外調整：

- 顯示「筆記」或來源網域，不再只以抽象的「連結」辨識來源。
- 文字預覽標示「我思我長」或「內容重點」，並限制預覽行數。
- 未封存 Card 的更多選單提供加入議題、暫停／恢復回流與封存。
- 刪除一律需要二次確認。
- 已封存 Card 不提供星標或稍後再看，先還原後再回到主要互動流程。

#### 仍待驗證

1. 卡片新增情境資訊後是否更容易理解各看板用途，而不會顯得資訊過密。
2. Today 直接顯示稍後再看，是否能降低處理到期卡片的摩擦。
3. 稍後再看次數是否真的能協助清理，還是反而形成壓力。
4. 從 Card 直接加入議題是否比先進入詳情頁自然。
5. 已封存卡片停用星標，是否符合實際管理習慣。
6. 手機寬度下主要操作、Card ID 與更多選單是否仍能清楚排列。

### 9. 2026.09.20 實驗場與卡片衍生模型

#### 決策狀態與現行實作邊界

截至 2026.09.23，Experiment／ExperimentCard／CardRelation、`needsProcessing`、實驗場列表與詳情、種入卡片、長出新卡，以及 Card Detail 實驗脈絡皆已完成程式碼實作。正式領域命名為「實驗場／實驗主題／Experiment」，前端主要路由為 `/experiments`，後端主要 API 為 `/api/experiments`，資料庫目標名稱為 `experiments`、`experiment_cards` 與 `experiment_id`。

目前仍處於相容與部署驗證階段：`cards.growth_status`、`CardGrowthStatus`、舊查詢與操作仍存在；後端也暫時接受 `/api/gardens`、`/api/cards/{cardId}/gardens` 及舊 `garden*` response 欄位。資料庫 rename migration 必須在既有環境完成備份、執行與筆數核對後，才可視為完成上線。開發環境不可依賴 Hibernate `ddl-auto=update` 自動推斷 rename，否則可能同時產生新舊資料表。

2026.09.20 同時決定暫停並完整撤回尚未提交的回流與成長儀表板原型。撤回原因不是統計永遠沒有價值，而是該原型仍以資料庫存量與回流異常為主要組織方式，沒有充分協助使用者理解內容如何轉化、此刻為何值得注意，以及下一步可以做什麼。未來若重新設計監控或統計，必須建立在真實事件資料與已驗證的 Card、Experiment、議題使用流程上，不沿用本次畫面與指標設計。

#### 真實使用證據與待解決問題

議事廳已在求職心理卡點與策略調整的真實情境中產生以下行為：

1. 從一個明確議題出發，更新整體進度、最新近況與研判。
2. 基於新的醒悟建立心得 Card。
3. 將 Card 引用回議題素材池，保存推演依據。

這證明議事廳能承擔由上而下的思考：

```text
Question → Material → Reasoning → Judgment / Action
```

另一方面，現有 `growthStatus` 長期未能自然使用。實際被標記為 `SEED` 的 Card 主要來自兩種不同需求：

1. 來源可能失效，之後想把影片或文章內容完整整理進 Card。這是保存或整理尚未完成。
2. 內容令人心動，可能想模仿、擴寫、實踐或持續吸收。這是材料可能長出新理解或行動。

兩者不應繼續共用同一個 `SEED` 語意。前者描述 Card 本身是否待整理；後者描述 Card 在某個思考主題中是否具有發展潛力。

#### 核心產品決策

舊模型把一張 Card 視為一株植物：

```text
Card A：SEED → GROWING → MATURE
```

新模型改為讓成長主要發生在 Card 之間：

```text
Card A ─┐
Card B ─┼─→ Card D
Card C ─┘
```

Card A、B、C 可以繼續保留原始材料與當時理解；Card D 則保存它們共同促成的新想法、行動方法或較穩定理解。使用者仍可修正 Card 的錯誤或補充內容，但實驗場不要求透過反覆改寫同一張 Card 來證明它已升級。

因此，新的核心原則是：

> Card 是可回流、可重複利用的知識與經驗原子；實驗場讓多張 Card 在特定主題中被放在一起，觀察關聯，並長出新的 Card。

`SEED / GROWING / MATURE` 不再描述 Card 的全域成熟度，而改為描述：

> Card 在某一座 Experiment 中，目前扮演什麼培育角色。

#### 與其他模組的責任邊界

| 模組 | 起點 | 核心問題 | 主要結果 |
|---|---|---|---|
| Card | 一份外部內容、經驗或想法 | 什麼值得保存與再次遇見？ | 可回流的知識原子 |
| Today／看板 | 到期或主動探索的 Card | 現在要重新看見什麼？ | 注意力重新分配 |
| Tag | 分類需求 | 如何橫向找回相似內容？ | 查詢與分類 |
| 實驗場 | 一組令人心動或彼此相關的材料 | 這些東西放在一起會長出什麼？ | 新 Card、理解或行動線索 |
| 議事廳 | 一個需要理解或推進的問題 | 這件事現在怎麼看、怎麼辦？ | 研判、決議、下一步與更新歷程 |
| Work／未來成果模型 | 一個需要落地的產出 | 如何形成作品或實際成果？ | 可交付成果或外部行動 |

實驗場承擔由下而上的思考：

```text
Material → Pattern → Synthesis
```

議事廳承擔由上而下的思考：

```text
Question → Material → Reasoning
```

兩者都可以引用 Card，也都可能促成新 Card，但起點、使用動機與資訊組織方式不同，不應合併成同一個容器。

#### Experiment：實驗主題

Experiment 是一個由使用者建立、具有假設的實驗主題，例如「求職中的自我信任」、「生活幸福感」、「故事創作」或「手機與注意力」。它不是標籤的視覺替代品，也不是必須完成的 Project。

現行資料模型：

```text
Experiment
- id
- userId
- title
- hypothesis        optional at API level; current UI requires it
- description       optional
- themeColor        LEAF / LAKE / AMBER / LAVENDER / CORAL / MIST
- isArchived
- createdAt
- updatedAt
```

第一版規則：

- Experiment 必須屬於登入使用者。
- Experiment 可封存，封存只代表暫時不在主要列表出現，不刪除 ExperimentCard 或 CardRelation。
- Experiment 詳情提供永久刪除；刪除前必須確認，並移除該實驗主題的 ExperimentCard 與 CardRelation，但不刪除任何 Card 本體。
- Experiment 不設定完成率、截止日期、產量目標或健康分數。
- Experiment title 不作為 Tag，也不自動建立同名 Tag。
- 後端限制 title 255 字、hypothesis 2,000 字、description 5,000 字；空白選填文字正規化為 `null`。
- 使用者從六個預設色盤選擇識別色，不自由輸入 HEX，也不替三塊土壤分別選色。

現行索引：

```text
INDEX (user_id, is_archived, updated_at)
```

#### ExperimentCard：Card 在 Experiment 中的角色

Experiment 與 Card 是多對多關係，由顯式關聯實體 ExperimentCard 表示：

```text
Experiment   N <------> N   Card
             ExperimentCard
```

現行資料模型：

```text
ExperimentCard
- id
- experimentId
- cardId
- stage
- note              optional
- addedAt
```

`stage` 第一版沿用既有 enum 值以降低遷移成本，但 UI 語意調整為三塊可獨立存在的土壤：

| stage | UI 顯示 | 語意 |
|---|---|---|
| `SEED` | 種子土壤 | 令人心動、值得持續接觸，或可能成為新想法來源的材料。 |
| `GROWING` | 茁壯土壤 | 已由材料長出的新連結、暫時理解、方法或正在驗證的想法。 |
| `MATURE` | 成熟土壤 | 目前相對穩定、可說明、可使用或已形成明確影響的理解。 |

此欄位是 ExperimentCard 的情境角色，不是狀態機：

- 不要求一張 Card 依序走過三個 stage。
- 原始種子可以永久留在種子土壤。
- 新 Card 可以直接放入茁壯或成熟土壤。
- 同一張 Card 在不同 Experiment 可以具有不同 stage。
- 同一張 Card 在同一座 Experiment 第一版只能出現一次。
- 使用者可透過明確的「重新分類」修正 stage，但第一版不以拖曳升級作為主要互動。

`note` 用來記錄 Card 與特定 Experiment 之間的情境說明，例如「為什麼把它種在這裡」、「希望從它長出什麼」，或「它目前在這個主題中扮演什麼角色」。它不是 Card 內容或 Experiment description 的複本。

- `note` 使用 nullable `TEXT`，前後端限制 1,000 字。
- 使用者可新增、編輯或清空 note。
- ExperimentCard 重新分類時保留原 note。
- 同一張 Card 在不同 Experiment 可有不同 note。
- note 顯示於 Experiment 與 Card Detail 的實驗關係區，不顯示於一般 Card 看板。

現行約束與索引：

```text
UNIQUE (experiment_id, card_id)
INDEX (experiment_id, stage, added_at)
INDEX (card_id)
```

第一版不加入 `position`。手動排序只有在實際使用出現反覆需求後再加入。

#### CardRelation：保存新 Card 的思想來源

第一版只需要一種關係：

```text
DERIVED_FROM
```

現行資料模型：

```text
CardRelation
- id
- experimentId
- sourceCardId
- derivedCardId
- relationType       DERIVED_FROM
- createdAt
```

語意為：`derivedCardId` 是在指定 Experiment 中，由 `sourceCardId` 促成或衍生的新 Card。一張新 Card 可同時擁有多個來源，因此「從 A、B、C 長出 D」會建立三筆 CardRelation。

第一版規則：

- 來源與新 Card 都必須屬於目前登入使用者。
- 來源 Card 必須已在該 Experiment 中。
- `sourceCardId` 不得等於 `derivedCardId`。
- 建立新 Card、ExperimentCard 與全部 CardRelation 必須在同一個 transaction 完成。
- Experiment 封存、Card 暫停回流或 Card 封存都不刪除關係。
- 永久刪除 Card 時，相關 ExperimentCard 與 CardRelation 隨 Card 一併移除；刪除確認需清楚告知思想關係也會失去。

現行約束與索引：

```text
UNIQUE (experiment_id, source_card_id, derived_card_id, relation_type)
CHECK (source_card_id <> derived_card_id)
INDEX (source_card_id)
INDEX (derived_card_id)
```

第一版不為 CardRelation 增加 note，也不建立 `INSPIRED`、`EXPANDED_FROM`、`VALIDATED_BY`、`CONTRADICTS` 或 `APPLIED_FROM` 等分類。CardRelation 只保存可驗證的衍生來源，避免和 ExperimentCard.note 重複；只有當使用者確實需要區分關係，而且分類摩擦低於理解收益時才擴充。

#### 「待整理」與 ExperimentCard SEED 必須分開

「來源可能失效，之後想補完整內容」描述的是 Capture 尚未完成，不是思想種子。第一版以 Card 自身的輕量欄位承接：

```text
needsProcessing BOOLEAN NOT NULL DEFAULT false
```

UI 顯示為「待整理」。它與 Experiment 的差異如下：

| 維度 | 回答的問題 |
|---|---|
| `Card.needsProcessing` | 這張 Card 的保存或整理是否尚未完成？ |
| `ExperimentCard.stage = SEED` | 這張 Card 在這個主題中是否可能長出新的理解？ |

`needsProcessing` 正式納入第一個垂直切片：

- 新建 Card 預設為 `false`，不替使用者產生整理債務。
- 建立或編輯 Card 時可主動設定「待整理」。
- Card Detail 與適合的 Card 快捷操作可切換此狀態。
- Card Search 已新增「只看待整理」條件；舊的全域 growthStatuses 篩選暫留相容，待資料遷移與使用驗證完成後移除。
- Search API 以 nullable boolean query parameter 表示；未傳入時不限制，`needsProcessing=true` 時只回傳待整理 Card。
- 此欄位不影響 Experiment membership、ExperimentCard.stage、回流排程、封存或 WorkCard status。
- 既有 `SEED` 混有「待整理」與「思想種子」兩種意圖，migration 不可自動推斷哪些項目應轉為 `needsProcessing = true`；既有 Card 一律先採 `false`，由使用者重新標記真正待整理的項目。

#### 實驗場第一版資訊架構

第一版只建立兩層主要畫面：

```text
實驗場列表
└── 實驗場詳情
    ├── 種子土壤
    ├── 茁壯土壤
    └── 成熟土壤
```

實驗場列表提供：

- 建立實驗主題。
- 以名稱與假設為主要文字資訊；假設缺省時才回退顯示說明。
- 查看三個 stage 的 Card 數量與最近更新時間；統計膠囊使用實驗主題色盤，並支援亮色與暗色模式。
- 進入 Experiment 詳情。
- 透過「觀察中／已封存」篩選器切換範圍；列表卡片不重複顯示狀態 badge。
- 透過卡片右上角更多操作編輯及封存／恢復 Experiment。
- 桌面版每列兩張、窄螢幕與手機版改為單欄，避免橫向捲動。

Experiment 詳情提供：

- 將既有 Card 種入指定土壤。
- 檢視三塊土壤中的 Card。
- 顯示並編輯 ExperimentCard.note。
- 明確重新分類放錯的 ExperimentCard。
- 將 Card 從 Experiment 移除，但不刪除原始 Card。
- 選擇一張或多張 Card 執行「長出新卡」。
- 從新 Card 查看它長自哪些來源；從來源 Card 查看在這座 Experiment 中長出的 Card。
- 顯示假設與說明，只有內容超出預覽高度時才提供展開／收起。
- 操作列提供狀態切換、永久刪除與編輯，手機版採與議題詳情一致的滿寬狀態列加雙欄操作。

三塊土壤在視覺上應能清楚辨識，但不可設計成待辦 Kanban。畫面不使用進度箭頭、完成百分比、逾期顏色或「尚有 N 顆未成熟」等債務文案。

Card Detail 將 ExperimentCard 與 CardRelation 收在同一張「實驗主題與思想脈絡」資訊卡中，並以兩個語意獨立的子區段避免混淆：

```text
所在實驗主題
├── Experiment 名稱
├── stage
└── ExperimentCard.note

思想脈絡
├── 這張卡長自：source Cards
└── 這張卡長出了：derived Cards
```

「所在實驗主題」回答 Card 被放在哪個假設下觀察、扮演什麼角色以及為什麼放在這裡；「思想脈絡」回答 Card 從哪些來源長出，以及後來促成哪些新 Card。Card 可以只有 ExperimentCard 而沒有 CardRelation，例如單純放入種子土壤的外部文章；沒有任何衍生關係時不顯示空的思想脈絡區塊。

「種入卡片」與議題詳情的素材選擇流程共用 `CardPickerDialog`；「長出新卡」與全站快速新增共用 `QuickCreateCardDialog` 的卡片表單，並以左右分欄補上實驗場來源、土壤與備註設定。各彈窗由 `AppDialog` 統一處理水平／垂直置中、最大高度、單一內容捲動區與手機版滿寬收斂，避免視窗與彈窗同時出現不必要的雙重捲軸。

#### 「長出新卡」核心流程

1. 使用者在 Experiment 中選擇一張或多張來源 Card。
2. 點選「長出新卡」。
3. 建立畫面持續顯示來源 Card 的標題與必要摘要，協助使用者形成新內容，但不自動拼接來源全文。
4. 使用既有 Card 建立欄位填寫新 Card。
5. 選擇新 Card 要放入茁壯或成熟土壤，預設為 `GROWING`。
6. 儲存時以單一 transaction 建立 Card、ExperimentCard 與全部 `DERIVED_FROM`。
7. 原始來源 Card 保持原 stage，不因產生新 Card 而自動移動。

失敗時不得留下只有 Card、沒有 ExperimentCard，或只有部分 CardRelation 的半套資料。目前後端以單一 transaction 保證原子性，前端也會在 request pending 時停用重複提交；但 API 尚未提供 idempotency key，使用者若在前一個 request 完成後再次送出，仍會建立另一張新 Card。若未來需要網路重試保證，必須另行設計 request idempotency。

#### Archive、暫停回流與 Experiment 的正交關係

實驗場是思想關係與培育情境；Today 與其他看板是注意力配送。兩者不可互相推導。

| Card 狀態 | 是否留在 Experiment | Experiment 顯示方式 |
|---|---|---|
| 正常回流 | 是 | 正常顯示，可輔助顯示下次回流日。 |
| 暫停回流 | 是 | 顯示「已暫停回流」badge。 |
| 已封存 | 是 | 視覺稍微淡化並顯示「已封存」badge。 |
| 永久刪除 | 否 | 移除 ExperimentCard 與相關 CardRelation。 |

Experiment 查詢不得預設加上 `Card.isArchived = false`，也不得因 `intervalDays` 或 `nextShowAt` 為 `null` 排除 Card。Experiment 中的檢視、重新分類與長出新卡也不更新 `nextShowAt`、`lastOfferedAt`、`lastOpenAt`、`openCount` 或 `snoozeCount`。

#### 既有 growthStatus 的相容遷移

目前正式資料仍將 `growth_status` 存在 `cards`，而正式環境使用 `ddl-auto=validate`。新模型必須採 additive migration，不可只修改 Entity 或依賴本機 `ddl-auto=update`。

建議部署順序：

1. 備份正式資料庫，記錄 Card 總數與各 growth status 筆數。
2. 歷史 additive migration 在 `cards` 新增 `needs_processing BOOLEAN NOT NULL DEFAULT false`，並以當時的 Garden 命名建立主題、membership、`card_relations`、foreign key、unique constraint 與索引。
3. 對每位至少有一張非 `UNMARKED` Card 的使用者，建立一座「待重新整理（舊成長狀態）」Experiment。
4. 將該使用者的 `SEED / GROWING / MATURE` Card 依原值建立 ExperimentCard。
5. `UNMARKED` 不建立 ExperimentCard，因為它表示使用者沒有賦予額外培育意圖。
6. 以 unique constraint 與存在性檢查確保 migration 可重複執行。
7. 比對 migration 前後各使用者與各 stage 筆數，確認沒有遺失或重複。
8. 停止後端，執行 Garden → Experiment rename migration，將資料表、關聯欄位、索引與約束改為 `experiments`、`experiment_cards`、`experiment_id`。
9. 核對 rename 前後筆數，再部署以 `/api/experiments` 為正式 contract、同時保留舊 Garden alias 的相容後端。
10. 完成前端切換後停止新增舊流程資料；經過實際資料驗證與回退觀察期，再以獨立 migration／任務移除 growthStatus 與 Garden 相容層。

遷移 Experiment 的名稱必須清楚表達它只是舊資料入口，不代表系統已正確判斷每張 Card 的主題。使用者可之後把 Card 種入真正 Experiment，再從遷移 Experiment 移除。系統不可將舊 `SEED` 自動轉為 `needsProcessing`，也不可自行替 Card 建立主題 Experiment。

#### API 現行範圍

目前已實作的第一版範圍如下：

```text
GET    /api/experiments
POST   /api/experiments
GET    /api/experiments/{experimentId}
PUT    /api/experiments/{experimentId}
PUT    /api/experiments/{experimentId}/archive
PUT    /api/experiments/{experimentId}/restore
DELETE /api/experiments/{experimentId}

GET    /api/experiments/{experimentId}/cards?stage=SEED&page=0&size=10
POST   /api/experiments/{experimentId}/cards
PUT    /api/experiments/{experimentId}/cards/{cardId}/stage
PUT    /api/experiments/{experimentId}/cards/{cardId}/note
DELETE /api/experiments/{experimentId}/cards/{cardId}

POST   /api/experiments/{experimentId}/grow

PUT    /api/cards/{cardId}/processing-status
GET    /api/cards/search?needsProcessing=true
GET    /api/cards/{cardId}/experiments
GET    /api/cards/{cardId}/relations
GET    /api/cards/{cardId}/experiment-context
```

`POST /api/experiments/{experimentId}/grow` 的 request 至少包含：

```text
sourceCardIds
stage
Card 建立所需欄位
```

此 API 必須完成 ownership 驗證、來源 membership 驗證、Card 建立、ExperimentCard 建立與 CardRelation 建立。第一版不讓前端以多次獨立 request 拼裝流程。

ExperimentCard.note 的更新 request 使用 nullable／可空白的 `note`，後端正規化空白內容為 `null`；`processing-status` 使用明確 boolean request，避免以一般 Card update 的欄位缺省語意猜測使用者是否要清除待整理狀態。Card Detail 使用獨立的 `experiment-context` 唯讀查詢一次取得 memberships 與雙向 relations，避免一般 Card detail response 永遠載入不需要的關聯資料；原本分開的 experiments／relations endpoint 暫時保留。

命名相容期間，`/api/gardens/**` 與 `/api/cards/{cardId}/gardens` 對應至相同服務，response 也暫時保留 `gardenId`、`gardenTitle`、`gardenHypothesis`、`gardenArchived` 與 `gardens`。新前端只使用 Experiment 命名；舊 alias 待已部署客戶端與資料驗證完成後再另案移除。

新模型不只增加一個 menu。部分整合已完成，但舊 `growthStatus` 相容功能尚未全面退場：

|---|---|

#### 效能與資料量原則

Experiment、ExperimentCard 與 CardRelation 是一般關聯式資料，符合 PostgreSQL 的常見使用方式。個人長期使用情境下，資料表增加本身不是主要效能風險；需要控制的是每個畫面一次讀取的 row 數與不必要的大型 Card content。

第一版遵循：

- Experiment 列表只回傳摘要與聚合數量，不載入所有 Card。
- Experiment 詳情的三個 stage 分別分頁或限量載入，不一次傳回整座 Experiment 的全部 Card。
- Card 摘要查詢不載入不需要顯示的長篇 `content`。
- ExperimentCard 以 EntityGraph 同批載入 Card 與 tags，避免逐卡 N+1；列表的三種 stage 數量由單一聚合查詢取得。
- CardRelation 的 Experiment、來源 Card 與衍生 Card 以 EntityGraph 載入，並以 `sourceCardId`、`derivedCardId` 索引支援雙向追查。
- 所有查詢先以 Experiment ownership 限縮，不把全使用者資料載入 JVM 或瀏覽器後再篩選。

例外是開啟「長出新卡」時，前端目前會分頁載入該實驗主題三塊土壤的所有 Card，供使用者選擇來源；此載入不會發生在一般詳情初始畫面。若單一實驗主題未來成長到大量 Card，應改為可搜尋的後端分頁來源選擇器。

第一版不需要 Redis、Elasticsearch、圖資料庫或背景聚合工作。若未來單一 Experiment 有數千張 Card，再依實際 query profile 評估 keyset pagination、summary projection 或快取。

#### 第一版明確實作範圍

第一個垂直切片只驗證：

1. 建立、編輯、封存與查看 Experiment。
2. 將既有 Card 種入某座 Experiment 的指定 stage。
3. 新增、編輯、清空並顯示 ExperimentCard.note。
4. 在 Experiment 詳情分區查看三種 stage。
5. 重新分類或移除 ExperimentCard。
6. 從一張或多張來源 Card 長出新 Card。
7. 在 Card Detail 分開查看所在實驗主題與雙向思想脈絡。
8. 保存並查看 `DERIVED_FROM` 關係。
9. 以 `needsProcessing` 標記待整理 Card，並從 Search 篩選找回。
10. 保留封存或暫停回流 Card 的 Experiment membership。
11. 安全遷移既有非 `UNMARKED` growthStatus。

#### 第一版明確不實作

- 儀表板、Experiment 健康分數、成熟率與產量 KPI。
- 種子逾期、未成熟警告或強迫處理提醒。
- 自動推薦 stage、自動成熟或依互動推導 ExperimentCard。
- AI 聚類、自動摘要或自動產生新 Card。
- CardGrowthEntry、培育日誌與單卡成長時間軸。
- ExperimentCard 拖曳排序、自由畫布與完整知識圖譜。
- `DERIVED_FROM` 以外的複雜關係 taxonomy。
- Soil 獨立 entity 或三張 soil 資料表。
- Experiment 截止日期、任務、完成勾選與 Project Management。
- 同步重新命名現有 Work／議題後端 domain。
- 以 Experiment 操作自動改變回流排程、封存或 WorkCard status。

#### 第一版驗收條件

功能驗收至少包括：

1. 同一張 Card 可加入不同 Experiment，且具有不同 stage。
2. 同一張 Card 不可重複加入同一 Experiment。
3. ExperimentCard.note 可新增、編輯、清空，重新分類後仍保留，且不同 Experiment 的 note 互不影響。
4. 原始種子長出新 Card 後仍保持原 stage。
5. 新 Card、ExperimentCard 與多筆來源關係建立成功，任一步失敗時全部回滾。
6. Card Detail 能分辨 ExperimentCard 歸屬與 CardRelation 衍生關係，並雙向進入來源或衍生 Card。
7. `needsProcessing` 可獨立切換；Search 未套用條件時不影響結果，套用「只看待整理」後只回傳 `true` 的 Card。
8. Experiment 顯示已封存與暫停回流 Card，但不使其重新進入 Today。
9. Experiment 與待整理操作不改變任何回流、回顧、星標或稍後再看欄位。
10. 使用者無法讀取或操作其他使用者的 Experiment、ExperimentCard、Card 或 CardRelation。
11. 舊 `SEED / GROWING / MATURE` 資料完整進入遷移 Experiment，`UNMARKED` 不被誤建成培育項目，也不自動轉成待整理。
12. Experiment 列表與詳情在空資料、少量資料、分頁及行動版寬度下都能正常操作。
13. 實驗場功能退出或 Experiment 封存時，不影響原始 Card、Tag、Today 與議事廳資料。

#### 上線後需要驗證的產品假設

第一版完成只代表具備觀察條件，不代表實驗場永久成立。至少需要驗證：

1. 使用者是否會自然建立不只一座 Experiment，而不是只用 Tag 或議題替代。
2. 把相關 Card 放在一起，是否真的提高新 Card、理解或行動產生的機率。
3. 「長出新卡」是否比修改原 Card 更符合實際思考習慣。
4. 三塊土壤是否幫助理解 Card 的角色，還是再次造成隱性升級壓力。
5. 同一 Card 在不同 Experiment 使用不同 stage 的情境是否真實發生。
6. 使用者是否會回看 Card 的思想來源，而不只是建立後忽略關係。
7. 封存與暫停回流 Card 保留在 Experiment 是否確實有價值。
8. 「待整理」是否會被自然使用並透過 Search 找回，而不會再次形成未處理債務。
9. Experiment 是否與議事廳形成互補循環：Experiment 長出 Card，Card 進入議題；議題醒悟再沉澱 Card，Card 回到 Experiment。
10. Experiment 提供的價值是否無法由 Search、Tag、Card Detail 與議事廳的組合輕易取代。

若使用者只把 Experiment 當成另一種 Tag、長期不會長出新 Card，或三階段再次形成心理債務，應縮減或撤回主導覽入口，保留可重用的 CardRelation 或關聯資料，而不是為了已投入開發成本繼續擴張功能。

### 10. 2026.09.26 資訊轉化觀測台 Mock 驗收與正式 V1 規劃

#### 與已撤回儀表板的界線

2026.09.20 撤回的是以到期量、成長狀態、異常量與健康度為中心的舊式儀表板原型；該決策仍有效。2026.09.26 確認的「資訊轉化觀測台」不是把舊儀表板重新上線，而是讓使用者看見內容目前如何被安放、近期留下哪些轉化線索，以及哪些具體內容值得重新觀看。

它不得顯示成熟率、完成率、健康分數、逾期壓力、行動轉化率或紅黃綠績效燈號。nextStep 是可帶往現實參考的方向，不是 Todo。

#### 已確認的正式 V1 範圍

第一版由兩層構成：

```text
資訊轉化觀測台概覽
├── 現在的系統
├── 回看近期（近 7／30／90 天）
├── 最近長出的內容
├── 現在可以往前走
└── 值得看一眼

卡片與回流
├── 卡片目前狀態
├── 回流週期分布
├── 未來一週回流預覽
├── 累積稍後再看分布
└── 明確的維護與排程訊號
```

概覽的期間切換只影響近期觀測；卡片與回流頁描述的是 current stock 與未來排程，不能被誤讀為某段期間的績效。

每個正式顯示的數字必須能 drill-down 到具體 Card、Experiment 或 Work，並讓使用者知道該資料為何被納入。若現有資料無法可靠回答某個歷史問題，第一版不應以推測數字呈現；是否建立 ActivityEvent 要等真實使用證據，而不是為了補齊圖表而預先建立。

正式實作的詳細 Metric、API、Search 篩選與效能規劃，以 `21_資訊轉化觀測台產品設計暨實作追蹤.md` 為準。

### 11. 2026.09.26 實驗場探索循環正式化

實際使用顯示，只有「種入卡片」與「長出新卡」仍要求使用者先知道成果應該長什麼樣，無法承接一個尚未成形、只適合先做小嘗試的方向。因此實驗場新增一個低摩擦探索循環：

```text
目前試法
  ↓
留下發現（可選擇是否連同試法保存）
  ↓
形成探索紀錄
  ↓
選取一筆或多筆紀錄整理成新 Card，或追加至實驗場中的既有 Card
```

探索資料正式保存於後端，不再使用瀏覽器 Local Storage。舊原型資料不匯入，也不再讀取。每個 Experiment 可保存一個目前試法、最多三個常用試法與多筆探索紀錄；最近使用過的三個試法由探索紀錄推導，不另存重複資料。

探索紀錄整理成新 Card 時，系統在同一筆交易中建立 Card、將它加入目前 Experiment 的 `GROWING` 階段，並保存紀錄與 Card 的關聯。這類 Card 沒有來源 Card，因此不建立 `CardRelation`，也不計入觀測台的「由既有內容長出」。它會被視為「探索整理後進入實驗場的材料」。

同一筆探索紀錄可整理至多張 Card，多筆探索紀錄也可共同整理至同一張 Card。刪除探索紀錄會連帶刪除其 Card 關聯，但不刪除已建立或已追加內容的 Card；刪除 Card 只會移除對應關聯；刪除 Experiment 則會刪除探索狀態、探索紀錄與關聯，但仍保留 Card 本體。

實驗列表不增加新的資訊列或卡片尺寸。既有時間文案改為「最近活動」，實驗主題、種入／移除材料、階段與備註、衍生新卡及探索異動都應更新該時間。資訊轉化觀測台維持以下界線：

- `CardRelation(DERIVED_FROM)` 才屬於生成性與「最近長出的內容」。
- 沒有來源關係的 ExperimentCard 屬於「近期進入實驗場的材料」。
- 由探索紀錄整理出的 Card 在材料清單標示為「探索整理」。
- 期間活動可顯示「留下探索發現」，但目前試法與常用試法不是成果，不納入活動數。

「目前想試」屬於不受 7／30／90 天影響的 current state，而不是期間績效。實驗列表在既有摘要位置優先顯示目前試法；資訊轉化觀測台則在「系統現在的狀態」下方顯示最多三個未封存實驗的目前試法，點擊後回到實驗詳情。沒有目前試法時不顯示該區塊。
