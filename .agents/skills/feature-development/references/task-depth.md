# 任務深度與階段選擇

本文件只在需要細化「完整開發／局部修改／承接已有計畫」時讀取。不要把以下範例當成固定必跑步驟。

## 完整開發

適用：新的獨立使用者流程、前後端契約協調、跨卡片／實驗／探索線／作品／奇珍的關係修改、重要資料語意／權限改動、跨多頁 UI 設計。

1. ①從使用者對話或需求文件擷取目標、已確認／被推翻／未決事項。以較新的明確決策為準；不要把所有 AI 建議當成要求。
2. ②有針對性地核對 router／view／component、API client／types、controller／service／repository、資料庫關聯與測試。只讀直接受影響及必要相依檔案。
3. ③涉及 UI 時按獨立使用者任務找可參照的**元件或整段流程**，列出沿用、調整、新增，並說明選用理由與差異。
4. ④提供可核准的實作計畫：行為與資料契約、前後端變更、風險、必要測試、尚未核准的選擇；此處停止等待授權。
5. ⑤在授權範圍內逐項實作並驗證。若後續發現重大缺口，回到必要階段，不從頭重做全部。
6. ⑥以精簡結果回報，實際 UI 使用感受交給使用者驗收。

## 局部修改

適用：明確的元件排版、局部文案、既有已定位錯誤、使用者提供截圖圈選的修正。

- ①一句話確認指定問題與成功條件；②只讀目標元件與直接依賴；③ UI 任務只比對相關模式；④提出精簡變更範圍（必要確認依 `AGENTS.md`）；⑤修改並執行必要測試；⑥簡短回報與需要人工確認的內容。
- 非 UI 任務直接略過③；僅技術討論或設計時略過⑤；若使用者已提供核准方案，直接承接已有決策並核對目前程式。
- 局部修改不能藉「小」之名擅自變更權限、API、資料結構、草稿保存語意、刪除後果或跨模組共用樣式；發現影響範圍擴大時重新分類並說明。

## 僅規劃／僅分析／已核准後續開發

| 當次請求 | 要做 | 不要做 |
| --- | --- | --- |
| 「貼上我們的對話，請幫我設計」 | ①②③④，辨識決策狀態，輸出可審閱方案 | 未核准就進入⑤；為了交付草圖去寫新 demo |
| 「方案已確定，幫我盤點如何實作」 | ①輕量，②③④ | 重新設計已核准產品行為 |
| 「照剛才核准的計畫開始開發」 | 核對計畫與當前程式相容，⑤⑥ | 重做①～④或逐檔詢問 |
| 「檢查詳情頁是否一致」 | ②③，只分析 | 自動改全站 UI |
| 「依截圖修正一個按鈕」 | 局部的②③④⑤⑥ | 全站重構、大量截圖、自製 HTML |

## 跨對話承接

若上一輪規劃在別的對話中且無法取得：使用者可貼核准摘要或提供既有設計文件。需要時用短摘要保留「任務、已核准決策、相關檔案、未決風險、下一步」，**不為每輪強制建立實體交接檔**。核對原始碼後才能將舊計畫用於新版本。
