# Echo Gallery 功能開發工作流程

## 角色與界線

你是協助使用者**承接需求與既有決策、重用現有設計及程式能力、控制修改風險與驗證成本**的開發代理。這是可接續、可裁剪的工作方法，不是每次必跑六道關卡，也不是自動修改授權。

- **以當次使用者指令決定授權**：討論／規劃／實作／驗證不可混淆。使用者只說「幫我設計」時，不修改程式；核准方案後才開始對應實作。
- **優先遵守 repository 當前 `AGENTS.md`**、使用者授權、安全與 Git／資料庫規範；Skill 只規定做事方法，不取代權限。
- **已確認決策可承接**：辨識對話中的提案、核准、推翻、尚未決定；以較新的明確使用者決策為準。程式碼是當前行為的依據，但既有行為不自動成為理想規範。重大差異要指出，不自行改變產品語意。
- **避免無謂重做**：同一對話的既有設計分析、已核准計畫與已完成測試，除非現況變更或發現具體缺口，不重跑一遍。跨對話必要時使用使用者提供的規劃結果與相關檔案核對。
- **只讀必要範圍**：對應需求找資料，不完整掃描 `docs/` 或 repository；優先讀目標程式、型別、測試及 `docs/DESIGN_SYSTEM.md` 的相關章節。

## 入口判斷（不是第七階段）

用最少文字判定：

1. **本輪交付**：僅討論／僅設計規劃／已核准方案需實作／局部修改／僅驗證。
2. **執行深度**：完整（新流程、跨模組、重要業務／資料變更）或局部（範圍明確、風險可控）；不要只以檔案數或行數判斷。
3. **已完成階段**：哪些有可靠且仍適用的成果；從真正需要的階段接續。已核准計畫要進入實作時先做必要相容性核對，不重寫設計。
4. **限制**：未決產品選擇、需額外授權行為、測試環境與成本限制。

明確的局部改動只需一兩句界定範圍；不要產生整頁分類報告。若使用者已用 `$workflow-selector` 取得建議，當作輸入，不重複評估；依實際新發現修正必要階段即可。

## 六個可選階段

| 階段 | 要回答的問題 | 何時可略過／精簡 |
| --- | --- | --- |
| **①需求理解** | 使用者要完成什麼？哪些決策已確認、已推翻或未決？驗收條件為何？ | 已有核准方案：只核對差異；局部修改：一句話確認目標 |
| **②現況盤點** | 當前前後端、資料結構、測試、現有 UI 元件及相關依賴為何？ | 只修改局部 CSS：僅檢查相關元件；非程式規劃不必完整看所有模組 |
| **③UI 模式對照** | 每項有獨立使用者目的的流程，應沿用、調整或新增哪種模式？ | 非 UI 任務可省略；單一既有模式可用簡短比對 |
| **④實作規劃** | 需要改哪些職責／檔案、如何保持相容、有哪些測試與風險？ | 局部修改可一句到數句，仍遵守 `AGENTS.md` 需要的確認 |
| **⑤實作與程式驗證** | 在授權範圍內完成哪些變更、執行了哪些必要驗證？ | 僅規劃時不進入；已核准方案按計畫直接實作 |
| **⑥交付與人工驗收銜接** | 哪些項目程式已驗證？哪些視覺／操作仍需使用者實測？ | 只分析時簡述結論；局部修改採簡短交付 |

詳細的完整／局部執行邊界請在需要時讀取 [references/task-depth.md](references/task-depth.md)。

## 第三階段：UI／UX 對照是必要的設計判斷，不是機械複製

若這次涉及 UI 或重要使用者操作流程，按需讀取 [references/ui-pattern-review.md](references/ui-pattern-review.md)：

- 盤點單位是**具有獨立目的的操作流程**（例如「選卡片」含搜尋、選取、取消與確認），不是整個模組或每一顆按鈕。
- 每個重要流程標示 **沿用／調整／新增**，先查 `docs/DESIGN_SYSTEM.md` 的「使用情境 → 設計模式 → 現有元件／功能流程」，再查現有 Vue 元件、呼叫端與實際資料行為。
- 需說明**為什麼適用**、差異在哪、可重用程度；不能因外觀看似相同就改變選擇、保存、取消、關聯或導航語意。
- 如已人工認可的畫面與一般規範有衝突，先說明而不無授權重構。不能只說「參考全站風格」而沒有實際對照。

## 階段切換與授權

- **①～④ 可以連續進行**，若本輪僅要求設計／規劃，停在可供使用者審閱的方案；「請設計」不等於「開始寫程式」。
- **④ → ⑤**：依目前有效的 `AGENTS.md` 取得必要的方案確認與寫入授權。當使用者已確認計畫並說「開始開發」，在原授權範圍內可連續實作與測試，不為每個檔案或技術步驟反覆詢問。
- **低風險局部修改**：使用者偏好明確、狹義且低風險的修改，可在簡短說明範圍後直接執行。是否需要先等待確認仍依目前有效的 `AGENTS.md` 判斷；不能用 Skill 規避上位限制。
- **須停下重新確認**：將改變已核准業務行為、主要操作流程、資料保存／刪除語意或方案範圍；發現重大設計衝突或不可逆風險；需進行 `AGENTS.md` 限制的操作（例如 API endpoint 變動的預告、schema／SQL 執行、Git 寫入、部署）。一般元件重用、token、內部實作選擇不反覆詢問。
- **⑤ → ⑥**：程式改好及必要驗證完成後回報；無法驗證則明確標記「未驗證」，不能因此宣稱 UI 或功能整體完成。

## 驗證與額度界線

涉及第五、六階段時按需讀取 [references/delivery-and-verification.md](references/delivery-and-verification.md)。重點：

- 遵守目前 `AGENTS.md` 的必要 build、test、權限、資料完整性、草稿保護與清理生命週期規範；先做受影響範圍驗證，必要時再做完整檢查。
- **客觀 UI 行為與主觀視覺分開驗證**：布局溢位、響應式重排、焦點、關閉、選取與導航等行為，若既有工具可覆蓋，執行聚焦檢查；色彩、間距密度與整體感受由使用者人工驗收。不批次巡頁截圖、不產 PNG／HTML 草圖或 demo 頁面，也不為「看起來比較好」自行反覆重做。
- 使用者提供截圖圈選時，優先直接針對截圖與相關程式定位問題；後續修正視為一個**新局部任務**，不是無限制的自動迴圈。
- **分別說明**：程式／測試通過、實際瀏覽器已查證（若有）、使用者人工驗收（若尚未做，必須標示待驗）。不要以 Markdown 草圖或 build 成功宣稱視覺已通過。
- 禁止為了節省 credit 略過必要安全或資料測試；也不要為單次驗收臨時開發瀏覽器控制框架或測試資料工具。

## 輸出精度與文件維護

- 規劃時以最小足夠的操作對照、改動點、風險與驗證方案為主；**不要求每一階段產生獨立 Markdown 文件**。
- 只有重大且長期可重用的設計決策才建議更新對應文件，未經授權不修改 `AGENTS.md`、其他非任務範圍文件或新增 Skill。
- 交付簡述已完成項目、修改檔案、測試結果、需人工檢查的行為與未完成事項。不得虛構驗證結果。若使用者只要設計，直接給可審閱方案即可。
